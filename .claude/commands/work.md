# /work — 구현 + diff 리뷰

사용법:
- `/work <task-id>` — 계획서의 작업 항목을 구현하고 Codex diff 리뷰를 받는다
- `/work` — 인자 없으면 진행 중 task 를 찾아 제시하고 승인받아 확정

> **축소 이력 (2026-08-26)**: 12-step 상태머신(lock · `state.json` · `review_plan` · gate TSV · metrics TSV)과 **diff 3-chunk 분할**을 제거했다.
> 실측 근거 — 상태머신은 결함 발견 0건이면서 런당 Bash 왕복 10~15회를 소모했고, chunk 분할은 ③ PR3d 에서 **24건 중 10건을 "분할 아티팩트" 오탐**으로 만들었다. 조각만 본 리뷰어는 조각 밖을 결함으로 신고한다.
> 진행 상태는 `state.json` 이 아니라 **계획서의 체크박스**로 남긴다.

---

## 절차

### 1. task 확정 + 계획서 로드
- `TASK_ID` 확정 (`[A-Za-z0-9._-]+`, `..` 및 선두 `-`/`.` 금지)
- `docs/plans/${TASK_ID}.md` 를 읽는다. 없으면 `/plan` 을 먼저 돌리도록 안내하고 종료.
  **등급 S 도 계획서가 있다** (최소형). 없다는 것은 `/plan` 을 안 돌렸다는 뜻이지
  작은 작업이라는 뜻이 아니다
- 계획서의 **§검증 방법**을 먼저 읽는다 — 구현은 그 표를 만족시키는 것이 목표다
- 등급을 읽는다. 이후 리뷰 단계가 이 값으로 갈린다

```bash
bash -c 'source .claude/scripts/shared-logic.sh; hpx_plan_grade "<TASK_ID>"'
```

| 등급 | diff 리뷰 | 재리뷰 | audit |
|---|---|---|---|
| S | 없음 | 없음 | 없음 |
| M | 1회 | 없음 | 1블록 |
| L | 1회 | 조건부 1회 | 라운드별 |

**§8 검증은 등급과 무관하게 전부 수행한다.** 등급이 줄이는 것은 리뷰이지 테스트가 아니다.

### 2. 브랜치
- 현재 브랜치가 이미 이 task 의 브랜치면 그대로 사용
- `main` 이면 `feat/${TASK_ID}-<한 단어 요약>` 을 제안하고 확인받아 `git switch -c`
- 다른 task 의 브랜치 위에 있으면 **중단하고 보고**한다

### 3. 구현
계획서의 작업 항목(`P1.`, `P2.`, ...)을 순회하며 구현한다.

- 항목 완료 시 계획서의 해당 체크박스를 `- [x]` 로 갱신한다 — 이게 진행 상태의 정본이다
- **계획과 다르게 구현하게 되면 계획서를 먼저 고친다.** 코드와 계획이 갈라진 채로 리뷰에 들어가면 리뷰어가 그 차이를 전부 결함으로 신고한다
- 검증 항목은 구현과 **같은 커밋 범위 안에서** 작성한다. "테스트는 나중에"는 §검증 방법을 무력화한다

### 4. diff 캡처
```bash
cd "$(git rev-parse --show-toplevel)"
BASE=$(git merge-base HEAD origin/main)
DIFF=".cache/codex-reviews/diff-${TASK_ID}-$(date +%s).patch"
mkdir -p .cache/codex-reviews
git diff "$BASE" > "$DIFF"
wc -l < "$DIFF"; git diff --stat "$BASE" | tail -20
```
- diff 가 비어 있으면 "변경사항 없음" 보고 후 종료

### 5. Codex diff 리뷰 — **통짜 1회**

**등급 S 는 이 절을 통째로 건너뛰고 8(검증) 로 간다.** 6 과 7 도 함께 건너뛴다.
리뷰 상태는 `해당 없음(등급 S)` 이다. M 과 L 은 계속 진행한다.

#### 5-0. 호출 게이트 (생략 금지)

Codex 를 부르기 전에 **먼저** 판정을 받는다. 스스로 판단해서 부르지 않는다.

```bash
cd "$(git rev-parse --show-toplevel)"
bash -c 'set -uo pipefail
source .claude/scripts/shared-logic.sh
hpx_codex_allowed "<TASK_ID>"
'
```

- 1행이 `allowed` 면 아래 5-1 을 수행한다
- 1행이 `blocked` 면 **5-1 을 건너뛰고 8(검증) 로 간다.** 6(결과 처리)과 7(재리뷰 판정)도
  함께 건너뛴다. 2행(source), 3행(reason), 4행(origin)을 그대로 보고하고, 리뷰 상태를
  `의도적 생략(<source>: <reason>)` 으로 기록한다. 이것은 **정상 종결**이다 (§9 참조)

차단 신호와 설정 방법은 `/plan` §5-0 과 같다. 스위치가 워크트리마다 따로라는 점도 같다.
사용자가 대화에서 "이번엔 Codex 돌리지 마"라고 하면 `.cache/codex-off` 에 사유와 함께
적는다. 말로 받은 지시는 다음 세션에서 사라진다.

**게이트가 막아도 §8 검증은 반드시 수행한다.** 리뷰를 생략하는 것이지 테스트를 생략하는
것이 아니다.

#### 5-1. 호출

```bash
RAW=".cache/codex-reviews/diff-${TASK_ID}-$(date +%s).json"
ERR="${RAW%.json}.stderr"

codex exec --cd "$(pwd)" --output-schema .claude/schemas/diff-review.json >"$RAW" 2>"$ERR" <<EOF
[역할] PeakCart 프로젝트의 시니어 코드 리뷰어
[원칙]
  - 추측 금지. diff 와 계획서, ADR 을 직접 읽고 인용
  - "괜찮아 보입니다" 같은 무내용 응답 금지
  - 한국어로 답변
[리뷰 대상] ${DIFF}
[계획서] docs/plans/${TASK_ID}.md
[맥락] <선행 PR · 이번 PR 범위 · 의도적으로 범위 밖인 것을 여기에 적는다>
[체크 항목]
  - 계획서 의도와 diff 의 일치 (누락/초과 구현)
  - 버그, race condition, null/empty 처리, 트랜잭션 경계
  - **false-green**: 테스트가 계약이 아니라 구현을 기술하고 있는가.
    단위 mock 이 트랜잭션 경계를 증명하지 못하는가. 검증 대상과 검증 도구가 같은 출처인가
  - 시큐리티 (입력 검증, 권한, 시크릿 노출)
  - 컨벤션 (네이밍, 패키지 위치 — CLAUDE.md 의 4-Layered 규칙)
[필수 필드] run_id 는 "${RUN_LABEL}" 로 고정. items[].id 는 1부터 시작.
EOF
```

**분할하지 않는다.** diff 가 커서 한 번에 안 들어가면 그건 **PR 이 큰 것**이므로, 분할이 아니라 **PR 분할**을 사용자에게 제안한다. 그래도 강행한다면 라인 수가 아니라 **모듈 경계**로 나누고, 각 조각의 프롬프트에 "이 조각 밖에 무엇이 있는지" 를 명시해 분할 아티팩트를 줄인다.

`[맥락]` 은 매번 채운다 — 비우면 의도적으로 후속 PR 로 미룬 것을 누락으로 오탐한다.

### 6. 결과 처리
```
=== Codex diff 리뷰 (N건) ===
[P0] 머지 차단  [P1] 강력 권고  [P2] nit

  [1] P0/P1만 반영 (기본)
  [2] 전체 반영
  [3] 항목 선택
  [4] 무시하고 진행   ← P0 ≥ 1건이면 사유 필수
  [5] 종료
```

**기각은 근거와 함께 기록한다.** 특히 "분할 아티팩트"·"범위 밖" 기각은 그 판단이 맞는지 diff 를 다시 보고 확정한다.
**내 테스트가 잘못된 구현을 정당화하고 있었다**는 지적은 최우선으로 다룬다 — 이 프로젝트에서 반복 발생한 유형이다.

### 7. 재리뷰 판정

**등급 L 만 해당한다.** M 은 라운드 1로 끝낸다 — 계약 표면이 하나 이하라 "수정이 만든 새 결함"
이 번질 범위가 좁다. M 에서 라운드 1이 P0 를 냈다면 그건 등급 판정이 틀렸다는 신호이므로,
재리뷰 대신 **등급을 L 로 올리고** 그 사실을 audit 에 남긴다.

**조건부 1회.** 라운드 1에서 **P0/P1 을 실제로 수정했다면** 1회 더 돌린다 — 수정이 새 결함을 만들었는지 보기 위해서다. ④-c-1a 에서 라운드2 8건 중 **2건이 라운드1 수정이 만든 새 결함**이었다.

P2 만 고쳤거나 수정이 없었으면 재리뷰하지 않는다.

재리뷰 프롬프트에 **무엇을 고쳤는지** 나열하고 "그 수정이 만든 새 결함" 을 최우선 체크로 명시한다.

상한: 3회.

### 8. 검증
종료 전에 반드시 실행하고 **결과를 그대로 보고**한다:
```bash
./gradlew test
```
- 계획서 §검증 방법의 각 행이 실제로 통과했는지 대조한다
- 관련 lint 스크립트(`scripts/*-lint.sh`) 실행
- **실패가 있으면 실패라고 보고한다.** 미충족 항목은 완료 보고에 명시한다

### 9. 종료

**리뷰 상태는 4값이다.** 앞의 셋은 전부 정상 종결이고, 미결은 마지막 하나뿐이다.

| 값 | 의미 | 미충족에 오르나 |
|---|---|---|
| `수행(N라운드)` | 돌렸다 | 아니오 |
| `해당 없음(등급 G)` | 그 등급의 절차에 없는 단계다 | 아니오 |
| `의도적 생략(<사유>)` | 대상이지만 판단해서 안 돌렸다. 5-0 게이트 차단 포함 | 아니오 |
| `미결(<사유>)` | 돌리려 했으나 실패했거나 중단됐다 | 예 |

"안 돌렸다"를 `미결` 로 적지 않는다. 게이트가 `blocked` 를 냈으면 그것은 `의도적 생략` 이고,
보고와 PR 본문에서 미충족 항목으로 취급하지 않는다. `P0/P1 = 0` 을 주장하지 않는 것과
`미완이다` 는 다른 말이다.

- audit 파일 `docs/plans/${TASK_ID}.audit.md` 에 1블록 append:
  ```markdown
  ## YYYY-MM-DD HH:MM — diff 리뷰 라운드 N
  - 상태: 수행(N라운드)
  - 항목: X건 (P0:N, P1:N, P2:N)
  - 처리: 반영 N건 / 기각 N건 (기각 사유)
  - 라운드1 수정이 만든 새 결함: (있으면)
  - 검증: N 테스트 M 실패 · lint
  - raw: .cache/codex-reviews/diff-...json
  ```
  생략한 경우는 라운드 블록을 만들지 않고 상태와 검증만 적는다:
  ```markdown
  ## YYYY-MM-DD HH:MM — diff 리뷰
  - 상태: 의도적 생략(env: HPX_CODEX=off)
  - 검증: N 테스트 M 실패 · lint
  ```
  **등급 S 는 audit 파일을 만들지 않는다.** 검증 결과는 완료 보고에만 남긴다.
  M 은 1블록, L 은 라운드별이다.
- **compound capture (필터 — 기본값은 prose 저장 안 함)**: 구현이 계획과 크게 달랐던 항목이 있으면 3-질문 라우팅(`docs/plans/PLAN-BLINDSPOTS.md` 상단)을 적용한다 — ① 반복되나 ② 재도출 어렵나 ③ 더 싼 자동검사로 못 바꾸나. **자동화 가능 → 가드/픽스로, prose 저장 안 함** / **셋 다 Yes → `Bn` 또는 메모리** / **그 외 → 폐기**
- 보고: 구현 요약 · 반영/기각 · **검증 결과(실패 포함)** · 미충족 항목 · 다음 단계 `/ship`
