# /plan — 계획 수립 + Codex 리뷰

사용법:
- `/plan <task-id>` — 지정 task 의 계획서를 작성/보강하고 Codex 리뷰를 받는다
- `/plan` — 인자 없으면 `docs/TASKS.md` 의 "다음 항목" 을 제시하고 승인받아 확정

> **축소 이력 (2026-08-26)**: 12-step 상태머신(lock · `state.json` · gate TSV · metrics TSV · `pending_run` finalize)을 제거했다.
> 실측 근거 — 해당 기구는 결함 발견 0건이면서 런당 Bash 왕복 10~15회를 소모했다. 결함을 실제로 잡아온 것은 **Codex 리뷰 본체**이므로 그것만 남긴다.
> 이력은 `state.json` 이 아니라 **audit 파일과 git 이력**으로 남긴다.

---

## 절차

### 1. task 확정 + 등급 판정
- 인자가 있으면 그것이 `TASK_ID`. 없으면 `docs/TASKS.md` 를 읽고 다음 항목을 제시해 승인받는다.
- `TASK_ID` 는 `[A-Za-z0-9._-]+` 만 허용하고 `..` · 선두 `-`/`.` 를 금지한다. 경로 보간 전에 확인한다.
- 계획서 경로: `docs/plans/${TASK_ID}.md`

**등급을 task 확정과 같은 왕복에서 정한다.** 이미 사용자와 한 번 주고받으므로 추가 왕복이 없다.

판정 기준은 셋이다. 계획 이전이라 diff 크기를 모르므로 크기가 아니라 **파급**으로 가른다.

1. 건드리는 모듈이 2개 이상인가
2. 다른 곳에서 참조하는 계약 표면(공개 API, 이벤트 스키마, DB 스키마, 설정 키, 공유 모듈)이 바뀌는가
3. 되돌리려면 이 작업 밖의 파일도 같이 고쳐야 하는가

셋 다 아니면 **S**, 하나면 **M**, 둘 이상이면 **L**. 애매하면 높은 쪽을 고른다.

> "이 작업을 S 로 봅니다. 근거: 단일 모듈, 계약 표면 무변화, 되돌림 국소. 맞습니까?"

확정한 등급은 계획서 frontmatter 에 적는다. **대화로만 받은 등급은 다음 세션에서 사라진다.**

```markdown
---
grade: S
---
```

이후 단계와 `/work`, `/ship` 은 이 값을 읽는다.

```bash
bash -c 'source .claude/scripts/shared-logic.sh; hpx_plan_grade "<TASK_ID>"'
```

frontmatter 가 없거나 값이 부적격이면 **L 로 떨어진다.** 기존 계획서 수십 개에 frontmatter 가
없고, 모르는 작업은 무겁게 처리하는 쪽이 안전하다. 부적격 값은 stderr 로 알린다.

### 1-1. 등급별 절차

| | S | M | L |
|---|---|---|---|
| 계획서 | 최소형 (아래 §4) | 명제 · 작업 항목 · 검증 방법 | 전체 5섹션 |
| 코드 검증 (§2) | grep 후 구두 보고 | 표 필수 | 표 + PLAN-BLINDSPOTS |
| ADR 판단 (§3) | 대상 아님 | 판단 | 판단 |
| Codex 계획 리뷰 (§5) | 없음 | 없음 | 1회 |
| Codex diff 리뷰 (`/work`) | 없음 | 1회 | 1회 + 조건부 재리뷰 |
| audit 파일 | 없음 | 1블록 | 라운드별 |

**S 도 계획서를 만든다.** 애초 구상은 "S 는 계획서 없음" 이었으나, `/work` 와 `/ship` 이
계획서 존재를 전제로 동작하고 등급을 적어둘 자리도 사라진다. 대신 최소형으로 줄인다.
10줄 안쪽이면 충분하다.

등급이 S 나 M 이라서 건너뛴 단계는 리뷰 상태 `해당 없음` 이다. 미결이 아니다 (§8 참조).

### 2. 전제를 코드로 검증 (생략 금지)

등급과 무관하게 수행한다. 달라지는 것은 **기록 형식**뿐이다. S 는 구두 보고, M 과 L 은 표.
검증 자체를 건너뛰는 등급은 없다 — 있는 걸 또 만드는 계획을 막는 장치라 크기와 무관하다.

**계획의 전제는 설계문서(ADR)가 아니라 현재 코드다.** 초안 작성 **전에** 직접 grep/파일 확인한다:
- 인용한 구성요소가 **이미 존재하는가** (있는 걸 또 만드는 계획이 되지 않도록)
- 의존 **방향** (무엇이 무엇을 참조하나)
- 부모 계획이 요구한 항목 중 **이미 완료된 것**

라이브러리 동작을 전제로 삼을 때는 **실제 jar/소스를 열어 확인**한다. 문서 기억이나 추측으로 적지 않는다.
검증 결과는 M 과 L 이면 계획서 §배경에 표로 남긴다. S 는 구두 보고로 갈음한다.
어느 등급이든 **여기서 범위가 줄거나 늘면 그 사실을 명시한다** — 범위 변화는 등급 재판정
사유이기도 하다(§1 로 돌아간다).

**구조 변경(모듈/경계 변경·코드 이동·peel·rename)이면** — 정의상 L 등급이다 — `docs/plans/PLAN-BLINDSPOTS.md` 의 각 항목을 수행하고 결과를 §배경에 기록한다. 특히 B1 역의존 스윕 — 옮기는 대상을 밖에서 참조하는 인바운드 의존(테스트 포함)을 grep 으로 뽑아 처분(이동/디커플/유지)을 한 줄씩 적는다. 이 표가 없으면 다음 단계로 넘어가지 않는다.

### 3. ADR 선행 판단

**등급 S 는 대상이 아니다.** S 의 정의(단일 모듈·계약 표면 무변화·되돌림 국소)가 곧
ADR 이 필요 없다는 뜻이다. 만약 ADR 이 필요해 보이면 등급 판정이 틀린 것이므로 §1 로 돌아간다.

M 과 L 은 아래 중 하나라도 해당하면 사용자에게 묻는다 — 없으면 자동 통과(보고 불필요):
- 새로운 외부 의존성 (DB/큐/SaaS)
- 아키텍처 경계 (레이어/모듈/바운디드 컨텍스트) 변경
- 새로운 환경/인프라 (GCP 리소스, k8s 네임스페이스)

판정이 애매하면 되돌리기 비용으로 가른다. **이 결정을 6개월 뒤 뒤집을 때 이 파일 밖의 것도
같이 고쳐야 하는가.** 그렇다면 ADR 이다. 한 파일 안에서 끝나면 코드 주석이나 progress 한 줄로
족하다.

> "위 신호로 ADR 선행이 필요해 보입니다. ADR 작성 후 다시 /plan 을 호출할까요?"

### 4. 계획서 작성

필수 섹션은 등급에 따라 다르다. 공통으로 frontmatter 에 `grade:` 를 적는다.

- **L**: §1 명제 · §2 배경(코드 검증 결과 포함) · §3 작업 항목 · §검증 방법 · §완료 조건
- **M**: §1 명제 · §2 작업 항목 · §3 검증 방법 (배경은 명제 안에 한두 줄로 녹인다)
- **S**: 아래 최소형

```markdown
---
grade: S
---
# <task-id>

## 명제
<무엇이 성립하면 미완인가. 한 줄>

## 작업 항목
- [ ] P1. <항목>
- [ ] P2. <항목>

## 검증
<실패를 주입해 확인하는 방법 한두 줄>
```

등급이 무엇이든 **명제, 작업 항목, 검증** 셋은 남는다. 이 셋이 빠지면 완료 판정이 불가능해서
등급의 문제가 아니라 계획서가 아니게 된다.

- **명제는 부정형으로 고정한다** — "무엇이 성립하면 미완인가". 긍정형 목표는 완료 판정이 흐려진다.
- 작업 항목은 **stable id** (`P1.`, `P2.`, ...) 강제
- 검증 방법은 항목별로 **"실패를 주입한 뒤 DB/상태로 확인"** 형태여야 한다. "존재한다"·"배선됐다"는 검증이 아니다.
- 범위 밖 항목은 §미해결에 처분과 함께 남긴다

Codex 호출 **전에** 필수 섹션과 stable id 를 자체 점검한다. 형식이 깨졌으면 고치고 나서 호출한다 — 형식 오류에 리뷰 토큰을 쓰지 않는다.

### 5. Codex 리뷰

**계획 리뷰는 L 등급만 돈다.** S 와 M 이면 이 절을 통째로 건너뛰고 8 로 간다. 리뷰 상태는
`해당 없음(등급 <G>)` 이다.

```bash
bash -c 'source .claude/scripts/shared-logic.sh; hpx_plan_grade "<TASK_ID>"'
```

#### 5-0. 호출 게이트 (생략 금지)

등급이 L 이어도 Codex 를 부르기 전에 **먼저** 판정을 받는다. 스스로 판단해서 부르지 않는다.

```bash
cd "$(git rev-parse --show-toplevel)"
bash -c 'set -uo pipefail
source .claude/scripts/shared-logic.sh
hpx_codex_allowed "<TASK_ID>"
'
```

- 1행이 `allowed` 면 아래 5-1 을 수행한다
- 1행이 `blocked` 면 **5-1 을 건너뛰고 6 으로 간다.** 2행(source), 3행(reason), 4행(origin)을
  그대로 보고하고, 리뷰 상태를 `의도적 생략(<source>: <reason>)` 으로 기록한다. 이것은
  **정상 종결**이다. 미결로 남기지 않는다 (§8 참조)

차단 신호는 셋이고 먼저 걸리는 것이 이긴다.

| 신호 | 설정 방법 | 지속 범위 |
|---|---|---|
| `HPX_CODEX` 환경변수 | `off` / `0` / `false` / `no`. `on` 은 나머지를 덮는 override | 셸 세션 |
| `.cache/codex-off` 파일 | 파일을 만들고 첫 줄에 사유를 적는다 | 지울 때까지 |
| 계획서 frontmatter | `docs/plans/<task-id>.md` 선두 `---` 블록에 `codex: off` | 그 task |

**스위치는 워크트리마다 따로다.** `.cache/` 와 `docs/plans/` 는 현재 워크트리 기준으로
해석된다. 이 레포는 본 체크아웃과 orca 워크트리에서 서로 다른 task 를 동시에 돌리므로,
한쪽에서 리뷰를 끈 것이 다른 쪽 작업까지 끄면 안 된다. 스위치가 안 먹는 것처럼 보이면
4행 origin 이 가리키는 경로부터 확인한다. `.cache/` 가 없으면 `mkdir -p .cache` 가 먼저다.

사용자가 대화에서 "이번엔 Codex 돌리지 마"라고 하면, 그 지시를 기억에 담아두지 말고
`.cache/codex-off` 에 사유와 함께 적는다. 말로 받은 지시는 다음 세션에서 사라진다.

#### 5-1. 호출

```bash
cd "$(git rev-parse --show-toplevel)"
mkdir -p .cache/codex-reviews
RAW=".cache/codex-reviews/plan-${TASK_ID}-$(date +%s).json"
ERR="${RAW%.json}.stderr"

codex exec --cd "$(pwd)" --output-schema .claude/schemas/plan-review.json >"$RAW" 2>"$ERR" <<EOF
[역할] PeakCart 프로젝트의 시니어 아키텍처 리뷰어
[원칙]
  - 추측 금지. 파일을 직접 읽고 인용
  - "괜찮아 보입니다" 같은 무내용 응답 금지
  - 한국어로 답변
[리뷰 대상] docs/plans/${TASK_ID}.md
[맥락] <부모 계획 · 선행 PR · 이번 PR 의 위치를 여기에 적는다>
[이번 PR 의 계약 표면] <공개 API · 이벤트 스키마 · DB 스키마 · 설정 키 중 이번에 건드리는 것>
[범위 밖] <의도적으로 후속으로 미룬 것. 여기 적힌 것을 누락으로 신고하지 마라>
[항목 분류] 각 item 에 scope 를 붙여라.
  in_scope     = 위 계약 표면 안
  out_of_scope = 범위 밖. 지적은 남기되 이번에 고칠 것으로 제안하지 마라
  new_surface  = 이 계획이 새로 만드는 표면
  또한 suggested_disposition 을 reflect / defer / reject 중 하나로 제안하라.
[체크 항목]
  - ADR(docs/adr/) 결정과의 충돌
  - 계획서가 코드 사실을 잘못 진술한 곳 (직접 확인하여 반증)
  - 누락된 작업 항목 (테스트·마이그레이션·문서·배포/롤백 순서)
  - 트레이드오프 누락
  - 검증 방법이 false-green 을 실제로 막는가
  - 작업 항목 id 규약(P1., P2., ...) 준수
[필수 필드] run_id 는 "${RUN_LABEL}" 로 고정. items[].id 는 1부터 시작.
EOF
```

`[맥락]` 은 매번 채운다 — 비우면 리뷰어가 이미 끝난 선행 작업을 누락으로 오탐한다.

### 6. 결과 처리
severity 별로 묶어 표로 제시하고 선택지를 준다:

```
=== Codex 계획 리뷰 라운드 N (총 N건: P0 a / P1 b / P2 c) ===
라운드 1 = 전 항목 처분 · 라운드 2 = P0 만 반영 (§7)

  [1] 권장 처분대로 (P0 반영 · P1 항목별 판정 · P2 이월)
  [2] 항목 선택
  [3] 전체 반영          ← 범위가 커진다. 사유 필수
  [4] 전체 이월          ← P0 ≥ 1건이면 사유 필수
  [5] 종료
```

**처분은 셋이다.** 지적이 맞다는 것과 이번 PR 에서 고친다는 것을 분리한다.

| 처분 | 의미 | 귀결 |
|---|---|---|
| 반영 | 이번 PR 에서 고친다 | 코드/계획서 변경 |
| **이월** | 지적은 맞지만 이번 범위가 아니다 | PR 본문 §이월 에 재검토 조건과 함께 기록 |
| 기각 | 지적이 사실과 다르다 | 사유 기록. 근거를 다시 확인한 뒤 확정 |

**이월이 기본 완충재다.** 이월이 없으면 "맞는 지적"이 곧바로 "지금 해야 할 일"이 되고,
그래서 작업이 라운드마다 커진다. 실측으로 이 프로젝트의 기각률은 0.3%(307건 중 1건)였고
P0 는 2.0%(442건 중 9건)였다. 즉 머지를 막지 않는 지적을 거의 전부 그 자리에서 구현해 왔다.

이월이 구조적이거나 반복되는 성질이면 `docs/TASKS.md` 의 부채 행(D-0NN)으로 승격한다.
한두 건이면 PR 본문 §이월 에만 남긴다. 부채 ID 를 남발하지 않는다.

severity 별 기본 처분:

| | 기본 | 비고 |
|---|---|---|
| P0 | 반영 | 예외는 사유 필수 |
| P1 | **판정 필요** | 반영·이월·기각 중 하나를 항목마다 고르고 한 줄 사유 |
| P2 | 이월 | 묶어서 한 줄. 같은 PR 에서 고칠 이유가 있으면 반영 |

P1 을 일괄 반영하지 않는다. 그 일괄 처리가 지금까지 작업 증가의 주 동력이었다.

**리뷰가 내 진술을 반증하면 직접 확인한 뒤 수용한다.** 반증 근거가 코드/바이너리면 그것을 열어보고, 확인 결과를 계획서에 **정정 이력으로 남긴다**(초안이 뭘 틀렸는지 포함). 조용히 고치지 않는다.

P0/P1 이 0건이면 자동 통과 — 1줄 요약만 보고한다.

### 7. 재리뷰 판정

**등급 L 만 해당한다.** S 와 M 은 라운드 1로 끝낸다.

라운드 2는 **검증 라운드**다. 새 설계를 보는 자리가 아니라 라운드 1의 수정이 제대로 됐는지
확인하는 자리다. 질문을 닫아서 돌린다.

```
[리뷰 대상] 라운드 1에서 반영한 아래 N개 항목만 검사하라.
  1. <원 지적> → <무엇을 고쳤는지>
  2. ...
[질문] 각 항목에 대해 두 가지만 답하라.
  (a) 그 수정이 원 지적을 실제로 해소했는가
  (b) 그 수정이 기존 동작이나 다른 항목을 깼는가
[금지] 새로운 개선 제안을 하지 마라. 위 두 질문 밖의 발견은 severity 를 P2 로 두고
       scope 를 out_of_scope 로 표시만 하라. 본문에서 논하지 마라.
```

**라운드 2에서는 P0 만 반영한다.** P1 과 P2 는 전부 이월이다.

"새 코드를 리뷰하라"는 무한하고 "고친 것을 검증하라"는 N개로 유한하다. 종전 프롬프트는
"1라운드 수정이 만든 새 결함을 찾아라"라는 열린 질문이어서 매 라운드 새 지적이 나왔다.

**상한: 2회.** 종전 3회였으나 실측상 라운드 3이 수렴에 기여한 증거가 없다. 18개 계획서에서
라운드 3 도달이 20회인데 전부 미수렴이거나 상한 종료였다. 2회를 넘겨야 할 사정이 있으면
사용자에게 명시 확인한다.

종료 조건을 "P1 = 0"으로 두지 않는다. P1 을 반영하면 계약 표면이 늘고 다음 라운드가 그것을
지적하므로, 루프가 만들어내는 것으로 종료를 정의하는 셈이 된다. 종료는 **예산**으로 정한다.
라운드 1에서 전 항목을 처분했고 라운드 2에서 P0 가 0이면 끝이다.

### 8. 종료

**리뷰 상태는 4값이다.** 앞의 셋은 전부 정상 종결이고, 미결은 마지막 하나뿐이다.

| 값 | 의미 | 미충족에 오르나 |
|---|---|---|
| `수행(N라운드)` | 돌렸다 | 아니오 |
| `해당 없음(등급 G)` | 그 등급의 절차에 없는 단계다 | 아니오 |
| `의도적 생략(<사유>)` | 대상이지만 판단해서 안 돌렸다. 5-0 게이트 차단 포함 | 아니오 |
| `미결(<사유>)` | 돌리려 했으나 실패했거나 중단됐다 | 예 |

"안 돌렸다"를 `미결` 로 적지 않는다. 게이트가 `blocked` 를 냈으면 그것은 `의도적 생략` 이고,
보고와 PR 본문에서 미충족 항목으로 취급하지 않는다.

- audit 파일 `docs/plans/${TASK_ID}.audit.md` 에 1블록 append:
  ```markdown
  ## YYYY-MM-DD HH:MM — 계획 리뷰 라운드 N
  - 상태: 수행(N라운드)
  - 항목: X건 (P0:N, P1:N, P2:N)
  - 처리: 반영 N건 / **이월 N건** / 기각 N건 (이월·기각 사유)
  - 이월 항목: <재검토 조건. 부채로 승격했으면 D-0NN>
  - 뒤집힌 전제: (있으면)
  - raw: .cache/codex-reviews/plan-...json
  ```
  생략한 경우는 라운드 블록을 만들지 않고 한 줄로 끝낸다:
  ```markdown
  ## YYYY-MM-DD HH:MM — 계획 리뷰
  - 상태: 의도적 생략(file: GKE 측정 세션이라 리뷰 불필요)
  ```
  **등급 S 는 audit 파일 자체를 만들지 않는다.** M 은 1블록, L 은 라운드별이다.
  S 에서 리뷰가 없었다는 사실은 계획서 frontmatter 의 `grade: S` 가 이미 말한다.
- 계획서 경로 · 수용/기각 요약 · 범위 변화 · 다음 단계(`/work`) 보고
