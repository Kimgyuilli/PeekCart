## 읽는 법

### ① S2 는 "미측정" 이지 "효과 없음" 이 아니다

OFF 셀이 재는 것이 MySQL 이 아니라 bulkhead 다. ①(list 배속)·②(2000m 새 천장)는 질문의 전제(캐시 miss 가 DB 동시성을
그대로 쓴다)가 ADR-0037 로 바뀌었고, ③④는 셀(B detail ON·list ON)을 돌리지 않았다. 재측정 전에 bulkhead 를 둔 채로
물을 질문을 다시 정해야 한다.

### ② ⑤ 의 before/after 는 DLQ 비율로만 비교한다

Phase 4 의 "충돌 7" 은 `OptimisticLockingFailureException` 로그 수이고 이번 "전달 실패" 는 재시도 시도마다 증가하는
`kafka_listener_delivery_failed_total` 이다. 세는 단위가 달라 충돌 수끼리는 비교하지 않는다. DLQ 는 둘 다 최종 실패 건수라
비교할 수 있다. 노드(2대 vs Phase 4)·이미지·k6(v2.2.0 동일)를 함께 적는다.

### ③ 대조군이 대조군 역할을 못 했다

spread 의 전달 실패(129)가 contend(31~61)보다 많다. 상품 10개를 replica 3 이 나눠 소비하면 같은 상품 행에 동시 쓰기가
여전히 생기고, 처리량이 높을수록(spread p50 51ms) 더 겹친다. "대조군의 충돌 = 다른 원인" 은 이 조건에서 성립하지 않는다.

### ④ run 간 주문 수 차이는 워밍업이다

주문 p50 이 1,205 → 701 → 151 → 51ms 로 떨어졌다. 배포 직후 첫 run 은 order-service CPU 1.89코어(한도 2)·VU 200 포화로
목표 170/s 의 44% 만 냈다. S3 에는 워밍업 규칙이 없었다. DLQ/주문 비율은 run 간 주문 수와 무관하게 0.04~0.07% 로 묶인다.

### ⑤ 왕복 지연은 처리 속도가 아니다

r3 의 왕복 p50 272s 중 order 발행 대기 83s, product 발행 대기 154s 가 폴링 설정 몫이다. product 발행률 20.0건/초는
5s·100건 상한과 정확히 같다. 배수가 예약 lease 보다 길면 결제 대기 주문이 만료 스케줄러에 취소되며(r2·r3·spread),
Phase 4 경합 run 의 RELEASED 733 도 같은 기전으로 보인다. D-075(폴링 기본값 처분)의 입력이다.

## 배포 편차

1. 측정 overlay(`gke-d002a`·`gke-d078-contention`)에 ServiceMonitor 가 없어 base `servicemonitor.yml` 5개를 단계마다 수동 apply 했다.
   15초 scrape 가 앱 Pod 에 더해진다(d026 기준선에는 없었다).
2. S3·S4 payment Secret 에 Toss smoke 값(`test_sk_smoke`)을 넣었다. 계획서 S3 에는 이 단계가 없어 첫 apply 에서 payment 가 CrashLoop 했다. 외부 연동 미검증.
3. S4 첫 배포는 `GW_URL` 없이 했다. 빈 스택에는 시드 계정이 없어 래퍼의 인증 게이트가 실패하므로, 사용자 시드 뒤 게이트를 따로 돌렸다.
4. saga 대시보드 "CPU 스로틀 (컨테이너별)" 패널이 빈다. `container_cpu_cfs_throttled_seconds_total` 이 Prometheus 에 없다
   (`..._periods_total` 은 있다). 스로틀 수치는 하네스의 cgroup `cpu.stat` 차분이 정본이다.
5. S5 에서 Secret Manager 시크릿 4개와 GSA 2개는 재측정을 위해 남겼다(사용자 결정). AR 리포지토리는 삭제했다.
