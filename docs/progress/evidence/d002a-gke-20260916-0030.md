## 결론 — "왜 ×3 에 못 미쳤나" 에 답이 나왔다

**`×3` 이라는 목표가 조건 없는 숫자였다.** 캐시 배속은 상수가 아니라 **CPU 여유와 엔드포인트
구조의 함수**이고, 이 세션에서 **×1.23 ~ ×2.39** 사이에서 움직였다.

1차 측정의 **×2.31 은 이상치가 아니다** — CPU 포화 조건에서 잰 값이고, 같은 포화 조건(limit
1000m)에서 list 가 **×2.39** 로 재현됐다. 즉 그 값은 "미달" 이 아니라 **그 조건의 정상값**이다.

## 측정 행렬

**조건 A — CPU limit 1000m(base 값), 50 VU** · product-service CPU **922m/1000m = 포화**

| endpoint | 캐시 OFF | 캐시 ON | 배속 |
|---|---|---|---|
| detail `/api/v1/products/{id}` | 107.9 rps | 200.5 rps | **×1.86** |
| list `/api/v1/products` | 136.2 rps | 325.3 rps | **×2.39** |

**조건 B — CPU limit 3000m, 400 VU(포화 기준)**

| endpoint | 캐시 OFF | 캐시 ON | 배속 |
|---|---|---|---|
| detail | 378.1 rps | 463.6 rps | **×1.23** |
| list | 380.0 rps | 767.1 rps | **×2.02** |

### 읽는 법 3가지

**① CPU 여유를 주면 배속은 오히려 떨어진다.** 캐시 OFF 경로가 CPU 기아에서 더 많이 손해보고
있었기 때문이다 — detail OFF 는 107.9→378.1(**×3.5**) 로 뛰는데 ON 은 200.5→463.6(×2.3) 에
그친다. **캐시는 CPU 가 부족할 때 더 크게 보인다.**

**② 가장 큰 레버는 캐시가 아니라 CPU 상한이었다.** 캐시를 켠 채 limit 만 1000m→3000m 로
올리니 list 가 325.3→**715.1 rps**(50 VU 기준, ×2.2) 가 됐다. base 매니페스트의
`limits.cpu: 1000m`(`k8s/base/services/product-service/deployment.yml`)이 실질 천장이었다.

**③ detail 은 구조적으로 캐시 이득이 작다.** 포화 기준 ×1.23 으로 list(×2.02)의 절반이다.
원인은 코드에 있다 — `ProductQueryService.getProduct` 는 상품 정보만 캐시에서 읽고
**재고는 매번 DB 에서 조회**한다:

```java
ProductInfoDto info = productCacheService.getProductInfo(productId);   // 캐시
int stock = inventoryRepository.findByProductId(productId)             // 항상 DB
```

게다가 클래스가 `@Transactional(readOnly = true)` 라 캐시 적중 여부와 무관하게 트랜잭션이 열린다.

## 2차 병목 — CPU 도 커넥션 풀도 아니었다

캐시 OFF 천장이 **두 엔드포인트에서 거의 같다**(detail 378.1 / list 380.0). 공통 자원이 천장을
쥐고 있다는 뜻이다. 후보를 하나씩 배제했다:

| 후보 | 판정 | 근거 |
|---|---|---|
| product-service CPU | **아니다** | 천장 상태에서 354~690m / **3000m** |
| MySQL CPU | **아니다** | 207~356m |
| **Hikari 풀 10** | **아니다** | `maximum-pool-size=50` 으로 올려도 322.9 rps — **개선 없음**(오히려 -10%) |

**재정의 문서가 "Hikari 기본 풀 10 이 D-002b' 1순위 변수" 라고 적었는데, 이 측정이 그것을
반증했다.** 남은 후보는 MySQL 내부(단일 Pod · PVC `pd-standard` IOPS 등)이며 **이 세션에서
분리하지 못했다** — DB 측 계측이 필요하고 이 세션 예산 밖이다.

### 포화 판정 근거 (VU 램프, 캐시 OFF · 3000m)

| VU | TPS | avg |
|---|---|---|
| 100 | 285.8 | 348ms |
| 200 | 353.9 | 559ms |
| 400 | 378.1 | 1.03s |

TPS 는 평평해지는데 지연만 선형으로 늘어난다 → **실제 포화**다.

> **방법론 주의**: 초기 50 VU 측정들은 전부 `TPS ≈ 50 / 지연` 을 만족했다. 즉 그 수치들은
> 처리량 천장이 아니라 **동시성에 묶인 값**이고, 조건 간 비교는 사실상 지연 역수 비교였다.
> 조건 B 를 400 VU 로 다시 잡은 이유다. **조건 A 는 50 VU 값이라 조건 B 와 직접 비교하지 말 것**
> (A 는 CPU 포화가 확인돼 그 조건의 유효값이지만, 축이 다르다).

## 계획 오류 2건

1. **Kafka 를 "읽기 경로 무관" 으로 제외했다가 되넣었다.** product-service 는 Kafka 없이는
   **부팅하지 않는다**(`internalKafkaListenerEndpointRegistry` 시작 실패 → CrashLoopBackOff).
   소비자가 있는 서비스는 읽기만 쓰더라도 브로커가 필요하다.
2. **시드가 두 번 틀렸다.** (a) `TRUNCATE` 는 앱 계정에 DROP 권한이 없어 1142 거부 → `DELETE`
   (최소 권한 설계대로다). (b) `status='ACTIVE'` 로 넣었는데 enum 은 `ON_SALE` 이라 목록이 비었다.

부수 관찰: 시드 이전의 **빈 목록·오류 응답이 캐시에 적재**돼 데이터를 넣은 뒤에도 그대로
반환됐다. `FLUSHALL` 후 정상화 — `redis-cache-fallback.md` §4(복구 후 stale 처리)와 같은 결이다.
