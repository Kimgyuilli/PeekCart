## 결론

1. **S2 상한 비교: "상한 4 증액 근거 있음".** 계획 §2.2 의 사전 규칙 네 조건이 모두 성립했다. 200 응답 rps 중앙값이 detail OFF
   26.5 에서 115.9, list OFF 30.3 에서 123.7 로 범위가 겹치지 않고, 503 이외 오류·Hikari 대기·MySQL 스로틀 차분이 모두 0 이다.
   ADR-0037 갱신은 사용자가 정한다.
2. **③ 측정, ④ 노드 경합 가설 기각.** detail ON 의 `product` 캐시는 hit 차분 168k~186k·miss 0 이다. list ON 에서 product-service
   노드의 CPU 최대는 84.0~84.6%(90% 미만), MySQL CPU 는 0.047코어라 hit 경로는 MySQL 을 거의 쓰지 않는다.
3. **S3(⑤⑥)는 측정 run 에 들어가지 못해 contend·spread 모두 "부하 미달"로 접었다.** 처음에는 order-service 가 부하 중 liveness
   실패로 재시작을 반복했고, 사용자 결정으로 측정 overlay 의 프로브를 완화했다. 그 뒤에는 수락이 초당 약 122건(목표 170)에서 멈췄다.
   order 의 DB 커넥션 풀이 MySQL 커밋(fsync) 대기로 포화된 상태이며, 원인은 분리하지 못했다.
4. **D-065 ②⑤ 는 실제 스택에서 통과했다.** drain preflight 가 단독 실행과 배포 래퍼 경로 양쪽에서 exit 0 이고, 토픽 상태 가드는
   토픽 30개(payment 6개 포함)와 업무 group 27개가 선언과 일치한다고 판정했다.
5. **배포 래퍼(D-107)와 토픽 가드(D-106 ⑩)의 첫 실사용이 통과했다.** 래퍼 다섯 번 모두 선언 토픽 30개를 만들고 파티션 수를
   대조했다. 가드는 S3 진입(22 group)·재기동 뒤(22 group)·S4(27 group)에서 exit 0 이었다.

## 읽는 법

### ① 상한 4 판정은 읽기 전용 부하의 풀 여유다

S2 스택에는 주문 경로가 없어 쓰기·메시지 소비가 거의 없다. Hikari 대기 0 은 읽기 부하에서의 여유이고, 예약 소비와 겹친 여유는
재지 않았다. 15초 scrape 보다 짧은 순간값도 놓친다. 증액을 결정할 때는 이 한계를 함께 적는다.

### ② S3 의 관찰값은 측정값이 아니다

⑤⑥ 은 이번에도 미측정이다. w6 의 DLQ/주문 0.068% 는 2026-10-24 범위(0.040~0.068%)와 겹치지만, 목표 부하가 들어가지 않은 run
이라 비교 근거로 쓰지 않는다. ⑥ 은 캡처상 taskScheduler active 최대가 order 3 / 풀 4 로 지난 세션과 같은 모양이다.

### ③ ADR-0045 는 product 쪽 지연과 만료 취소를 없앴다

product 발행 대기 p50 이 154초(2026-10-24 r3)에서 0.6초(w6)로, 만료 취소가 3,839건에서 0 으로 줄었고 사가 왕복 p50 은 272초에서
122초가 됐다. 사가 왕복 p99 198초는 재검토 조건 1 의 4분 아래다. 남은 지연은 order outbox 발행 대기(p50 83초, 두 세션이 같다)다.
부하 중 order 발행률이 수신을 못 따라가는 것은 재검토 조건 2 의 관찰과 같다.

### ④ 수신 상한(초당 약 122건)의 원인은 분리하지 못했다

2026-10-24 r3 는 같은 order 풀 10 으로 초당 168건을 받았다. 이번에는 CPU 가 아니라 커밋 완료 대기가 커넥션을 붙잡는다. 후보는
(가) ADR-0045 로 늘어난 product 쪽 커밋이 공유 MySQL 디스크의 커밋 지연을 키웠다, (나) USERS 450 의 동시성이 풀 앞 대기열을
키웠다, (다) 세션마다 새로 만드는 디스크·Pod 배치 차이다. product outbox 를 5s·100 으로 되돌린 A/B 나 USERS 200 대조로만 가를 수
있다.

### ⑤ 워밍업 1회로는 부족했다

프로브 완화 뒤 새 JVM 의 수락은 3,108 → 5,663 → 7,055 → 7,341 로 세 번째 run 부터 멈췄다. 결과를 보기 전에 "첫 유효 run 까지
워밍업(연장 최대 3회)"으로 규칙을 바꿨고, 그 안에 유효 run 이 없어 접었다. 다음 계획은 워밍업 종료를 객관 기준으로 사전 등록한다.

## 배포 편차

1. 사용자 결정으로 측정 overlay 에 order-service 프로브 완화 patch 를 더했다(`gke-d078-contention/patches/order-service-probes.yml`,
   liveness timeout 5초·12회, readiness 5초·6회). 계획 §5 "세션 안에서 고치지 않는다"의 예외다.
2. S3 워밍업 규칙을 세션 중에 바꿨다(위 ⑤). spread 는 같은 고정 상한이 확실해 재시도 2회 없이 1회 뒤 접었다.
3. S2·S3 스크린샷은 run 마다가 아니라 블록 구간(run 은 annotation)으로 찍었다. 원 시계열 export 는 run 마다 정확한 구간이다.
4. S4 의 notification Slack 두 값은 실제 webhook 대신 base 기본값과 같은 loopback 을 넣었다(D-092 를 반복하지 않음).
5. gateway 가 Internal LB 라 시드·인증 게이트는 `kubectl port-forward svc/gateway` 주소로 돌렸다. 부하는 loadgen 에서 LB 로 보냈다.
6. 결제 계정 연결은 자동 모드 검사가 막아 사용자가 직접 실행했다. 세션 동안 gcloud·kubectl·helm·crane 허용 규칙을 로컬 설정에
   임시로 두었고 S5 에서 지웠다.
