## P2 음성 대조군 — 완료 (선행 세션 미수행분)

계획서 §4: "GSA 에서 `secretAccessor` 를 뺀 상태로 Pod 기동 → CSI 마운트 실패 → `ContainerCreating`
고착. 권한 부여 후 기동 성공. **Secret Manager 를 실제로 경유한다는 증거**"

### 처음엔 재현되지 않았다 — IAM 전파 지연

권한 제거 **직후** 배포했더니 Pod 이 정상 기동했고 키까지 마운트됐다. gateway GSA 의 프로젝트 레벨
role 은 0건이라 다른 경로도 아니었다. 원인은 IAM 전파 지연이다.

→ **Pod 을 삭제해 새 마운트를 강제**하니 재현됐다:

```
Warning FailedMount  MountVolume.SetUp failed for volume "internal-signing-key":
  code = PermissionDenied desc = Permission 'secretmanager.versions.access' denied on resource
  reason = IAM_PERMISSION_DENIED  permission: secretmanager.versions.access
gateway-69c65f8655-86b2g  0/1  ContainerCreating
gateway-69c65f8655-dnrf5  0/1  ContainerCreating
```

권한 재부여 후 **Pod 재생성 없이** 복구됐다(CSI 가 재시도) — `1/1 Running` ×2.

> **음성 대조군 설계 시 주의**: 권한 변경 직후의 관측은 대조군이 되지 못한다. 전파를 기다리거나
> 새 마운트를 강제해야 한다. 이 함정 때문에 "권한을 뺐는데 떴다 → 검사가 무의미하다" 는 잘못된
> 결론에 도달할 뻔했다.

## P12 순서 역전 재현 — 완료, **계획서·runbook 오류 3건 발견**

③(gateway 전환)을 ②(공개키 선배포)보다 먼저 실행. 신 키 = `rot3`, kid `peekcart-gateway-2026-11`,
공개키는 서비스에 **배포하지 않음**.

### ① 역전 실패는 "전 요청 401" 이 아니라 롤아웃 비율에 비례한다

수렴 전 측정 — 구 Pod 과 신 Pod 혼재:
```
보호경로#1=401  보호경로#2=200  보호경로#3=200
```
전 Pod 수렴 후에야 전면화:
```
login=200 (user 도메인이라 영향 없음)
보호경로 x5: 401 401 401 401 401
공개경로=200
```

계획서 §4 는 "전 요청 401 발생을 관측" 이라 썼지만 실제로는 **부분 장애로 시작해 점진 전면화**한다.
운영 중이라면 이 혼재 구간이 원인 파악을 어렵게 만든다.

### ② 게이트는 "수렴" 은 통과시키고 "서명 probe" 에서만 막는다

```
[ROLLOUT-GATE] 전량 수렴 확인 — 다음 단계 진입 가능        ← 통과 (이미지·replica·RS 정상)
[ROLLOUT-GATE]   gateway-b6dbdc799-89fxg(10.40.1.28): 401
[ROLLOUT-GATE]   gateway-b6dbdc799-sn2ps(10.40.1.29): 401
[ROLLOUT-GATE] FATAL 서명 주입 미수렴 — 평문 주입 0 을 주장할 수 없다
```

**`--gateway-signing-probe` 없이 수렴만 봤다면 이 상태가 green 으로 통과했다.**
또 진단 메시지가 *"구 이미지가 평문을 주입 중일 수 있다"* 라고 하는데 **실제 원인은 kid 불일치**다
— 이미지 digest 는 일치한다. 메시지가 오진을 유도한다.

### ③ `active-kid` 만 되돌리면 복구되지 않는다 — runbook §4.1 이 틀렸다

`active-kid` 를 `2026-10` 으로 되돌리고 롤링했는데 **401 이 유지**됐다:

```
[ROLLOUT-GATE] 전량 수렴 확인 — 다음 단계 진입 가능
보호경로 x3: 401 401 401
```

원인: Secret Manager `versions/latest` 가 여전히 **v3(rot3 개인키)** 를 가리켜, gateway 가 새 키로
서명하면서 구 kid 라벨을 붙였다. **kid 와 개인키는 쌍이므로 둘 다 되돌려야 한다.**

그리고 **버전 비활성화는 롤백 수단이 아니다**:

```
FailedPrecondition desc = Secret Version [.../versions/3] is in DISABLED state.
```

`versions/latest` 는 비활성 버전을 **건너뛰지 않고** 그대로 가리키다 마운트를 통째로 실패시킨다.
올바른 복구는 **구 키를 새 버전(v4)으로 다시 올리는 것**이었고, 그렇게 하니 복구됐다:

```
login=200  보호경로 x5: 200 200 200 200 200
```

> `docs/runbooks/user-jwt-key-rotation.md` §4.1 은 *"`active-kid` 를 구 kid 로 되돌리고 롤링하면
> 바로 복구된다"* 고 서술한다. **이 문서는 수정이 필요하다** — 개인키 버전 되돌림이 빠져 있고,
> 비활성화가 아니라 재업로드여야 한다는 점도 없다. 후속 PR 로 고친다.

부수 관측: 2노드 구간에서 gateway 롤링(`maxUnavailable: 0` · min 2)이 3번째 Pod 을 못 띄워
`0/2 nodes are available: 2 Insufficient cpu` 로 대기했다.

## P13 gateway scrape 실증 — 완료

### 타깃

```
up{namespace="peekcart"}
  user-service / product-service / order-service / payment-service / notification-service  up=1
  gateway-metrics (endpoint=management)  up=1   ×2 Pod
→ up=7
```

ADR-0024 의 세 집합 분리(태그 `gateway` / scrape Service `gateway-metrics` / SM `gateway`)가
실물로 확인된다.

### 메트릭 계열

```
count by (application) (http_server_requests_seconds_bucket{application="gateway"})  → 414 계열
auth_failure_total                                                                   → 22 계열
```

**PR4 의 미충족이 해소된다.** PR4 는 "의존성 추가만으로 S1 이 배선되지 않는다 — `_bucket` 만 없어
p95 alert 만 조용히 NaN" 을 기록했는데, 실제 스크랩 출력에 `_bucket` 이 414계열 존재한다.

### 계측이 실제로 증가하는가 (존재 ≠ 동작)

gateway 인증 실패를 주입하고 카운터를 확인:

```
위조 Bearer(not.a.jwt) → 401     만료형 가짜(HS256 헤더) → 401     bad.token.here ×3 → 401

auth_failure_total > 0
  reason=alg_not_allowed  app=gateway  value=1
  reason=malformed        app=gateway  value=1
  reason=malformed        app=gateway  value=3   (Pod 별 분리)
```

`alg_not_allowed` 가 별도 사유로 잡힌 것이 의미 있다 — ADR-0013 D1 의 alg allow-list 가 런타임에
강제되고, **401 응답은 합쳐 나가되 메트릭에서만 사유가 분해**된다는 S9 설계(ADR-0024)가 실물로
증명된다.

### 음성 대조 — 계획서 예상과 다름

계획서 P13 은 "SM selector 를 `app: gateway` 단독으로 되돌리면 타깃이 8081 아닌 Service 로 잘못
붙거나 사라지는지" 를 기대했다. 실제로는 **타깃 집합이 변하지 않았다**:

```
selector 에서 monitoring-role 제거 → gateway 관련 타깃 2개 (둘 다 gateway-metrics/management)
```

이유: selector 가 느슨해져 public `gateway` Service 까지 매칭되지만, ServiceMonitor 의
`endpoints[].port: management` 가 **2차 필터**로 작동한다. public Service 의 포트 이름은
`http`(8080)라 일치하는 엔드포인트가 없어 타깃이 생성되지 않는다.

```
gateway         -> http       / port 8080
gateway-metrics -> management / port 8081
```

매니페스트 주석의 "`app: gateway` 만 쓰면 8081 이 없는 public Service 까지 매칭한다" 는 selector
층위에서는 맞지만 **타깃 생성까지 가지는 않는다**. lint 가 selector 를 강제하는 건 여전히 타당하나
(방어선이 하나 더 있을 뿐), 위험의 크기는 주석이 시사하는 것보다 작다.

## P14 부하 측정 — 완료 (축소하지 않음)

### 구성 변경 — loadgen 을 VM 이 아니라 클러스터 안으로

선행 세션은 CPU 쿼터(`CPUS-ALL-REGIONS` = 12) 때문에 노드 2대 + VM 2 vCPU = 10 으로 갈 수밖에
없었고, 앱 여유 4994m 로는 HPA 피크(6100m)를 못 받아 P14 를 이월했다. 쿼터 증설은 **두 번 자동
거부**됐고 콘솔에서도 `조정 가능 여부: 아니요` 다.

검토한 대안과 기각 사유:

| 안 | 판정 |
|---|---|
| Spot/preemptible 노드 | `PREEMPTIBLE_CPUS` 한도 **0** |
| 다른 머신 패밀리(N2/C2/T2D) | `CPUS-ALL-REGIONS` 는 패밀리 무관 **전역** 상한 — 우회 불가 |
| 큰 노드 1대(`e2-standard-8`) | 노드가 줄면 singleton 비중이 커져 앱 여유 5514m — 피크 미달 |
| 외부에서 부하 | Internal LB 라 VPC 밖 불가. 외부 노출은 PR3c 보안 계약 파기 |

채택: **loadgen VM 삭제(2 vCPU 확보) → 노드 3대 → k6 를 Pod 으로 실행**.

```
2노드 + VM    10 vCPU  →  앱 여유 4994m   (피크 미달)
3노드 + k6Pod 12 vCPU  →  앱 여유 8464m − k6 500m = 7964m  ✅
```

NetworkPolicy 는 문제되지 않는다 — `backend-ingress-gateway-only` 는 `component: backend` Pod 의
ingress 만 제한하고 gateway 는 `component: gateway` 라 선택되지 않는다.

### 첫 측정은 무효였다 — Rate Limiter

90 VU / 298 req/s 로 밀었더니 **60% 실패**. 전수가 `429` 였다:

```
status=429 uri=UNKNOWN  32327     ← k6 실패 수와 정확히 일치
status=200 uri=UNKNOWN  21631
status=401 uri=UNKNOWN      5
```

결함이 아니라 ADR-0013 D3 fail-closed RateLimiter 가 **설계대로** 동작한 것이다. 한도는
`fail-closed-rate-limiter.burstCapacity: 40` / `windowSeconds: 1` = **키당 40 req/s**.
이 상태의 `http_req_duration` p95 744ms 는 429 가 섞인 값이라 **인증 경로 지연을 대표하지 못한다**.

> **부하 측정 시 rate limit 을 모르면 지연 수치가 통째로 오염된다.** 계획서 P14 에는 이 전제가 없다.

### 재측정 (경로당 15 req/s, 한도 아래)

`constant-arrival-rate` 로 전환. 실패 0%, 3,602건.

**(a) 경로 분리 — 서명 비용 격리**

| 경로 | avg | p50 | p90 | **p95** | max |
|---|---|---|---|---|---|
| 인증 `/api/v1/orders` | 17.43ms | 16.79ms | 22.04ms | **23.61ms** | 44.25ms |
| 공개 `/api/v1/products` | 10.54ms | 10.34ms | 12.78ms | **13.67ms** | 22.46ms |
| **차이** | +6.9ms | +6.5ms | +9.3ms | **+9.9ms** | — |

Prometheus 측 gateway 전체(SUCCESS): **p95 26.9ms · p99 34.6ms**.

PR3d-a 의 마이크로벤치 baseline 은 RSA2048 서명 **p95 1.80ms** 였다. 실측 +9.9ms 가 더 큰 것은
당연하다 — 이 값에는 서명 외에 JWT 파싱·JWKS 조회·blacklist/family deny Redis 조회·헤더 재작성·
다운스트림 홉이 전부 포함된다. **서명 단독 비용이 아니라 인증 경로 전체 오버헤드**로 읽어야 한다.

**(b) event-loop 대리 측정** (관리 포트 8081 `/actuator/health/liveness` probe)

| 상태 | n | min | p50 | p95 | max |
|---|---|---|---|---|---|
| 무부하 | 10 | 3.8 | **4.8** | — | 5.0 |
| 한도 내 부하(30 req/s) | 15 | 4.2 | **5.0** | 6.2 | 7.1 |
| 과부하(298 req/s, 429 다수) | 15 | 7.3 | **9.2** | 12.3 | 31.9 |

한도 내에서는 **영향이 사실상 없다**(4.8 → 5.0ms). 과부인 구간에서만 p50 이 약 2배가 된다.
계획서 §8 U2 대로 이것은 lag 의 **직접 측정이 아니다** — 전용 계측은 별건.

**(c) auth 실패 기저율**

```
총 라우팅 요청                     31,873
auth_failure_total (주입 2건 제외)      0
auth_ratelimit_rejected_total      16,084   (첫 과부하 실행의 429)
```

**정상 트래픽의 인증 실패 기저율은 0 이다.** 따라서 `auth_failure_total` 은 "낮은 비율" 임계가 아니라
**증가 자체를 사건으로 보는** alert 이 적절하다 — ADR-0024 가 reuse alert 에 적용한 논리와 같다.
반면 `auth_ratelimit_rejected` 는 부하에 비례해 대량 발생하므로 비율 기반이어야 한다.
계획서 §8 U4 가 미룬 "임계의 입력값" 이 이것이다. **임계 확정 자체는 여전히 이 PR 범위 밖.**

### HPA 스케일아웃 — 처음 관측

과부하 구간에서:
```
gateway        cpu: 196%/60%   min 2 / max 4 → REPLICAS 4  (max 도달)
order-service  cpu: 109%/60%   min 1 / max 3 → REPLICAS 2~3
```
선행 세션의 2노드 구성에서는 불가능했던 축이다.

## 배포 편차

선행 세션 편차 1~6 중 **재현된 것**: 노드 SA AR pull 403(`artifactregistry.reader`) ·
외부 자격증명 smoke placeholder · drain preflight skip(fresh deploy 사유 기록).
`container.developer`(loadgen VM SA)는 **이번엔 불필요**했다 — VM 을 쓰지 않았다.

이번 세션 고유:

1. **부하 발생기 co-location** — ADR-0004 는 "같은 zone 의 **별도** Compute Engine VM"을 규정하나,
   CPU 쿼터 상한 때문에 클러스터 내 k6 Job 으로 실행했다. ADR-0004 가 별도 VM 을 고른 근거는
   "집 인터넷 경유 기각"(Alternative B)이라 VPC 내 co-location 과는 다른 축이지만, **부하 발생기가
   앱과 CPU 를 경쟁**하는 것은 사실이다. 여유가 피크 대비 1864m 있어 실행은 됐으나 측정된 p95/p99 에
   경합이 일부 섞인다. 경로도 다르다 — VM 은 `→ Internal LB → gateway`, Pod 은 같은 LB IP
   (`10.178.0.18`)를 타깃해 최대한 맞췄으나 동일하지 않다.
2. **Phase 3 시나리오 미사용** — 계획서 P14 는 `loadtest/scripts/order-concurrency.js` 를 지정하나,
   그것은 **오버셀링 정합성** 시나리오(1000 VU · `seed.sql` · `users.csv` 의존)로 P14 의 목적
   (지연 분리·auth 기저율)과 축이 다르다. 목적 전용 스크립트를 작성해 공개/인증 경로를 태그로
   분리했다. **오버셀링 정합성은 이 세션에서 검증하지 않았다.**
3. **노드 3대 · `pd-standard` 부팅 디스크** — README §전제(`e2-standard-4 × 1`)와 다르다.
   pd-standard 는 선행 세션에서 SSD 지역 쿼터에 막힌 경험을 반영해 **처음부터** 지정했다.
4. **Secret Manager 버전이 4개로 늘었다** — gateway 키: v1(초기) · v2(rot2) · v3(rot3, **disabled**) ·
   v4(rot2 재업로드). P12 의 롤백 과정에서 생긴 것으로, 운영이라면 정리 대상이다.

## 수정이 필요한 것 (후속 PR)

1. **`docs/runbooks/user-jwt-key-rotation.md` §4.1** — "`active-kid` 되돌림만으로 복구" 서술이 틀렸다.
   개인키 버전도 함께 되돌려야 하고, **비활성화가 아니라 재업로드**여야 한다(§P12 ③).
   내부 토큰 runbook(`task-impl3-pr3d-internal-token.md` §11)에도 rollback 절이 없어 같은 함정이 있다.
2. **`rollout-convergence-gate.sh` 의 서명 probe 진단 메시지** — "구 이미지가 평문을 주입 중일 수
   있다" 는 오진을 유도한다. kid 불일치·키 부재도 같은 401 을 낸다(§P12 ②).
3. **계획서 P13 음성 대조 기대값** — selector 완화만으로는 타깃 집합이 변하지 않는다(§P13).
4. **계획서 P14 에 rate limit 전제 누락** — 한도 위에서 측정하면 수치가 통째로 오염된다(§P14).

## 미충족

- **오버셀링 정합성 미검증** — Phase 3 시나리오를 돌리지 않았다(위 편차 2).
- **event-loop lag 직접 계측 없음** — (b)는 관리 포트 probe 대리 지표다(계획서 §8 U2).
- **auth failure alert 임계 미확정** — 입력값만 산출했다(계획서 §8 U4).
- **측정에 co-location 경합이 섞여 있다** — 별도 VM 측정과 직접 비교 불가.
- **리뷰 미수행** — Codex 리뷰 미호출(사용자 지시). "P0/P1 = 0" 주장 없음.
