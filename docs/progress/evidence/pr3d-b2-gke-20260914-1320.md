## 관찰 — lint 계약의 사각 (수정하지 않음)

`gateway-exposure-lint.sh` 의 `GWX-CSI-005` 는 승인 `resourceName` 을
`projects/PROJECT_ID_PLACEHOLDER/...` 로 **placeholder 문자열 자체**를 박아 대조한다. 따라서
PROJECT_ID 를 치환한 트리(= 실제로 배포 가능한 상태)에서는 이 검사가 **구조적으로 항상 red** 다.

커밋 상태를 지키는 lint 이므로 CI 에서는 의도대로 동작한다. 다만 "배포 직전 상태를 lint 로 검증할
수 없다"는 뜻이기도 하다 — operator 가 치환한 뒤에는 계약 검사 없이 apply 하게 된다.
본 세션에서는 고치지 않았다(범위 밖). `workload-key-ownership-lint` 는 치환 후에도 green 이라
신원 경계 검사는 배포 직전 상태에서도 유효하다.

### 무엇이 빠져 있었나

```

### 내부 토큰 — 운영 kid 로 교체 (seam 있음)

               /etc/peekcart/internal-token-keys/peekcart-gateway-2026-09.pem

```

### user 키 도메인 — override seam 이 없다 (결함)

계획서 P3 는 "user 공개키는 `app.jwt.rs256.public-keys` 로" 라고 썼으나, **그 seam 이 매니페스트에
존재하지 않는다**:

- `app.jwt.rs256.public-keys[0].location` 은 `classpath:keys/dev-jwt-public.pem` 로 이미지에 고정
- `k8s/base/services/user-service/deployment.yml` 의 마운트는 2종뿐 —
  `/etc/peekcart/user-keys`(개인키 CSI) · `/etc/peekcart/internal-token-keys`(내부토큰 **공개키**)
- 내부 토큰 도메인에는 ConfigMap + 인덱스 env seam 이 있는데 **user 도메인에는 대칭이 없다**

`internal-token-keys` ConfigMap 에 끼워 넣는 우회는 불가하다 — `internal-key-ownership-lint` 가
SPKI fingerprint 로 두 도메인의 서로소를 강제하며, JWKS 로 게시되는 키가 내부 토큰 키 집합에
들어가는 것이 바로 그 lint 가 막는 위반이다(ADR-0017 D3).

**이번 세션 조치(A안)**: dev 키쌍을 user secret 의 **버전 2** 로 올려 JWKS 와 일치시켰다.
CSI/Secret Manager 전달 증명은 키 바이트와 무관하므로 그대로 유효하다.

**미충족**: user 키 도메인은 "운영 전용 키" 축을 이 세션에서 증명하지 못했다. Secret Manager 에
공개 절반이 레포에 커밋된 키가 들어가 있다. **공개키 override seam 신설은 구조적 매니페스트 변경**
(ConfigMap + volume/mountPath + lint 갱신)이라 별건 PR 로 분리한다.

### 복구 확인 — end-to-end (양성 대조군)

재기동 후 마운트된 개인키와 JWKS 게시 공개키가 일치:

```
마운트 개인키 모듈러스   m_giFVAWs6E18uYDDkCYx-zqPs1XirQa_ugvFfZn
JWKS "n"                m_giFVAWs6E18uYDDkCYx-zqPs1XirQa_ugvFfZn
```

loadgen VM 에서 gateway 경유 전 구간:

```
signup  /api/v1/auth/signup  -> 201
login   /api/v1/auth/login   -> 200  (accessToken len=546)
보호    /api/v1/orders        -> 200  ← 양성 대조군
```

서비스는 커밋 기본값인 **`SIGNED_ONLY`** 로 떠 있다(`internal-token-keys.yml` 주석 · ADR-0007).
그 상태에서 보호 경로 200 이 나왔다는 것은 **서명 내부 토큰 경로가 전 구간 동작**한다는 뜻이다 —
gateway 가 Secret Manager 개인키로 서명하고, 5서비스가 ConfigMap 으로 받은 운영 공개키로 검증한다.

## P5~P8. §7 롤아웃 리허설 ②~⑤ — 완료

### 출발점을 인위적으로 만들었다 (정직성)

fresh deploy 는 커밋 기본값대로 **곧장 ④(SIGNED_ONLY)에 착지**했다. 서명 경로가 이미 동작하는
상태였으므로(위 P3 보정 §end-to-end), ②~④ 를 "전진"으로 실행할 수 없었다. 그래서 ② 로 **되감아**
출발점을 구성했다 — 이는 실제 운영 전환의 역방향이며, 리허설을 위해 인위적으로 만든 상태다.

되감기 순서를 지켰다: **5서비스를 DUAL_ACCEPT 로 먼저** 올린 뒤 gateway 를 PR3c 이미지로 내렸다.
반대로 했다면 SIGNED_ONLY 서비스가 평문을 거부해 전 요청이 401 이 된다.

### P5. ② 서비스 dual-accept + 평문 gateway

`internal-token-binding` ConfigMap 에 `APP_INTERNALTOKEN_MODE: DUAL_ACCEPT` 한시적 override
(커밋 기본은 SIGNED_ONLY — ADR-0007). 수렴 게이트는 **서비스별로 자기 digest** 를 걸어 5회 실행:

```
[ROLLOUT-GATE]   notification-service: 전 Pod image digest 일치 (1 Pod)  → 전량 수렴
[ROLLOUT-GATE]   user-service:         전 Pod image digest 일치 (1 Pod)  → 전량 수렴
[ROLLOUT-GATE]   product-service:      전 Pod image digest 일치 (1 Pod)  → 전량 수렴
[ROLLOUT-GATE]   order-service:        전 Pod image digest 일치 (1 Pod)  → 전량 수렴
[ROLLOUT-GATE]   payment-service:      전 Pod image digest 일치 (1 Pod)  → 전량 수렴
```

> **계획서 P5 표기 부정확**: `--workloads user-service,...,notification-service --expect-image <digest>`
> 로 적혀 있으나 `--expect-image` 는 **하나를 전체에 적용**한다. 5서비스는 digest 가 각각 달라
> 서비스별 실행이 맞다. (`--allow-any-image` 로 뭉개면 digest 검증 자체가 사라진다.)

gateway 를 **PR3c 시점 이미지**(`gateway:pr3c-5ec2d56`,
digest `sha256:15e34a17c9301f5532c20bf395933b9ffc1d42a2cce1e0ec4877816f90b788e7`)로 교체 후
loadgen VM 에서:

```
login                  -> 200
평문 주입 경로 /api/v1/orders  -> 200   ← ② 재현 성공
공개 경로 /api/v1/products     -> 200
```

**W7 실측 해소** — "평문 경로는 미검증으로 남길 수 있다"던 축이 실제로 측정됐다.

### P6. ③ Gateway 서명 주입 배포

gateway 를 현재 digest(`sha256:f3511b96…`)로 교체 → 수렴 게이트:

```
gateway: 수렴 (replicas 2/2) · 활성 ReplicaSet 1개 — 구 RS drain 완료 · 전 Pod image digest 일치 (2 Pod)
```

> **계획서 P6 과 스크립트가 충돌 — 스크립트가 옳다.** P6 은 `--gateway-signing-probe` 를 ③ 에
> 걸라고 썼으나, `rollout-convergence-gate.sh` 의 `assert_downstream_signed_only` 가 이를 거부한다:
> *"이 상태에서는 200 이 '서명 주입' 을 증명하지 못한다(평문도 수용되므로). §7 ③ 의 '평문 주입 0'
> 은 ④(signed-only 전환) 이후에 이 probe 로 확정한다."* — ③ 에서는 서비스가 DUAL_ACCEPT 라
> 평문 주입 gateway 도 200 을 받는다. 계획서 문구를 따랐다면 vacuous-green 이었다.
> 따라서 ③ 에서는 수렴만 판정하고 서명 probe 는 ④ 이후로 미뤘다.

### P7. ④ signed-only 전환

한시적 override 제거 → `APP_INTERNALTOKEN_MODE` unset → base 기본값 SIGNED_ONLY 복귀 확인.
그 상태에서 Pod 별 서명 probe(loadgen VM 에서 **Pod IP 직접** — Service 경유는 어느 Pod 가 받았는지
보증하지 못한다):

```
[ROLLOUT-GATE] 다운스트림 5서비스 SIGNED_ONLY 확인 — 200 을 서명 주입 증거로 쓸 수 있다
[ROLLOUT-GATE]   gateway-668759b984-fskk8(10.56.2.26): 200 — 유효한 X-Internal-Auth 주입 확인(평문 주입 아님)
[ROLLOUT-GATE]   gateway-668759b984-mxhtr(10.56.0.43): 200 — 유효한 X-Internal-Auth 주입 확인(평문 주입 아님)
[ROLLOUT-GATE] 전 Pod 서명 주입 확인 (평문 주입 0)
```

첫 실행은 롤아웃 중이라 Pod 1개만 존재했다 — "전 Pod" 주장을 실제 2 Pod 상태에서 재실행해 확정했다.

### P8. ⑤ signed-only crypto barrier

```
[GKE-SMOKE] (②-1) 위조 X-Internal-Auth 401 OK
[GKE-SMOKE] (②-2) 평문 X-User-* 무시→401 OK
[GKE-SMOKE] (②-3) 정상 로그인 토큰 200 OK (양성 대조군 — gateway 서명 주입 경로 동작)
[GKE-SMOKE] (②-4) 직접경로 Bearer(유효 사용자 토큰) 401 OK — 서비스 측 사용자 verifier 부재 확인
[GKE-SMOKE] crypto barrier PASS
EXIT=0
```

(②-3) 양성 대조군이 있으므로 (②-1)/(②-2) 의 401 은 "전부 거부"가 PASS 로 위장된 것이 아니다.
(②-4) 는 **유효한** 사용자 토큰을 직접경로로 보냈는데 401 이라는 것이므로, 서비스가 사용자 토큰을
인증 근거로 쓰지 않음을 뜻한다 — **ADR-0014 D2-c exit** 에 해당한다.

## 결함 — `apply -k` 가 HPA 최소값을 깎는다 (리허설이 찾아낸 것)

`k8s/base/services/gateway/deployment.yml:20` 이 `replicas: 1` 로 고정돼 있고, gke overlay 패치
(`patches/gateway-deployment.yml:2`)는 *"replicas 는 HPA(minReplicas 2)가 관리한다 — 여기서
고정하지 않는다"* 는 **주석만** 달고 replicas 를 제거하지 않았다.

결과: `kubectl apply -k k8s/overlays/gke` 를 칠 때마다 gateway `spec.replicas` 가 **1 로 덮인다**.
HPA minReplicas 는 2이므로 HPA 가 곧 2로 되돌리지만, 그 사이 구간에는 **HPA 최소값 미만**으로 내려가
있다. 실제로 본 세션의 매 apply 마다 재현됐고, P7 서명 probe 첫 실행이 1 Pod 만 본 원인이기도 하다.

관측:

```
kubectl get deploy gateway -o jsonpath='{.spec.replicas}'  → 1
kubectl get hpa gateway                                     → MINPODS 2 / REPLICAS 2
노드 CPU 여유                                                → 84% / 74% (용량 부족 아님)
```

배포 때마다 gateway 가용 Pod 가 일시적으로 최소값 아래로 떨어지므로 **가용성 계약 위반**이다.
수정(overlay 패치에서 `replicas` 를 실제로 제거하거나 base 에서 빼는 것)은 커밋 매니페스트 변경이라
본 세션 범위 밖 — 별건으로 올린다.

## P9. ⑥ 후속 정리 확인 — 완료

PR3d-a 가 코드로 지운 것(서비스 측 사용자 토큰 verifier)을 **실행 중인 Pod 에서 관측**한다.

> **계획서 P7 표기 부정확**: "모드/필터 집합이 readiness 로 노출됨" 이라고 썼으나, actuator 노출은
> `health` 뿐이고 details 도 `never` 다(ADR 최소 노출). 실제 기전은 노출이 아니라
> **부팅 거부**다 — `InternalTokenModeInvariant` 는 `SmartInitializingSingleton` 으로
> 위반 시 `IllegalStateException` 을 던져 컨텍스트 기동을 막는다.
> 따라서 **"Pod 가 Ready 다" 자체가 관측 증거**이며, 그 근거 로그는 다음과 같다:

```
order-service          내부 토큰 인증 구성 확인: mode=SIGNED_ONLY chains=1
user-service           내부 토큰 인증 구성 확인: mode=SIGNED_ONLY chains=1
product-service        내부 토큰 인증 구성 확인: mode=SIGNED_ONLY chains=1
payment-service        내부 토큰 인증 구성 확인: mode=SIGNED_ONLY chains=1
notification-service   내부 토큰 인증 구성 확인: mode=SIGNED_ONLY chains=1
```

이 로그가 찍혔다는 것은 불변식이 통과했다는 뜻이고, 불변식은 (a) `JwtFilter`(사용자 토큰 검증
필터)가 체인에 없음 (b) 내부 토큰 필터가 정확히 1개 (c) 체인 0개 아님 (d) SIGNED_ONLY 면
`familyIdRequired=true` 를 강제한다. → **verifier bean 0** 이 5서비스 전부에서 성립.

## P10. rollback 행렬 ④ 출발 행 — 완료

부모 §12 표의 "④ → ② 되돌림은 env 하나, 이미지 교체 없음" 주장을 실측으로 고정했다.

### 계획서 P10 의 검증식은 이 아키텍처에서 관측되지 않는다

계획서 §4 는 *"`SIGNED_ONLY` 상태에서 평문 요청 → mode 되돌림 → 재요청 | **401 → 200**"* 을
기대하지만, **gateway 를 통해서는 나올 수 없다** — 현재 gateway 는 외부 `X-User-*` 를 항상 strip
하므로(PR3d-a), 모드가 무엇이든 외부발 평문은 신원을 세우지 못해 401 이다. 실측:

```
④ SIGNED_ONLY  · gateway 경유 평문 주입 -> 401
② DUAL_ACCEPT  · gateway 경유 평문 주입 -> 401   ← 되돌렸는데 그대로 401 (vacuous)
```

즉 계획서대로 측정했다면 "되돌림이 동작하지 않는다"는 **잘못된 결론**에 도달했을 것이다.
DUAL_ACCEPT 의 효과는 *서비스가 평문을 수용하는가* 이므로, 관측 지점은 gateway 바깥이 아니라
**NetworkPolicy 가 허용하는 유일한 출발점 = gateway Pod 내부**여야 한다.

### 재설계한 관측 지점에서의 결과

gateway Pod 에서 `order-service:8080` 으로 평문 헤더 직접 주입:

| 상태 | gateway Pod → order-service 평문 | order-service image digest |
|---|---|---|
| ④ SIGNED_ONLY | `401` | `sha256:878d6976…` |
| ② DUAL_ACCEPT (`set env` 하나) | **`200`** | `sha256:878d6976…` |
| ④ 복귀 (`set env ...-` 로 제거) | `401` | `sha256:878d6976…` |

digest 가 3회 측정 내내 동일 — **이미지 교체 0회**로 되돌림과 복귀가 모두 성립한다.
"1순위 되돌림이 env 하나"라는 설계 주장이 실측으로 고정됐다.

### 계획서 정정 3건

1. **P5** — `--expect-image` 는 하나를 전체 workload 에 적용한다. 5서비스는 digest 가 각각 달라
   서비스별 실행이 맞다.
2. **P6** — 서명 probe 를 ③ 에 걸라는 지시는 틀렸다. ③ 은 DUAL_ACCEPT 라 평문 주입 gateway 도
   200 을 받아 vacuous-green 이 된다. 스크립트의 `assert_downstream_signed_only` 가 이를 막는다.
3. **P10** — 기대식 `401 → 200` 은 관측 불가. gateway 가 외부 `X-User-*` 를 strip 하므로 모드와
   무관하게 401 이다. 관측 지점을 gateway Pod 내부로 옮겨야 한다.
