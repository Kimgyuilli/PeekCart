# D-002b'/c GKE 측정 세션 — 증적 (2026-09-17)

> 계획서: `docs/plans/task-d002-bc-session.md` · 하네스 PR [#119]
> 선행: D-002a 세션 [#117] / `evidence/d002a-gke-20260916-0030.md`

## 요약 — 무엇이 밝혀졌나

D-002a 는 "2차 병목은 CPU 도 Hikari 풀도 아니다 — **MySQL 내부**가 남았다" 로 끝났다.
그 "MySQL 내부" 를 열어보니 **세 겹**이었고, 셋 다 서로 다른 축이다.

| # | 천장 | 정체 | 증거 |
|---|---|---|---|
| ① | **동기 주문 생성** | MySQL **자기 CPU 한도(500m)** | 한도 500m→2000m 로 **×2.94** (54→158.6 건/초) |
| ② | **비동기 예약 사가** | **outbox 폴링 설정**(100건/5s = 상한 20/s) | 설정 완화로 **×4.8** (16.3→77.3 건/초) |
| ③ | **발행의 가용성** | **스케줄러 스레드 1개** — 형제 잡이 발행을 굶김 | 형제 잡 185초 실행 동안 발행 **완전 정지** |

①은 D-002a 가 놓친 축이다. **D-002a 가 배제한 "CPU" 는 product-service 의 CPU 였고**,
`gke-d002a/kustomization.yml` 의 `patches` 가 1건(product-service)뿐이라 **MySQL 은 그 세션 내내
base 값 `limits.cpu: 500m` 으로 돌았다**. 그 축은 한 번도 변경되지 않았다.

## 측정 전 관문 (계획서 §4 P2)

`d002bc-ratelimit-probe.js` — 단일 사용자로 한도 초과 부하:
**5,152 요청 중 429 4,532건 → PASS**. 이후 측정의 "429 = 0" 이 비로소 "한도 아래에서 쟀다" 의
증거가 된다. (세션 2 는 반대 방향으로 당했다 — 298 req/s 를 밀고 60% 실패가 전부 429였다.)

## ① 동기 경로 — MySQL CPU 한도가 천장 (P4/P5/P6)

동일 부하(200 사용자 고정, 목표 300 rps, 2분), MySQL `limits.cpu` 만 변경:

| MySQL limit | 주문 생성 | http_reqs | p95 | 실패율 | 측정 중 MySQL CPU |
|---|---|---|---|---|---|
| **500m** (D-002a 와 동일) | 54.0 건/초 | 109/s | 2.38s | 0% | **498m / 500m (한도 도달)** |
| **2000m** | **158.6 건/초** | 318/s | **879ms** | 0% | 1,259m / 2000m (여유) |

**×2.94.** 지연도 2.38s→879ms 로 줄었다. 2000m 조건에서 병목은 order-service(1,784m/2000m)와
gateway(1,097m+1,228m)로 **이동**했다.

- 429 = 0 · `ORD-007`(가격 캐시 미스) = 0 — 두 관문 모두 통과
- 주문 201 성공률 100% (9,599/9,599)

### 이 run 의 편차 (정직성)

목표 300 rps 를 **달성하지 못했다** — 500m 조건 `dropped_iterations 26,401`.
VU 200개가 각각 ~2.5초 반복을 도니 구조적 상한이 ~80 iter/s 이고 실측은 54였다.
즉 이 run 은 "300 rps 를 넣은 결과" 가 아니라 **"200 동시 사용자로 포화시킨 결과"** 다.
(2000m 조건은 dropped 8,226 으로 크게 줄어 158.6 달성.)

## ② 사가 경로 — 자원이 아니라 설정이 천장

```java
// order-service/src/main/java/com/peekcart/global/outbox/OutboxPollingScheduler.java:19
@Scheduled(fixedDelayString = "${app.outbox.polling.delay:5s}")   // k8s 프로파일 미오버라이드
batch-size: 100                                                    // → 이론 상한 20 건/초
```

| 조건 | 사가 완결율 | 비고 |
|---|---|---|
| MySQL 500m · 폴링 기본 | 14.3 건/초 | |
| MySQL 2000m · 폴링 기본 | 16.3 건/초 | **CPU 4배인데 +14%** |
| MySQL 2000m · 폴링 완화(500건/0.5s) | **77.3 건/초** | **×4.8** |

배수 구간 CPU: mysql 333m · product 212m — **둘 다 한도에서 멀다**. 사가는 처음부터
자원 병목이 아니었다.

**병목 위치 확정 증거**: Kafka consumer **LAG = 0** (3 파티션 전부), 그리고
`stock_reservations` 건수가 outbox `PUBLISHED` 건수와 **정확히 일치**(3,300 = 3,300).
소비자는 발행되는 족족 처리한다 — 굶고 있는 쪽이다.

완화 후에도 이론 상한(1,000/s)에 한참 못 미치는 **77/s 라는 새 천장**이 나타났고, 이때
mysql 828m·order 348m·product 402m 로 **아무도 한도에 닿지 않는다**. 이벤트당 ~13ms 는
순차 동기 Kafka 발행(블로킹 `.get()`, `publish-timeout 6s`)과 정합적이다. **한 겹 더 있다.**

## ③ 스케줄러 스레드 1개 — 발행이 완전히 멈춘다

측정 도중 발행율이 **0** 이 되어 추적한 결과:

```
스케줄러 스레드: "scheduling-1" 단독 (최근 로그 200줄 전부 · Spring 기본 pool-size=1, 오버라이드 없음)

shedlock:
  orderOutboxPollingJob       locked_at 12:16:57.454  →  이후 실행 기록 없음
  orderReservationTimeoutJob  locked_at 12:17:09.332  lock_until 12:20:14.129   (185초 실행)
  orderOutboxPollingJob       locked_at 12:20:27.861  ← 형제 잡 해제 13초 후 재개

PUBLISHED: 그 구간 내내 5,500 고정 → 재개 즉시 6,717
```

**형제 스케줄 잡이 길어지면 outbox 발행이 완전히 멈춘다.** 상관이 아니라 인과다 —
멈춘 시각과 재개 시각이 형제 잡의 점유/해제와 13초 이내로 붙는다.

양성 피드백이 성립한다: 백로그가 쌓이면 타임아웃·예약 잡이 길어지고 → 발행이 멈추고 →
백로그가 더 쌓인다. **부하 상황에서만 발현**하므로 평소에는 보이지 않는다.

②의 실측(14.3~16.3 < 이론 20)이 상한에 못 미친 것도 부분적으로 이것 때문으로 보인다.

## 정합성 — 유실 0

첫 run(주문 9,599건) 완전 배수 후:


RELEASED 207 은 미결제 타임아웃 취소분이다. **유실·DLQ 0.** 배수 총 552초 —

## D-002c — 경합은 replicas=1 에서 **구조적으로 불가능**, replicas=3 에서 나타났고 V5 가 확인됐다

### 왜 replicas=1 에서는 0 인가 — 발행 상한보다 근본적인 이유

```
KafkaListenerEndpointContainer#N-0-C-1     ← "-0-" = 컨테이너당 consumer 1개(concurrency 기본 1)
product-service replicas: 1 · concurrency 설정 없음
```

예약 소비는 **시스템 전체에 스레드 1개**다. 분산 락에 **경쟁자가 존재할 수 없다** —
`tryLock` 은 항상 즉시 성공하고, 3초 대기는 소진되지 않으며, `PRD-004` 는 발생 불가능하다.
`@Version` 낙관락도 쓰는 쪽이 하나뿐이라 충돌하지 않는다. **부하와 무관하다.**

실측(replicas=1, 경합군 = 전 주문을 상품 1개로, 주문 2,977건):
`OptimisticLock 0 · PRD-004 0 · DLQ 0`.

### replicas=3 — 경합이 나타나고, 락이 막지 못한다 (P9)

깨끗한 상태에서 1분 경합군(주문 **9,782**, 예약 9,776 완전 배수):

| 지표 | 값 |
|---|---|
| `PRD-004` (락 대기 3s 초과) | **0** — 락은 항상 즉시 획득된다 |
| `OptimisticLockingFailureException` | **7** |
| DLQ 유입 | **7** — 충돌 수와 정확히 일치 |

**이 조합이 V5 의 런타임 확인이다.** 락이 커밋을 직렬화한다면 낙관락 충돌은 **불가능**해야 한다 —
한 번에 한 쓰기만 커밋까지 통과할 것이기 때문이다. 락이 멀쩡히 획득되는데(대기 실패 0) 충돌이
발생한다는 것은 **락 해제가 커밋보다 먼저 일어난다**는 코드 사실이 그대로 나타난 것이다
(`InventoryService.decreaseStock` 이 REQUIRED 로 consumer 트랜잭션에 참여 →
`InventoryLockFacade` 의 `finally { unlock }` 이 커밋보다 앞선다).

**대가는 DLQ 다.** 충돌 7건이 재시도 소진 후 DLQ 7건이 됐다 — 수동 replay 가 필요한 운영 부담이다.

### 그러나 정합성은 지켜졌다 (P10)

```
negative_stock_rows            0
품목별 diff <> 0                해당 행 없음
상태: RESERVED 9,042 + RELEASED 733 + CANCEL_REQUESTED 1 = 9,776
```

`Inventory @Version` 이 홀로 정합성을 지킨다. **분산 락은 지금 아무 일도 하지 않는다** —
replicas=1 에서는 경쟁자가 없어서, replicas=3 에서는 커밋을 감싸지 못해서.

그리고 이것이 V5 를 날카롭게 만든다: **락은 필요해지는 바로 그 시점(레플리카↑)에 틀린 상태가 된다.**

### 대조군은 오염됐다 (미충족)

`spread` 대조군은 직전 contend run 의 잔여가 배수 중일 때 초기화해 두 run 이 섞였다
(`RESERVED 8,250` 이 해당 run 주문 6,634건을 초과). **contend vs spread 비교는 무효**이며,
위 결론은 **replicas=1(0건) ↔ replicas=3(7건)** 대조에 근거한다.

## 배포 편차 (증적 정직성)

1. **키쌍 불일치 2건** — `user-jwt-public-keys` · `internal-token-keys` ConfigMap 의 공개키가
   Secret Manager 개인키와 **다른 쌍**이었다. 배포는 전부 성공하고 파드는 Ready 이며 로그인도
   200 인데 **인증된 요청이 전부 401**이었다. 커밋 매니페스트는 의도된 dev 템플릿이므로
   (주석: "운영 키는 operator 가 Secret Manager 개인키와 쌍으로 교체한다") 커밋을 바꾸지 않고
   **클러스터 ConfigMap 만 교체**했다 — `PROJECT_ID_PLACEHOLDER` 치환과 같은 층위.
   → **D-022 승격 후보**(키쌍 preflight 부재).
2. **Toss 자격증명 placeholder** — `TOSS_SECRET_KEY`/`TOSS_WEBHOOK_SECRET` 에
   `docker-health-smoke.sh` 의 smoke 값 주입(실제 자격증명 아님). PR3d-b-2 편차 4와 동일.
   **외부 연동 미검증.**
3. **outbox 폴링 완화** — D-002c 경합 구간 진입과 백로그 배수를 위해
   `delay 5s→500ms · batch 100→500` 을 env 로 오버라이드했다. **시스템 설정을 바꾼 측정**이며,
   ②의 표에서 조건을 명시했다.
4. **MySQL 파드 교체를 `scale 0→1` 로 수행** — `mysql.yml` 에 `strategy:` 선언이 없어
   기본 RollingUpdate 이고, RWO PVC + 같은 노드에서 신·구 파드가 같은 datadir 을 잡아
   mysqld 기동이 실패했다(재현됨). → **D-023 승격 후보**. redis/kafka 도 동일 구조.
5. **하네스 결함 1건 수정** — `d002bc-seed-products.sh` 가 `categoryId: 1` 존재를 전제하면서
   만드는 단계가 없어 상품 생성이 전부 `PRD-003` 404 였다. `[0/4]` 단계 추가.
6. **Codex 리뷰 미호출**(사용자 지시) — **"P0/P1 = 0" 주장 없음.**
