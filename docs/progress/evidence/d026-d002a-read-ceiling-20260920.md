## 결론 두 줄

1. **D-026 은 detail 을 "빠르게" 만든 게 아니라 "캐시 적중 천장에 도달시켰다."**
   같은 MySQL 조건(500m)에서 detail ON / list ON 비가 **0.60 → 1.01**. 재고 DB 왕복 1회가
   detail 을 list 천장의 60% 에 묶어두고 있었고, 그것이 사라졌다.
2. **D-002a 가 "MySQL 내부"로 남겨둔 공통 천장은 MySQL 자신의 CPU 한도였다.**
   500m → 2000m 에서 캐시 OFF detail 이 **393 → 904 rps**, MySQL 스로틀이
   **147.6초 → 0.1초**(60초 런 기준)로 소멸. 되돌림(A′)에서 **392.6 rps(+0.2%)** 로 복귀해
   재시작·드리프트 효과가 아님을 확인했다.

## 읽는 법

### ① 세션 간 절대값 비교는 오염돼 있다 — 세션 내부 비율을 쓴다

대조군 게이트가 실패한 이유는 **캐시 OFF 는 기준선과 겹치는데(±4%) 캐시 ON 만 +16.7%** 올랐기
때문이다. 두 경로의 병목이 다르다 — OFF 는 MySQL 500m 에 묶인 **DB 바운드**라 환경이 좋아져도
안 움직이고, ON 은 **앱/CPU 바운드**라 새 노드·새 GKE·새 k6 의 이득을 받는다. **바닥은 고정,
천장만 이동**이다.

따라서 `×1.23 → ×2.30` 같은 세션 간 비교를 D-026 의 성과로 쓰지 않는다. 계획서 §3-3 이 미리
정한 대로 **같은 세션 안의 paired ratio** 로 판정한다:

| | detail ON ÷ list ON | MySQL |
|---|---|---|
| 기준선 (2026-09-16) | **0.604** | 500m |
| **블록 A (이번)** | **1.013** | 500m |
| 블록 B (이번) | 0.807 | 2000m |

기준선과 **같은 MySQL 조건(500m)** 인 블록 A 가 정당한 비교 대상이고, **0.60 → 1.01** 이
D-026 의 순효과다. 두 엔드포인트를 같은 스택에서 나란히 잰 비율이라 환경 이동에 면역이다.

### ② 블록 B 가 드러낸 것 — detail 은 여전히 list 보다 조금 비싸다

MySQL 천장을 풀자 두 엔드포인트가 다시 갈라졌다(**0.807**). 블록 A 에서 1.01 로 보였던 것은
"동률"이 아니라 **둘 다 같은 천장(≈900 rps)에 눌려 있어서** 생긴 착시다. 천장을 걷어내면
detail 은 list 의 **약 81%** 다.

이 20% 차이는 결함이 아니라 **ADR-0026 이 택한 설계의 잔여 비용**으로 보인다 — detail 은
Redis 를 **두 번**(`product` + `productStock`) 타고 list 는 **한 번**(`products`) 탄다.
다만 이 세션은 그 인과를 분리하지 않았다(§미해결 2).

### ③ MySQL CPU 상한이 공통 천장이었다 — detail 은 확정, list 는 미확정

- **detail**: A 393.4 → B 903.8 → A′ **392.6**. 되돌림 오차 **+0.2%** 로 사실상 완전 복귀.
  **CPU 효과 ×2.30 을 확정한다.**
- **list**: A 367.6 → B 1406.4 → A′ 409.9. 되돌림 오차 **+11.5%** 로 게이트(±10%) **실패**.
  효과 크기(×3.83)가 오차보다 훨씬 크므로 **방향은 확실**하나, **배속 숫자를 확정값으로
  적지 않는다.** 재측정이 필요하다.

list OFF 블록 B 의 산포 44.5% 도 같은 자리를 가리킨다. 개별값은 **782.7 / 1406.4 / 1408.4** 로,
**첫 런만 낮다** — CPU 전환 직후 `Recreate` 로 식은 버퍼풀이 아직 덜 데워진 상태다.
블록 워밍업(전 상품 풀스캔 3회)이 list 경로에는 충분하지 않았다.

### ④ D-026 의 기전이 숫자로 확인됐다

블록 B `detail ON`: **`productStock` 캐시 miss 10.0/s · 적중률 99.4%**.
상품 100개 · TTL 5s 이면 이론 갱신률은 `100/5 = 20/s` 인데 실측이 그 **절반**이다.
계획서 §V10 이 우려한 **400 VU TTL stampede 는 관측되지 않았다** — 오히려 반대 방향이다.
(`@Cacheable` 에 `sync=true` 가 없어 원리적으로 가능하긴 하나 이 부하에서는 발현하지 않았다.)

## 미해결

1. **list 경로의 CPU 효과 배속이 확정되지 않았다** — 되돌림 게이트 실패(+11.5%).
   재측정 시 **블록 워밍업을 list 경로까지 포함**해야 한다(전 상품 풀스캔만으로는 부족).
2. **캐시 ON 경로도 MySQL CPU 에 반응했다** — list ON 이 894.9 → 2249.2 인데 이 셀의
   캐시 miss 는 **0** 이다. DB 를 안 건드리는 경로가 DB CPU 한도에 반응한 이유를 이 세션은
   분리하지 못했다. 후보: 노드 레벨 CPU 경합(MySQL·product-service 가 같은 2노드를 공유) ·
   cgroup `cpu.stat` 판독 범위. **추측으로 메우지 않는다.**
3. **`product`(단수) 캐시가 측정에서 누락됐다** — 캐시는 셋인데(`product`·`productStock`·
   `products`) 하네스가 뒤의 둘만 분해했다. 핵심인 `productStock` 은 잡혔으나, detail 경로의
   상품정보 캐시 거동은 이번 증적에 없다.
4. **2차 병목의 다음 축** — MySQL CPU 를 풀자 천장이 올라갔으므로 D-002a 의 질문은 닫혔다.
   그러나 2000m 에서도 새 천장이 있다(detail OFF 904). 그 정체는 미분리.
