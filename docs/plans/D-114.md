# D-114 — 측정 환경의 볼륨 크기와 영속성

## 1. 명제
아래 중 하나라도 성립하면 미완이다.
- 측정 overlay(`gke-d002bc` 계열)를 렌더하면 `mysql-pvc` 가 1Gi 다. 2026-10-25 세션은 약 6만 주문(7 run)에서 가득 찼다.
- base Kafka 가 PVC 를 마운트하고도 로그를 컨테이너 저장소(`/tmp/kafka-logs`)에 써서, Pod 가 재시작되면 토픽과 offset 이 사라진다.
- run 스크립트가 데이터 볼륨 여유를 보지 않고 run 을 시작해, 디스크가 가득 차면 run 중간이나 초기화 단계에서야 드러난다.

사용자 결정(2026-11-16): ① binlog 설정은 그대로 두고 측정 overlay 볼륨을 10Gi 로 고정한다(PURGE 하지 않음).
② payment 스키마는 초기화하지 않고 예산에 넣는다. 예산 점검은 run 전 여유 공간 가드와 계획 규율 B14 로 한다.
③ Kafka 는 base 에서 PVC 로 연결한다.

## 2. 배경

### 코드 검증 (2026-11-16, main `59259f3e`)
| 전제 | 확인 결과 |
|---|---|
| `mysql-pvc` 크기 | `k8s/base/infra/mysql/mysql.yml` 1Gi. `gke-d002bc/patches/pvc-storageclass.yml` 은 `storageClassName` 만 더한다. 세션 중 10Gi 온라인 확장은 파일에 없다 |
| 측정 overlay 계보 | `gke-d002bc` ← `gke-d002bc-mysql-2000m` ← `gke-d078-contention` ← `gke-d078-contention-product-outbox-5s`. PVC 패치는 뿌리 `gke-d002bc` 에만 있다 |
| Kafka 실제 로그 경로 | `apache/kafka:3.8.1` 을 base 와 같은 env 로 로컬에서 띄우니 `Loading logs from log dirs ArrayBuffer(/tmp/kafka-logs)`. `/var/lib/kafka/data` 는 비어 있었다. env 로 만든 server.properties 에 `log.dirs` 가 없어 Kafka 기본값이 쓰인다 |
| Kafka 재기동 시 포맷 | 이미지 `launch` 가 storage format 결과의 `already formatted` 를 허용한다. 영속 볼륨에서 재기동해도 막히지 않는다 |
| Kafka 실행 계정 | uid/gid 1000(`appuser`). 이미지 안 `/var/lib/kafka/data` 는 appuser 소유지만 PD 를 마운트하면 그 뿌리는 root 소유가 된다. base 에 `securityContext` 가 없다 |
| run 사이 초기화 | `d078-s3-run.sh` 가 `d002bc-reset.sql`(order)·`d002bc-product-reset.sql`(product)만 실행한다. payment 는 초기화하지 않고, run 스크립트는 payment 수치를 읽지 않는다 |
| 영향받는 소비자 | `scripts/deploy-overlay.sh`(kafka PVC·Deployment 를 먼저 적용), `scripts/tests/test_deploy_overlay.py`(kafka-pvc 의 storageClassName 단언). 크기와 env 를 바꿔도 둘의 단언 대상은 그대로다 |

### 디스크 예산
- MySQL: 첫 run 전 고정분 214MiB에 run 마다 83~123MiB(binlog 73%)가 늘었다. 10Gi(ext4 약 9.8GiB)면 run 당 123MiB 기준으로 약 75 run(약 60만 주문)이 들어간다. 계획 run 수(6~8 + 재시도)의 열 배에 가깝다.
- Kafka: run 당 증가량은 측정된 적이 없다(지금까지 PVC 에 쓰지 않았다). 기본 보존 7일·세그먼트 1GiB 라 세션 안에서 지워지지 않는다. MySQL 과 같은 10Gi 로 두고 실제 증가량은 P3 가드가 run 마다 남기는 기록으로 잰다.

### 트레이드오프
- 과거 기준선(2026-10-24·25)에서 Kafka 는 노드 부트 디스크에 썼다. 이 변경 뒤에는 별도 PD 에 쓴다. 측정 조건이 하나 바뀌므로 다음 측정 계획의 전제표에 적어야 한다(§미해결).
- base 를 고치므로 운영 overlay(`gke`, `minikube`)의 Kafka 도 1Gi PVC 에 쓰게 된다. 지금까지는 노드 저장소에 크기 제한 없이 썼다. 보존 설정이 없어 오래 돌면 1Gi 를 채울 수 있다(§미해결).
- `fsGroup` 을 주면 kubelet 이 마운트 때 볼륨 소유 그룹을 재귀적으로 바꾼다. 볼륨이 작아서 기동 지연은 무시할 수 있다.

### ADR 판단
새 외부 의존성, 경계 변경, 새 인프라 모두 없다. 되돌릴 때 고칠 곳은 kafka.yml 과 측정 overlay 패치뿐이다. ADR 은 쓰지 않는다.

## 3. 작업 항목
- [x] P1. base `kafka.yml`: `KAFKA_LOG_DIRS=/var/lib/kafka/data/logs` 를 더한다. 마운트 뿌리가 아닌 하위 경로를 쓰는 이유는 ext4 뿌리의 `lost+found` 를 피하기 위해서다. Pod `securityContext.fsGroup: 1000` 을 더해 appuser 가 PD 뿌리 아래에 쓸 수 있게 한다.
- [x] P2. 측정 overlay `gke-d002bc` 에 `mysql-pvc`·`kafka-pvc` 를 10Gi 로 올리는 패치를 더한다. 하위 overlay 는 상속한다.
- [x] P3. `d078-s3-run.sh`: run 시작 전에 MySQL `/var/lib/mysql` 와 Kafka `/var/lib/kafka/data` 의 여유를 `df` 로 읽어 `$P-disk.tsv` 에 남긴다. 어느 하나라도 `MIN_FREE_MIB`(기본 1024)보다 적거나 읽지 못하면 k6 전에 exit 5 로 멈춘다. 초기화 뒤 한 번 더 기록해 run 당 증가량을 남긴다.
- [x] P4. `docs/conventions/plan-blindspots.md` 에 B14 를 더한다. 과금 측정 계획은 계획 run 수에 run 당 디스크 증가를 곱한 값(binlog·초기화 DELETE 포함)을 볼륨 크기와 대조한다.
- [x] P5. 문서: 스크립트 머리 주석(선택 인자·exit 코드), `loadtest/README.md` 에서 해당 run 절차를 설명하는 곳이 있으면 갱신한다.

## 검증 방법
- P1, 실패 주입: 로컬 docker 볼륨을 PD 처럼 root:root 0755 로 만들고 `lost+found` 를 넣는다.
  (a) `KAFKA_LOG_DIRS` 를 마운트 뿌리로 두고 기동해 결과를 기록한다(lost+found 로 실패하는지 확인).
  (b) 하위 경로만 주고 권한은 그대로 두면 쓰기 실패로 기동하지 못하는지 확인한다.
  (c) fsGroup 을 흉내 내 root:1000 2775 로 바꾸면 기동한다. 메시지를 쓰고 consumer offset 을 커밋한 뒤 컨테이너를 지우고 같은 볼륨으로 다시 띄운다. 토픽과 offset 이 남는지 보고 볼륨에 세그먼트 파일이 생겼는지 확인한다.
- P2: `kubectl kustomize` 로 `gke-d002bc` 와 하위 overlay 3개를 렌더해 두 PVC 가 10Gi 인지 확인한다. `gke`·`minikube`·`gke-d002a` 렌더는 Kafka env 와 securityContext 말고는 바뀌지 않아야 한다(main 렌더와 diff). `python3 scripts/tests/test_deploy_overlay.py` 통과.
- P3, 실패 주입: PATH 에 `kubectl` 스텁을 넣어 `df` 출력의 여유를 (a) 500MiB (b) 빈 출력 (c) 5000MiB 로 준다. (a)(b) 는 k6·ssh 전에 exit 5, (c) 는 가드를 지나는지 확인한다. 가드를 지난 뒤의 호출이 스텁에 기록되지 않는지(= 멈췄는지)를 스텁 호출 로그로 대조한다.
- 공통: ci.yml 의 CI policy lint 를 전부 돌린다. k8s 매니페스트 변경이라 일부만 돌리면 red 를 놓친다(plan-blindspots 자동화 후보 참고).

## 완료 조건
- 위 검증이 모두 통과하고 결과를 audit 에 남긴다.
- GKE 실환경 검증은 이번 범위가 아니다. 다음 과금 세션의 첫 배포에서 `kubectl exec deploy/kafka -- ls /var/lib/kafka/data/logs` 와 P3 기록으로 확인한다(§미해결).

## 미해결
- 운영 overlay Kafka 1Gi 에 보존 정책이 없다. 지금까지는 노드 저장소라 드러나지 않았다. 처분: /ship 때 부채 행으로 올릴지 사용자에게 묻는다.
- Kafka 저장 위치가 노드 부트 디스크에서 PD 로 바뀐다. 처분: 다음 측정 계획의 전제표(B13)에 적는다. 이번에 측정하지 않는다.
- `gke-d002a`(읽기 경로) 계열 PVC 는 1Gi 로 둔다. 쓰기가 적고 디스크 문제가 난 적이 없다. 처분: 그 계열로 장시간 세션을 계획하면 B14 점검에서 다룬다.
- GKE 실환경에서 fsGroup 과 하위 경로가 동작하는지는 로컬 흉내로만 확인한다. 처분: 다음 과금 세션 첫 배포에서 확인한다.
