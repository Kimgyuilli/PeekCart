# D-120 — 주문번호 접미사의 번호 공간 확대

기준: 2026-11-19, main `8433ad29`. 사용자 결정(2026-11-19)은 번호 공간 확대다. 충돌 시 재생성과 시퀀스 방식은 기각됐다.

등급 M: 고치는 모듈은 order-service 하나다. 다만 주문번호 값의 형식(길이 21자에서 29자)이 공개 API 응답과
`order.created`·`order.cancelled` 페이로드로 나간다. 필드 타입은 그대로이고 파싱하는 곳은 없지만(아래 표),
값 형식도 계약으로 볼 여지가 있어 높은 쪽을 골랐다. 되돌림은 이 PR 의 revert 로 끝난다. 이미 저장된 행은 형식과
무관하게 유효하다.

## 1. 명제

다음 중 하나라도 성립하면 미완이다.

- `OrderCommandService` 가 만드는 주문번호의 접미사가 16 hex 가 아니다. 즉 `^ORD-\d{8}-[0-9A-F]{16}$` 에 맞지 않는다.
- 접미사 16자 중 값이 고정된 자리가 있다. UUID 앞 16자를 그대로 자르면 13번째 자리가 버전 니블 `4` 로 고정돼
  실제 공간이 60비트가 된다. 사용자 결정의 64비트가 아니다.
- 새 형식이 `orders.order_number` 컬럼(`VARCHAR(50)`)이나 이 값을 받는 다른 곳의 길이·형식 제약을 넘는다.
- `docs/04-design-deep-dive.md` 의 `order.created` 예시가 실제 형식과 다르다.

### 코드 검증 (2026-11-19)

| 전제 | 확인 결과 | 계획에 미친 영향 |
|---|---|---|
| 생성 위치 | `OrderCommandService.generateOrderNumber`(private) 한 곳. `"ORD-" + BASIC_ISO_DATE + "-" + UUID 앞 8 hex 대문자` | 이 메서드만 고친다 |
| UUID 앞 16 hex 의 무작위 비트 | `UUID.randomUUID()` 는 v4 다. 하이픈을 뺀 문자열의 13번째 자리(인덱스 12)는 버전 `4` 로 고정이다 | UUID 를 자르지 않고 `SecureRandom.nextLong()` 64비트를 16 hex 로 쓴다. 기존 생성기와 같은 예측 불가성(SecureRandom)을 유지한다 |
| 컬럼 제약 | `V1__init_order.sql` `order_number VARCHAR(50) NOT NULL`, `uk_orders_order_number`. `Order.orderNumber` 의 `@Column` 에 length 없음 | 29자는 들어간다. 마이그레이션 없음. 기존 21자 번호와 새 29자 번호는 길이가 달라 서로 충돌하지 않는다 |
| 이벤트 페이로드 | `common` 의 `OrderCreatedPayload`·`OrderCancelledPayload` 가 `String orderNumber`. 형식 검증 없음 | 변경 없음 |
| 소비자 | notification `NotificationConsumer` 는 `asText()` 로 읽어 알림 문구에 넣기만 한다. payment·product main 에는 `orderNumber` 참조가 없다(테스트 픽스처 `"ORD-001"` 만) | 변경 없음. 파싱하는 외부 계약이 없으므로 사용자 결정이 더 필요한 분기도 없다 |
| 응답 DTO | `OrderResponse`·`OrderDetailResponse`·`OrderSummaryDto`·`OrderDetailDto` 가 문자열을 그대로 전달 | 변경 없음 |
| 테스트·스크립트 | order-service 통합 테스트는 `"ORD-" + UUID.randomUUID()`(40자)를 이미 쓴다. `loadtest/`·`scripts/e2e/saga_e2e.py` 는 `ORD-00x` 에러 코드만 본다 | 길이 가정이 깨지는 곳 없음 |
| 충돌 계수 | `OrderPoolContentionLocalProbeTest` 가 `orderNumberCollisions` 를 센다. 열린 PR #269 가 같은 파일을 고친다 | 이번 범위에서 건드리지 않는다(§미해결) |

ADR 판단: 새 외부 의존성, 경계 변경, 새 인프라가 없다. 되돌림이 이 파일 안에서 끝난다. ADR 은 쓰지 않는다.

## 2. 작업 항목

- [x] P1. `generateOrderNumber` 의 접미사를 `SecureRandom.nextLong()` 의 16 hex 대문자로 바꾼다. 단위 테스트가 호출할 수 있게 package-private static 으로 연다(인스턴스 상태를 쓰지 않는다).
- [x] P2. `OrderCommandServiceTest` 에 테스트를 더한다. (a) `createOrder` 가 저장하는 `Order` 의 번호가 `^ORD-\d{8}-[0-9A-F]{16}$` 이고 날짜가 오늘이다. (b) 생성기를 여러 번 불러 접미사 16자리 각각이 두 가지 이상의 값을 가진다(고정 자리 없음).
- [x] P3. `docs/04-design-deep-dive.md` §8-2 `order.created` 예시의 `orderNumber` 를 새 형식으로 고친다.

## 3. 검증 방법

- P1·P2, 실패 주입 1: 생성기를 원래 코드(UUID 앞 8 hex)로 되돌리면 P2(a) 가 실패한다.
- P1·P2, 실패 주입 2: 생성기를 UUID 앞 16 hex 로 바꾸면 P2(a) 는 통과하고 P2(b) 가 13번째 자리 고정으로 실패한다.
  P2(b) 의 반복 횟수는 자리마다 한 값만 나올 확률이 무시할 만큼 작게 잡는다(256회면 한 자리가 우연히 고정될 확률이 16 x 16^-255 수준).
- 회귀: `./gradlew :order-service:test` 전체 통과. 번호를 받는 다른 모듈은 코드가 바뀌지 않으므로 돌리지 않는다.
- `scripts/*-lint.sh` 전부 통과.

## 미해결

- `OrderPoolContentionLocalProbeTest` 의 주문번호 충돌 계수(`collisions`, `orderNumberCollisions`)는 64비트 공간에서 사실상 0 이 된다.
  열린 PR #269 가 같은 파일을 고치므로 이번에 지우지 않는다. #269 머지 뒤 계수를 남길지(회귀 감시) 지울지 정한다.
- 충돌 확률은 0 이 아니다. 하루 6만 건이면 약 1e-10 이다. 충돌하면 여전히 500 이다. 재생성은 사용자가 기각했다.
