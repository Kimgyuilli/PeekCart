# D-076 — Kafka 오류 핸들러 jitter 일관성

## 1. 명제
4개 기존 고정 재시도 핸들러 중 하나라도 jitter가 없거나 재시도 예산·소진 후 DLQ/정지 계약을 바꾸면 미완이다.

## 2. 배경과 코드 검증
| 전제 | 실제 코드 | 처분 |
|---|---|---|
| Product만 jitter | ProductKafkaConfig 0.5, 1/5/30초 | 기존 유지 |
| 나머지 4 handler | Order/Payment/NotificationKafkaConfig 및 공유 DeadLetterKafkaConfig의 FixedSequenceBackOff | 같은 jitter 적용 |
| 원본 DLQ 계약 | 세 서비스 recoverer는 topic.dlq 발행 뒤 Slack | 그대로 검증 |
| DLQ 원장 실패 | guard.onRetriesExhausted, ackAfterHandle=false | 재귀 DLQ 없이 유지 |
| 라이브러리 구성 | 로컬 spring-kafka 3.3.14 jar javap로 failureTracker/backOff/backOffHandler 확인 | 실제 빈 검사, sleeper만 대체 |

등급 L: 다서비스와 공유 모듈의 정책 표면을 변경한다. 신규 의존·스키마·경계 이동 없음. ADR-0025 D2의 기존 원칙을 적용하므로 새 ADR 불필요. 구조 이동이 없어 B1/B1b/B5/B6/B8/B10 해당 없음. B2 실제 경로 확인, B3 공용 테스트 헬퍼 common testFixtures, B4 네 핸들러 명시, B7/B9 상태 계약 유지, B11 관측 표면 변화 없음, B12 DB 원자성 변경 없음.

## 3. 작업 항목
- [x] P1. 네 핸들러를 기존 공용 JitteredSequenceBackOff(0.5, 1000, 5000, 30000)로 변경.
- [x] P2. 실제 구성 handler로 3회 retry와 4번째 failure recovery, 범위·jitter 비율, 원본 DLQ/원장 guard 계약 검증.
- [x] P3. 전체 CI·독립 검증·root 병합·기록.

## 검증 방법
실제 구성 빈의 backoff를 검사한다. 고정 backoff로 되돌리면 타입/비율 검사가 실패하고, retry 횟수나 간격을 바꾸면 실제 handleOne 호출 회수/범위 검사가 실패한다. sleep만 기록용으로 바꾸고 recoverer는 실제 서비스 구성 그대로 호출해 Kafka 발행 토픽/키/값 1회 및 DLQ guard 인수를 확인한다. 기존 integration suites와 CI gate는 사용자 승인에 따라 원격 전체 검증으로 대체한다. 로컬 Gradle은 root 슬롯 승인 후에만 실행한다.
