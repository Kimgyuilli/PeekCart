# D-113 — sweeper 다건 회수의 재고 복구 유실

## 명제
`sweepExpiredLeases` 가 한 트랜잭션에서 예약 N 건을 회수하면 재고가 N 보다 적게 복구된다.

배경: `StockReservationJpaRepository.markReleasedIfReserved` 는 `@Modifying(clearAutomatically = true)` 이고
`flushAutomatically` 가 없다. JPQL bulk UPDATE 의 auto flush 는 질의 공간(`stock_reservations`)만 보므로 직전 건의
`Inventory.restore` 변경(`inventories`)이 flush 되지 않은 채 clear 로 버려진다. 임시 통합 테스트(만료 RESERVED 3건,
재고 100)에서 `reclaimed=3`·재고 101 이었다(기대 103). "RELEASED 인데 재고 미복구"라 D-108 세션의 diff −1 과 같은
모양이지만, 세션 증거에 sweeper 실행 기록이 없어 그 −1 의 귀속은 증명할 수 없다(사용자 결정 2026-11-16: 결함 수정만).

## 작업 항목
- [x] P1. `markReleasedIfReserved` 에 `flushAutomatically = true` 를 더한다.
- [x] P2. 통합 테스트: 같은 상품 만료 RESERVED 3건을 sweeper 로 회수하면 재고가 +3, 3건 모두 RELEASED.

## 검증
P2 를 P1 없이 돌려 1건분만 복구돼 실패하는지 확인한 뒤(실측: 기대 100, 실제 80) P1 을 적용해 통과시킨다. `./gradlew :product-service:test` 통과.

## 미해결
- `markConfirmedIfReserved`·`markCompensatedIfAbsent` 도 `clearAutomatically` 만 있다. 지금 호출 경로(`confirm`)에는 그 앞에
  dirty 엔티티가 없어 유실이 없다. 앞에 엔티티 변경을 두는 코드가 생기면 같은 결함이 된다. 이번에 고치지 않는다.
- 커밋 정지·lock wait timeout 경로의 장애 주입 재현은 하지 않는다. 그 경로는 eventId 멱등과 단일 트랜잭션이라 코드 분석상
  원장을 깨는 경로가 보이지 않았다.
