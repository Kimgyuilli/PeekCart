# D-093: 실제 alert 초기 평가 준비 대기

## 1. 명제
API 준비와 고정 15초 경과만으로 baseline을 시작하거나, 초기 NoData·비정상 인스턴스·부재 벡터를 정상으로 취급하거나, 준비 실패 원문을 남기지 않으면 미완이다.

### 코드로 확인한 배경
| 전제 | 확인 결과 |
|---|---|
| `scripts/monitoring/verify_alerts.py` | API 준비 뒤 고정 15초 후 baseline120s를 시작한다. `snapshot`의 vector/health 단언은 관측 기록보다 앞이어서 실패 원문을 보존하지 못한다. |
| 정본 평가 주기 | 모든 그룹 `interval: 1m`을 검증한다. 임의 15초가 첫 평가 완료를 보장하지 않는다. |
| 기존 정상 조건 | rule inactive, 실제 vector 0, 개별 instance Normal과 서비스/cache 집합을 본다. 이를 초기 준비 gate에도 사용한다. |
| 기존 단위 검사 | 저장된 Grafana11.6 fixture의 state vocabulary만 검사한다. 시간 경과·준비 지연·timeout 검사는 없다. |

등급 M: 공유 검증 도구의 baseline 진입 계약을 바꾼다. 운영 alert·타이머·인프라 변경은 없다. ADR-0019의 실제 평가 증거 경계를 유지하므로 새 ADR은 추가하지 않는다.

## 2. 작업 항목
- [x] P1. 고정 sleep을 단조 시계 기준 유한 준비 대기로 대체한다. 모든 대상의 벡터 존재/0·서비스/cache·Grafana health ok·instance Normal을 확인한 뒤 baseline을 시작한다.
- [x] P2. 각 준비 시도의 원본 Grafana/query 응답과 실패 정보를 먼저 보존한다. timeout 시 관측 경로를 포함해 실패하고 cleanup을 수행한다.
- [x] P3. fake clock으로 지연 NoData 후 정상, 0 아닌 vector·인스턴스 미준비·서비스 누락, 영구 NoData/timeout을 검증하고 CI에 연결한다.
- [x] P4. `--startup-only`로 동일 운영 평가 주기와 baseline120s를 실제 무료 로컬 바이너리에서 검증한다. 결과는 BASELINE_PASS로 구분하고 전체 lifecycle 성공으로 기록하지 않는다. 전체 CI와 검증 결과를 audit에 기록한다.

## 3. 검증 방법
- P1/P3: fake probe/시계가 첫 NoData, 다음 부재/0표본, 마지막 정상 표본을 반환할 때 정상 표본 전 반환하지 않아야 한다. 모든 영구 미준비 종류는 주어진 deadline에서 실패해야 하며 대기 후 baseline을 실행할 수 없어야 한다.
- P2: 지연 및 HTTP 오류의 raw 응답/메시지가 관측 JSONL에 남고 timeout 메시지에 경로가 있어야 한다. 원문이 기록되기 전 단언하면 실패하는 검사를 둔다.
- P4: root heavy 슬롯 승인 후 clean commit의 `--run --startup-only`를 실행한다. source SHA, rule hash, 실제 이미지/버전, 초기 readiness 관측과 baseline 정상 표본, cleanup을 보존한다. 제품 pending/평가 시간을 줄이지 않는다.
- 단위 검사, 관련 PromQL/SSOT lint, syntax/diff/consistency/writing 검사 및 동일 SHA 전체 CI를 실행한다. 로컬 전체 Gradle은 공유 자원 지시에 따라 CI test shards로 검증하고 pending을 통과로 기록하지 않는다.

## 미해결 / 범위 밖
- D-090 정적 Outbox 계약 변경은 별도 PR이다. 이 PR은 초기 평가 준비 경쟁을 다룬다.
- 전체 Normal/Pending/Alerting/Normal lifecycle 및 외부 전달을 새 증거로 주장하지 않는다. 기존 D-063 역사 기록을 유지한다.
- 실제 Docker 실행은 root heavy 슬롯 승인 전 대기한다. root 소유 공유 완료 문서는 변경하지 않는다.

실행 세부: 초기 준비 timeout 기본값은 180초다. `--readiness-timeout`으로 유한 양수만 지정할 수 있으며, 짧은 deadline의 실제 실패 대조에도 사용한다. 이 값은 Grafana rule의 평가 주기/for를 바꾸지 않는다.

## 최신 main 통합 (2026-10-21)

최종 비교 base를 `d506f7eef5d29e9894342a6d47b93b89a34266b2`로 고정하고 정상 merge했다. 검증 도구/테스트와 fixture exporter·Grafana 정본은 최초 검토 및 실측 이후 바뀌지 않았다. CI에는 보존 gate와 앞선 작업의 호출을 유지하면서 기존 D-093 단위 검사 두 줄을 병합했다. 운영 결제·DLQ의 최신 변경은 이 독립 fixture 기반 startup 검증의 입력이 아니며 최신 전체 제품 검증은 Actions에서 수행한다.

원본 증거 16개 파일은 이전 head와 SHA-256이 같다. 전체 PR `git diff --check`는 raw startup/cleanup 텍스트의 trailing whitespace 72건으로 exit 2다. 바이트 보존을 위해 정규화하지 않으며 전체 diff가 clean이라고 주장하지 않는다. 실행 코드·CI·계획·해설/index 범위의 공백 검사는 통과했다. 새 보존 gate는 같은 base로 편집 전후 재실행하며 문서 이동/공유 완료 문서는 변경하지 않는다. 기존 실제 baseline/timeout은 역사 증거이고 이번 통합에서 Docker/로컬 전체 Gradle을 다시 실행하지 않았다. 최신 전체 Actions 결과와 정확 head의 독립 delta 검토를 기다린다.
