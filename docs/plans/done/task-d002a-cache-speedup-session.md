# 계획 — D-002a 캐시 배속 격리 측정 (GKE 세션)

> 선행: `task-d002-rescope.md` (범위 재정의). 이 세션은 재정의된 3축 중 **D-002a 만** 한다.

## 0. 범위를 하나로 줄인 이유

쿼터 `CPUS_ALL_REGIONS = 12` 안에서 D-002a/b'/c 를 전부 넣으면 노드를 앱과 부하발생기가
나눠 쓰게 된다. 세션 2 가 정확히 그렇게 했고 **"측정에 co-location 경합이 섞였다"를 편차로
남겼다**. 오염된 측정 3개보다 깨끗한 측정 1개가 낫다 — D-002b'/D-002c 는 다음 세션.

D-002a 를 고른 이유: **원문 D-002 의 표제(캐시 TPS ×2.31, 목표 ×3 미달)** 이고, 토글
`peekcart.cache.enabled`(`CacheConfig:69/111`)로 **대조군이 코드에 이미 있다**.

## 1. 예산 배치 (쿼터 12 vCPU)

| 자원 | 사양 | vCPU |
|---|---|---|
| GKE 노드 | `e2-standard-4` × 2 | 8 |
| loadgen VM | `e2-medium` × 1 | 2 |
| **합계** | | **10 / 12** |

**부하발생기를 클러스터 밖 VM 으로 되돌린다** — 세션 2 는 3노드가 필요해 k6 를 in-cluster Job
으로 돌렸지만, 이 세션의 스택은 product-service + MySQL + Redis 뿐이라 2노드로 충분하고
그만큼 VM 을 살 여유가 생긴다. 세션 2 의 편차를 구조적으로 제거한다(ADR-0004 원래 설계).

## 2. 스택 — 최소

product-service · MySQL · Redis **만**. 제외와 사유:

| 제외 | 사유 |
|---|---|
| gateway | 읽기 캐시 배속에 **인증 오버헤드 상수(+9.9ms, 세션 2 P14)** 와 RateLimiter(40 req/s fail-closed)를 섞지 않는다. 한도가 배속 측정을 무의미하게 만든다 |
| 나머지 4서비스 · Kafka | D-002a 읽기 경로와 무관 |
| NetworkPolicy | 8080 ingress 를 gateway 로만 제한하므로 VM 에서 직접 부하를 못 넣는다. **측정 전용으로 Internal LB 노출**(PR3c 가 지운 표면을 측정 목적으로 한시 복원 — `gke-probe-state1` 선례) |

이미지: AR `product-service:latest`(2026-09-14T22:07) — `product-service/src` 최종 변경이
09-14 00:49, `common/src` 11:38 이므로 **현재 코드와 동일**. 재빌드하지 않는다.

## 3. 측정

가설: 1차 측정의 ×2.31 은 **CPU 포화 상태에서 잰 값**이다(1차 병목 = CPU 확증). 캐시는 DB 시간을
없애지만 CPU 시간은 그대로라, CPU 가 binding constraint 면 배속이 ×3 에 못 미친다.
→ **CPU 여유를 바꿔가며 배속이 변하는지** 본다. 변하면 "×3 미달"의 설명은 캐시가 아니라 CPU 다.

| # | 조건 | 측정 |
|---|---|---|
| P1 | 클러스터 + VM + 스택 기동, 시드 | 준비 |
| P2 | 캐시 **OFF** (`peekcart.cache.enabled=false`) · CPU 여유 있음 | TPS·p95 기준선 |
| P3 | 캐시 **ON** · 동일 부하 | 배속 = TPS_on / TPS_off |
| P4 | 캐시 ON/OFF × **CPU 제한을 좁힌 조건** | 배속이 CPU 여유에 따라 변하는가 |
| P5 | Redis 왕복·MySQL 쿼리 시간 분해(가능 범위) | 잔여 시간의 귀속 |
| P6 | 정리(`loadtest/cleanup.sh` 계열) + 증적 | 과금 0 확인 |

**부하 수준은 429 가 없는 경로(gateway 미경유)라 한도가 아니라 포화로 정한다** — OFF 조건에서
CPU 가 포화되지 않는 지점을 먼저 찾고 그 지점을 고정한다.
