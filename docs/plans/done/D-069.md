# D-069 상품 cache miss의 DB 진입 제한

## 명제

Redis 장애 중 동시 cache load가 설정 상한보다 DB에 많이 진입하거나 초과 요청이 대기열을 만들면 미완이다.
상품 모듈과 공용 ErrorCode의 장애 응답 정책 변경으로 L. DB 보호 우선·초과 503은 사용자 승인, 구체 정책은 ADR-0037.
코드 확인: ResilientCacheErrorHandler는 get/put 실패를 삼키며 현재 모든 요청이 cache miss 본문으로 들어온다.

## 배경

새 외부 의존성 없이 기존 Spring AOP advisor와 semaphore를 사용한다. 공용 에러 코드 소비자는 BusinessException handler이며 기존 응답 형태를 유지한다. 구조 이동 없이 advisor가 기존 cache service만 대상으로 삼는다.

## 작업 항목

- [x] P1. cache와 transaction 사이 semaphore advice, 양의 상한/풀 여유 검증, PRD-005 503을 추가한다.
- [x] P2. 실제 Redis 연결 거부 중 동시 HTTP 요청의 상한·응답/거절·회복 및 permit 반납을 검증한다.
- [x] P3. 최신 전체 CI·독립 검증·root 병합/기록.

## 검증

기존 Toxiproxy 통합 하네스에서 Redis를 차단하고 첫 repository 진입을 latch로 고정한다.
다른 동시 요청이 503이고 repository 진입 횟수 1인지 확인한다. 실제 Hikari 최대/active/idle을 기록하며 차단된 read 옆에서 다른 connection의 UPDATE가 성공해야 한다. release 및 Redis 회복과 정상 캐시 hit의 permit 우회를 별도 확인한다.
mock만으로 DB 원자성 주장을 하지 않는다. 실제 DB가 있는 통합에서 경합 진입 지점만 latch로 제어한다.
기본 1은 SLO 측정값이 아니라 DB 보호 우선에 따른 보수적 직렬 정책이다. pod별 제한이며 GKE 성능은 범위 밖.
