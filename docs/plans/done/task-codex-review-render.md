# task-codex-review-render

> D-027 ② — Codex 리뷰 JSON → severity 표 렌더러.
> 재개 조건(실물 스키마 확보)은 2026-09-20 충족. `.cache/codex-reviews/*.json` 282개를 실측해 설계했다.

## 1. 명제

다음 중 하나라도 남아 있으면 미완이다.

- Codex 리뷰 JSON 을 사람이 손으로 읽어 `/plan` §6 · `/work` 의 severity 표를 조립하고 있다.
- **실패한 리뷰 응답(빈 파일 · `items: null` · 파싱 불가)이 "0건 = 자동 통과" 로 조용히 통과된다.**

두 번째가 이 작업의 무게중심이다. `/plan` §6 은 "P0/P1 이 0건이면 자동 통과" 라고 적혀 있는데,
사용량 한도로 죽은 런의 결과도 0건이다. 실측상 **282개 중 44개(16%)가 그 상태**다. 원인은 한 가지가 아니다 —
사용량 한도 9 · MCP transport/OAuth 실패 14 · 모델 capacity 1 · 나머지는 분류되지 않았다.
즉 "리뷰가 깨끗했다" 와 "리뷰가 아예 안 돌았다" 가 현재 구분되지 않는다. false-green 이다.

## 2. 배경 — 코드 검증 (2026-09-20, 실측)

전제를 ADR 이 아니라 현재 파일로 확인했다.

### 범위 변화 — 축소 1건 (이후 P6 으로 되돌림, §7 참조)

`scope` / `suggested_disposition` 이 **1267건 전부에서 비어 있다.** 두 필드는
`.claude/schemas/{plan,diff}-review.json` 의 `required` 에 없고, 프롬프트 `[항목 분류]` 가
말로만 요구한다. Codex 는 required 가 아닌 필드를 내보내지 않았다.

이 발견의 처분: **범위 밖(이월).** 렌더러는 두 필드를 "있으면 렌더, 없으면 컬럼 생략" 으로
다루고, 스키마 `required` 수정은 건드리지 않는다. 이유는 되돌림 비용이다 — 스키마 required
변경은 Codex 출력 계약을 바꾸는 일이라 `/plan` §5-1 · `/work` 프롬프트와 함께 움직여야 하고,
그 순간 등급이 L 로 올라간다. 렌더러 없이는 그 변경이 잘 됐는지 확인할 방법도 없다.
**렌더러가 먼저고 스키마는 그 다음이다.** 재검토 조건: 렌더러 배선 후 새 리뷰를 2~3회 돌려
"(미기재)" 가 계속 나오는 것을 눈으로 확인한 시점.

### ADR 판단

해당 없음. 새 외부 의존성 없음(`jq`·`python3` 는 기존 스크립트가 이미 쓴다), 아키텍처 경계
무변화, 인프라 무관. 되돌리려면 새 파일 2개 삭제 + 커맨드 문서 2곳 복원이 전부다.

## 3. 작업 항목

- [x] **P1.** `scripts/codex-review-render.sh <json>` — 정상 JSON 을 **스캔용 severity 표 +
      항목별 전문 블록** 두 단으로 렌더한다. 표는 처분을 고르는 자리(id·sev·category·위치·발견
      요약)이고, 전문은 그 판단의 근거다.
      출력은 `/plan` §6 헤더 형식(`=== ... (총 N건: P0 a / P1 b / P2 c) ===`)을 그대로 낸다.
      `--round N` 으로 라운드 번호를 받고(JSON 에 없다), 리뷰 종류(plan/diff/adr)는 파일명
      접두사에서 뽑되 `--kind` 로 덮을 수 있게 한다.
- [x] **P2.** 실패 응답을 **exit 2 로 구분**한다. 판별 대상 셋: 빈 파일(`! -s`) · `items` 가
      `null` · `jq` 파싱 실패. (`items: null` 은 이력에 실물이 없지만 스키마상 가능하고
      비용이 한 줄이라 유지한다 — V2 가 합성 입력으로 덮는다.) 셋 다 동명 `.stderr` 의 마지막 유의미한 줄을 인용해
      `리뷰 실패 — 표를 렌더하지 않는다` 를 내고 끝낸다. **0건과 절대 섞지 않는다.**
      정상 0건은 exit 0 + `지적 0건 (자동 통과)`.
- [x] **P3.** 선택 필드 처리 — `file`/`line` 은 있을 때만 컬럼을 만든다(plan 리뷰엔 없다).
      `scope`/`suggested_disposition` 은 현재 전량 결측이므로 **한 건이라도 있을 때만** 컬럼을
      추가한다. 전량 결측이면 컬럼 자체를 내지 않는다 — 빈 칸 줄을 1267개 그리지 않기 위해서다.
- [x] **P4.** `scripts/codex-review-render-selftest.sh` — 고정 입력으로 아래를 검증한다.
      기존 `*-selftest.sh` 관례를 따른다.
- [x] **P6.** `.claude/schemas/{plan,diff}-review.json` 의 `required` 에 **전 property 를 넣는다.**
      현재 API 는 structured output 스키마에 대해 "`required` 는 properties 의 모든 키를 포함해야
      한다" 를 강제하고, 그렇지 않으면 400 `invalid_json_schema` 로 **호출 자체를 거부한다.**
      즉 지금 Codex 리뷰는 전부 깨져 있다. 부수 효과로 `scope`/`suggested_disposition` 결측
      (1267/1267)도 함께 해소된다 — 프롬프트가 말로 요구하던 것을 스키마가 강제하게 된다.
- [x] **P5.** `.claude/commands/plan.md` §6 과 `.claude/commands/work.md` 의 대응 절에 호출을
      배선한다. "표로 제시하라" 산문을 스크립트 호출 한 줄로 바꾸고, **exit 2 면 리뷰 상태를
      `미결(리뷰 실패: <사유>)` 로 기록** 하라는 규칙을 명시한다(§8 4값 중 `미결`).

## 4. 검증 — 실패를 주입해 확인한다

`scripts/codex-review-render-selftest.sh` 가 임시 디렉토리에 아래 입력을 만들고 각각 돌린다.
"존재한다" 는 검증이 아니므로 전부 **깨진 입력을 넣어 기대한 실패가 나오는지** 본다.

| # | 주입하는 실패 | 기대 |
|---|---|---|
| V1 | 0바이트 파일 + stderr 에 `usage limit` | exit **2**, 출력에 `usage limit` 인용. **exit 0 이면 실패** |
| V2 | `{"run_id":"x","summary":"s","items":null}` | exit **2**. 이 입력이 `총 0건` 을 내면 실패 |
| V3 | `{"run_id":"x","summary":"s","items":[]}` | exit **0**, `지적 0건 (자동 통과)`. V1·V2 와 **다른** 출력이어야 한다 |
| V4 | 깨진 JSON (`{"items":`) | exit **2** |
| V5 | plan 형태 3건 (P0 1 / P1 1 / P2 1), `file` 없음 | exit 0, 헤더 `총 3건: P0 1 / P1 1 / P2 1`, **file 컬럼 없음** |
| V6 | diff 형태 2건, `file`/`line` 있음 | exit 0, **file:line 컬럼 있음** |
| V7 | `scope`/`suggested_disposition` 전량 결측 | 해당 컬럼이 출력에 **없다** |
| V8 | 그중 1건만 `suggested_disposition: "defer"` | 해당 컬럼이 **생긴다**, 나머지 행은 `-` |
| V10 | 실제 이력 중 `발견` 이 400자인 항목 | **표의 해당 칸은 잘리고**, 아래 전문 블록에 전체가 나온다 |
| V13 | `items` 가 `{}` · `false` · `0` · `""` · `"x"` | 전부 exit **2**. 파이썬 `or []` 로 접혀 "지적 0건" 이 되면 실패 |
| V14 | `--round` / `--kind` 뒤에 값 없음 | exit 1. **끝나는지**를 본다 — `shift 2` 실패는 무한 루프가 된다 |
| V15 | 잘못된 `--kind` · 위치 인자 중복 · 인자 없음 · 없는 파일 | 전부 exit 1 + 해당 메시지 |
| V9 | 실제 이력 회귀 — `.cache/codex-reviews/*.json` 전수 | 종료 코드가 **0 아니면 2** 뿐이고, exit 2 집합이 "빈 파일 ∪ 파싱 불가 ∪ items null" 과 **정확히 일치**. 건수는 하드코딩하지 않는다 |
| V11 | 원인 줄이 파일 중간에 있고 마지막 줄이 `}` 인 실제 stderr | `}` 가 아니라 `"message"` 본문을 인용한다 |
| V12 | 원인 줄 뒤에 리뷰 대상 diff 가 echo 된 stderr | diff 내용이 아니라 원인 줄을 인용한다 |

V9 가 핵심이다. 실측 분포를 그대로 재생산하지 못하면 판별 로직이 틀린 것이다.
`.cache/` 가 없는 환경에서는 V9 를 `skip` 으로 보고한다(조용히 통과시키지 않는다).

## 7. 정정 이력

- **2026-09-20 · P1 — 단일 표에서 "표 + 전문 블록" 두 단으로.**
  초안대로 단일 마크다운 표를 만들어 실제 이력(`plan-task-impl3-...json`, 13건)에 돌렸더니
  `발견`·`제안` 셀이 **평균 400자**라 한 행이 화면을 몇 배 넘겼다. 표의 용도는 훑으면서 처분을
  고르는 것인데 그 용도가 죽는다. 표에는 요약만 싣고 전문은 아래 블록으로 내린다.
  실물 데이터를 돌려보기 전에는 보이지 않던 문제다.

- **2026-09-20 · §2 표 / §4 V9 — 실패 파일 수 45 → 44, `items: null` 1 → 0.**
  초안은 `jq -s` 를 `find -size +2c` 로 고른 파일 집합에 돌려 집계했는데, 크기 반올림 때문에
  집합이 282개와 어긋났고(44 + 239 = 283) 그 어긋남이 `null_items: 1` 로 새어 나왔다.
  V9 회귀가 전수를 직접 돌려 **238 / 44 / null 0** 으로 반증했다. 실측 수치를 그 쪽으로 맞췄다.
  교훈은 집계를 `find -size` 로 미리 거르지 말고 전수에 돌리라는 것이다.

- **2026-09-20 · §2 "빈 파일의 원인" — "전부 usage limit" 은 틀렸다.**
  초안은 stderr 2개를 표본으로 보고 전부 사용량 한도라고 적었다. 44건 전수 분류 결과
  usage limit 은 **9건뿐**이고 rmcp transport 9 · OAuth refresh 5 · model capacity 1 ·
  기타 20 이었다. 표본 2개로 전수를 단정한 것이 잘못이다. 결론(0건과 구분해야 한다)은
  그대로지만 근거를 정정한다.

- **2026-09-20 · §4 V9 — 건수 하드코딩(238/44)에서 불변식 검사로.**
  V9 를 238/44 로 박아두었는데 이번 세션에서 Codex 를 한 번 더 돌리자마자 `.cache` 가 늘어
  그 자리에서 깨졌다. 스냅샷은 계약이 아니다. 종료 코드 집합과 실패 조건의 일치를
  렌더러와 별도 경로로 계산해 대조하는 형태로 바꿨다.

- **2026-09-20 · P2 stderr 인용 — "마지막 유의미한 줄" 휴리스틱 폐기.**
  실제 codex stderr 에 돌려보니 마지막 줄이 `}` 이거나 **리뷰 대상 diff 에서 echo 된 내용**
  이었다. 원인 줄은 대개 파일 중간에 있다. 위치가 아니라 패턴으로 찾도록 바꾸고
  (`"message"` → 알려진 마커 → `^ERROR:` → 마지막 줄) V11·V12 로 고정했다.
  V1 픽스처가 원인 줄을 마지막에 둔 순한 형태라서 잡히지 않았던 결함이다.

- **2026-09-20 · 등급 M → L · P6 편입 — 스키마 이월 판단의 전제가 틀렸다.**
  §2 는 스키마 `required` 수정을 "렌더러가 먼저고 스키마는 그 다음" 이라며 이월했다.
  그 판단은 **리뷰가 정상 작동 중**이라는 전제 위에 있었다. 실제로는 현재 API 가 이 스키마를
  400 `invalid_json_schema` 로 거부하고 있어서 **Codex 리뷰가 한 건도 돌지 않는다.**
  이번 PR 의 diff 리뷰를 시도하다 렌더러가 그 400 을 잡아내 드러났다 — 이월 조건으로 걸어둔
  "렌더러 선행" 이 그 자리에서 충족된 셈이다.
  임시 스키마 사본으로 확인한 결과 `required` 에 전 property 를 넣으면 호출이 통과하고
  Codex 가 `scope`·`suggested_disposition` 를 실제로 채워 반환한다.
  Codex 출력 계약 변경이므로 등급을 **L** 로 올린다. 사용자 확인을 받아 범위에 넣었다.

- **2026-09-20 · diff 리뷰 라운드 1 — P1 2건이 명제의 빈틈을 드러냈다.**
  ① `items` 가 배열인지 보지 않아 `{"items":{}}` 가 exit 0 `지적 0건` 으로 샜다. 파이썬의
  `or []` 가 falsey 를 빈 배열로 접는 경로다. **이 작업이 막으려던 false-green 그 자체가
  구현 안에 남아 있었다.** 게다가 V9 의 기대값을 렌더러와 같은 jq 식으로 계산한 탓에
  회귀 검사도 함께 눈을 감았다 — 기대값 계산을 다른 표현으로 분리했다.
  ② 값이 빠진 `--round` 에서 `shift 2` 가 실패해도 루프가 전진하지 않아 무한 루프가 됐다.
  둘 다 직접 재현한 뒤 고쳤고 V13·V14 로 고정했다.
  교훈은 "검증 도구와 검증 대상이 같은 출처면 둘 다 틀려도 통과한다" 이며, 이는 `/work` §5
  체크 항목의 false-green 항이 정확히 지목하는 유형이다.
