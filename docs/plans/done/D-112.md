# D-112 — payment 예약 결과 선도착을 marker 로 받아 파티션 차단 제거

## 1. 명제

다음 중 하나라도 해당하면 미완이다.

- `stock.reservation.result(reserved=true)` 처리 시 Payment 가 없으면 예외를 던져 blocking 재시도(1·5·30초)로 파티션을 막는다.
- Payment 가 없을 때 받은 예약 결과가 나중에 `order.created` 로 Payment 가 생겨도 적용되지 않는다(결제 준비 상태 유실).
- 두 consumer group 이 같은 주문을 동시에 처리할 때 marker 가 적용되지 못하고 남는 순서가 있다.

배경: D-108 세션(`loadtest/reports/2026-10-26/session-issues.md` 5)에서 디스크 가득 참 구간에 결제 생성 134건이 DLQ 로 갔다.
그 주문들의 예약 결과가 건마다 30~60초 재시도한 뒤 DLQ 로 가며 약 1.5시간 동안 뒤 레코드를 막았다. 선행 `order.created` 가 DLQ 로
간 주문은 재시도로 풀리지 않는다. 사용자 결정(2026-11-15): non-blocking 재시도 토픽·선행 DLQ 판별 대신, 같은 서비스의 취소 선도착
marker(`payment_cancellations`)와 같은 방식으로 예약 결과를 영속하고 `order.created` 처리 때 적용한다.

### 코드 검증

| 전제 | 확인한 곳 | 결과 |
|---|---|---|
| 현재 재시도 경로 | `PaymentEventConsumer:103` | Payment 미존재면 `PaymentException(PAY_003)` → `PaymentKafkaConfig` `JitteredSequenceBackOff(0.5, 1s, 5s, 30s)` 뒤 DLQ |
| 선례 marker | `PaymentCancellation` · `PaymentCancellationRepository{,Impl}` · `PaymentCancellationJpaRepository` · `V1__init_payment.sql:39` | `order_id` PK + 시각. `handleOrderCreated` 가 존재하면 CANCELLED 로 생성하고 삭제 |
| 소비 group 분리 | `PaymentEventConsumer:35-36` | `order.created`·`stock.reservation.result` 가 다른 group → 같은 주문을 동시에 처리할 수 있다 |
| 잠금 조회 | `PaymentJpaRepository:26` `findByOrderIdForUpdate` | `@Lock(PESSIMISTIC_WRITE)` 이미 있음(replay 사전조건용). domain `PaymentRepository` 에는 없음 |
| 유일 인덱스 | `V1__init_payment.sql` `uk_payments_order_id` | 미존재 조회의 잠금 읽기가 그 키 구간에 gap lock 을 건다(InnoDB RR) |
| 상태 가드 | `Payment:185` `markReadyForPayment` | 가드 없음. 적용 시점의 Payment 는 막 생성된 PENDING 이거나 취소 marker 로 CANCELLED |
| replay 사전조건 | `PaymentReplayPrecondition` | Payment 미존재 예약 결과 replay 를 거부한다. 이번에 바꾸지 않는다(새 실패가 이 이유로 DLQ 에 들어가지 않게 됨) |
| 마지막 마이그레이션 | `db/migration/V16__dead_letter_replay_contract.sql` | 새 파일은 V17 |
| ADR | ADR-0012 §D3·D4 | payment 가 예약 결과로 `ready_for_payment` 를 표시한다는 것만 정한다. 수렴 방식(재시도)은 계약이 아니다 → ADR 불요 |

범위 변화: 없음. 경합 분석 중 기존 취소 marker 경로에도 같은 경합이 있음을 발견했다(§미해결).

### 경합 설계

- 예약 결과 쪽(T1): `findByOrderIdForUpdate` 로 Payment 를 잠금 조회한다. 있으면 기존대로 `markReadyForPayment`, 없으면 marker 저장.
- 주문 생성 쪽(T2): Payment 를 저장·flush 한 뒤 예약 marker 를 잠금 조회한다(`@Lock` PK 조회). 있으면 적용하고 삭제.
- T1 이 먼저 잠그면 gap lock 이 T2 의 Payment INSERT 를 T1 커밋까지 세운다. T2 의 잠금 읽기는 커밋된 marker 를 본다.
- T2 가 먼저 INSERT 하면 T1 의 잠금 조회가 T2 커밋까지 기다린 뒤 Payment 를 찾아 직접 적용한다.
- 비용: Payment 가 없을 때만 `uk_payments_order_id` 끝 구간 gap lock 이 생겨 그동안 다른 주문의 Payment INSERT 가 기다린다.
  T1 트랜잭션은 marker INSERT 하나라 짧다. 정상 순서(Payment 존재)에서는 행 잠금만 걸린다.

## 2. 작업 항목

- [x] P1. `V17__payment_reservation_results.sql`: `payment_reservation_results(order_id PK, reservation_expires_at DATETIME(6) NULL, received_at DATETIME(6) NOT NULL)`.
- [x] P2. domain `PaymentReservationResult` 엔티티와 `PaymentReservationResultRepository`(save · existsByOrderId · findByOrderIdForUpdate · delete(엔티티)),
  infrastructure `PaymentReservationResultJpaRepository`·`PaymentReservationResultRepositoryImpl`. domain `PaymentRepository` 에
  `findByOrderIdForUpdate` 를 노출한다(JPA 메서드는 이미 있음).
- [x] P3. `handleStockReservationResult`: 잠금 조회로 바꾸고, 미존재면 marker 를 저장하고 정상 종료한다(이미 있으면 덮지 않는다). `PAY_003` 예외와 주석을 지운다.
- [x] P4. `handleOrderCreated`: Payment 저장·flush 뒤 예약 marker 를 잠금 조회한다. 취소 marker 가 있으면 CANCELLED 가 우선이고 예약 marker 는 적용하지 않고 지운다.
  없으면 `markReadyForPayment(marker 의 lease)` 를 적용하고 지운다.
  (정정 2026-11-15: 초안의 `deleteByOrderId` 는 쓰지 않는다. 파생 삭제는 먼저 스냅숏 SELECT 를 해서, T1 선잠금 순서에서
  T2 스냅숏 이후 커밋된 marker 를 못 찾고 지우지 않았다(통합 테스트가 marker 잔존 1 로 잡음). 잠금 조회로 받은 엔티티를 PK 로 지운다.
  Payment INSERT 는 IDENTITY 라 `save` 시점에 나가므로 별도 flush 는 두지 않는다.)
- [x] P5. 테스트: `PaymentEventConsumerTest` 의 PAY_003 재시도 기대를 marker 저장으로 바꾸고, order.created 의 marker 적용·취소 우선 케이스를 더한다.
  Testcontainers 통합 테스트로 경합 두 순서(T1 선잠금·T2 선INSERT)에서 Payment 가 `readyForPayment=true` 가 되고 marker 가 남지 않음을 확인한다.
- [x] P6. `docs/05-data-design.md` ERD 와 소유 테이블 설명에 `payment_reservation_results` 를 추가한다. `V1__init_payment.sql` 머리 주석은 손대지 않는다.

## 3. 검증 방법

- 통합 테스트 두 순서. 멈추는 쪽은 바깥 `TransactionTemplate` 안에서 handler 를 끝낸 뒤 커밋 전에 latch 로 선다.
  풀어 준 뒤 DB 에서 `payments.ready_for_payment=1`·`reservation_expires_at` 일치·`payment_reservation_results` 0행을 확인한다.
  - T2 선INSERT 순서: T2 가 Payment INSERT 와 marker 잠금 조회를 마치고 커밋 전에 멈춘 상태에서 T1 을 시작한다.
    false-green 대조: T1 의 조회를 비잠금 `findByOrderId` 로 바꾸면 T1 이 미존재로 보고 marker 를 남겨 실패해야 한다.
  - T1 선잠금 순서: T1 이 잠금 조회와 marker 저장을 마치고 커밋 전에 멈춘 상태에서 T2 를 시작한다.
    false-green 대조: T2 의 marker 조회를 비잠금으로 바꾸면 T2 의 스냅숏이 T1 커밋 전이라 marker 를 못 보고 실패해야 한다.
  - 각 대조는 코드를 바꿔 실패를 확인하고 되돌린다. (정정 2026-11-15: 초안은 T1 선잠금 순서가 T1 잠금을 검증한다고 적었다.
    그 순서에서는 T1 의 미커밋 marker 행 잠금이 T2 의 잠금 조회를 세워 T1 잠금 없이도 통과한다.)
- 단위 테스트: Payment 미존재 예약 결과가 예외 없이 marker 를 저장하는지, 취소 marker 와 예약 marker 가 모두 있으면 CANCELLED 이고 두 marker 가 모두 지워지는지.
- `./gradlew :payment-service:test` 와 `scripts/*-lint.sh`(특히 `integration-test-container-lint.sh`) 통과.

## 미해결

- **기존 취소 marker 경로의 같은 경합**: `handleOrderCancelled` 는 비잠금 `findByOrderId`, `handleOrderCreated` 는 비잠금 `existsByOrderId` 라
  두 group 이 겹치면 취소 marker 가 남고 Payment 가 PENDING 으로 생길 수 있다(ADR-0012 D3 취소 게이트 누수). 이번 범위 밖이다.
  취소 marker 삭제도 파생 `deleteByOrderId` 라 같은 스냅숏 문제를 가진다(P4 정정 참조).
  새 부채 행으로 올린다(`/ship` 에서 TASKS 등록).
- 고아 주문(선행 `order.created` 가 DLQ 에 남은 주문)의 예약 marker 는 적용되지 않고 남는다. 취소 marker 와 같은 성질이고 행이 작아 정리 스케줄러는 두지 않는다.
  `order.created` DLQ 를 replay 하면 그때 적용된다(만료된 lease 면 `ensureConfirmable` 이 PAY-010 으로 막는다).
- `PaymentReplayPrecondition` 의 "결제 건이 없다" 거부는 그대로 둔다. 이 변경 전에 DLQ 로 간 예약 결과 행은 기존 운영 절차를 따른다.
