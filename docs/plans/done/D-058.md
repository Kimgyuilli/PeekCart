# D-058

## 1. 명제

리스너를 켜는 통합 테스트 클래스 중 하나라도 **리스너 컨테이너가 파티션을 할당받기 전에 발행**하거나,
**발행 실패를 버려 20초 무언 timeout 으로만 드러나게** 두거나, 할당 대기 규약을 어긴 새 클래스가
CI lint 를 초록으로 통과하면 미완이다.

> 이 task 는 **CI 실패의 근본 원인을 확정하지 않는다** (§2 실측 참조). 원인 후보 2개를 선행조건으로
> 봉쇄하고, 재발하면 실패 지점이 예외로 드러나게 하는 것이 범위다.

## 2. 배경

[#164](https://github.com/Kimgyuilli/PeekCart/pull/164) CI (run 36519843378, seed 1790654636691)에서
payment `DlqIntegrationTest` 의 original timestamp 테스트가 20초 await 동안 DLT 레코드를 0건 받고 실패했다.
그 클래스는 JVM 의 첫 Kafka 통합 클래스였고 같은 클래스의 나머지 2건은 각 1.6초에 통과했다.

코드 검증(2026-09-29):

| 확인 | 결과 |
|---|---|
| consumer offset 정책 | `auto-offset-reset: earliest` (payment `application.yml:45`). 할당이 늦어도 레코드는 결국 읽힌다. 20초 동안 0건이면 할당 자체가 예산을 넘긴 것(첫 group join · `__consumer_offsets` 생성 · 토픽 발견) |
| producer 차단 한도 | `max.block.ms: 3000` · `delivery.timeout.ms: 5000`. 테스트는 `send()` future 를 버리므로 첫 발행이 메타데이터 대기로 실패해도 조용히 20초 timeout 으로만 보인다. **2차 후보 원인** |
| 토픽 소유 | payment 는 `payment.*`(+`.dlq`) `NewTopic` 만 선언한다(producer-owns-topic). `order.created`·`order.created.dlq` 는 테스트에서 자동 생성에 기댄다 |
| 할당 대기 선례 | `waitForAssignment`·`getAssignedPartitions` 사용 0건. 헬퍼 없음 |
| 같은 구조 | `app.kafka.listener.enabled=true` 인 클래스 **12개** / 4모듈 — notification 2 · order 3 · payment 5 · product 2. 클래스 순서가 매 실행 섞이므로 어느 것이든 첫 Kafka 클래스가 될 수 있다 |
| 첫 클래스만의 문제인가 | 아니다. 리스너를 켠 클래스는 `@DirtiesContext(AFTER_CLASS)` 라 매 클래스가 **같은 groupId 로 재가입**하고 rebalance 를 다시 겪는다. 첫 클래스가 가장 느릴 뿐이다 |
| 헬퍼 위치 의존성 | common `testFixturesApi` 에 `spring-kafka-test`·`awaitility` 가 이미 있다. `AbstractIntegrationTest` 에 둘 수 있다 |
| 컨테이너 게이트 | `KafkaListenerStartupConfig` 가 factory `autoStartup` 을 끈다. 켠 클래스에서는 registry 의 모든 컨테이너가 기동 상태다 |
| 규약 lint | `scripts/integration-test-container-lint.sh` 가 CI(`ci.yml:67-68`)에 배선돼 있고 `--self-test` 픽스처 구조가 있다 |

처방: 발행 전에 **자기 context 의 모든 리스너 컨테이너가 파티션을 할당받을 때까지** 기다린다.
할당이 끝났다면 토픽은 존재하고, group 은 가입했으며, 브로커 메타데이터도 준비됐다 — 두 후보 원인이 함께 제거된다.
await 연장은 증상 은폐라 택하지 않는다.

**정정 (구현 중 실측, 2026-09-29)**: 초안은 "할당 지연이 첫 테스트를 느리게 한다"를 전제로 했고 검증을
"헬퍼 없이 빨강 → 적용 후 초록"으로 잡았다. 실측이 이를 반증했다. `DlqIntegrationTest` 단독(= JVM 첫 Kafka
클래스) 2회씩, 계측 로그:

| | 할당 대기 | 첫 테스트 await | 나머지 await |
|---|---|---|---|
| 헬퍼 적용 | 105~123ms | 1949 / 2035ms | 1573~1716ms |
| 헬퍼 없음 | — | 2046 / 2509ms | 1627~2062ms |

로컬에서는 테스트 시작 시점에 할당이 이미 거의 끝나 있고, 첫 테스트가 0.4초 느린 것은 할당 때문이 아니다.
따라서 로컬에서 빨강을 재현할 수 없다. CI 의 "20초 동안 0건" 과 가장 잘 맞는 설명은 2차 후보(느린 러너에서
할당·토픽 생성 전에 발행 → producer 가 메타데이터 대기로 실패 → 버려진 future)이며, 할당 대기는 그 선행조건을
막는다. 확정은 못 하므로 발행 실패가 **예외로 드러나도록** send 를 동기화하는 P2b 를 추가했다(사용자 결정).
notification·product 는 producer 타임아웃이 기본값(`delivery.timeout.ms` 120초)이라 `join()` 만으로는 무한정에
가깝게 막힐 수 있어 `orTimeout(10초)` 로 묶는다. 기존 선례 `.get(10, SECONDS)` 는 checked 예외가 헬퍼와
호출자 시그니처로 번져 택하지 않았다.

ADR 판단: 새 외부 의존성·경계·인프라 없음 → 대상 아님. 구조 변경이 아니므로 PLAN-BLINDSPOTS 비대상.
