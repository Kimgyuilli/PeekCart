# D-092: 운영 알림 전달과 Outbox 복구 경계

## 1. 명제와 코드 근거

Grafana 운영 신호의 목적지·검증 경계, notification-service의 사용자/운영 webhook 분리, Outbox `FAILED`의 안전한 수동 재발행 조건 중 하나라도 처분과 재개 조건이 없으면 미완이다.

| 확인 항목 | 현재 코드·문서 | 계획에 미치는 영향 |
|---|---|---|
| Grafana 라우팅 | `grafana-alerts.yml`은 `signal=outbox-publish`와 `signal=dlq`를 이미 구분한다. GKE values와 alert 파일 머리는 contact point/notification policy가 없다고 밝힌다. | 새 alert 규칙은 만들지 않고 기존 label 기반 provisioning을 검증한다. |
| 앱 webhook | `NotificationCommandService`와 `NotificationKafkaConfig`가 같은 `SlackPort`를 주입받는다. 공통 `SlackNotificationClient`는 `slack.webhook.url` 하나를 사용하며 notification의 YAML은 이를 `SLACK_WEBHOOK_URL`에 연결한다. Outbox와 DLQ 공통 경로도 `SlackPort`를 호출한다. | 사용자 메시지를 운영 경로와 분리하고 공통 포트는 운영 신호에 남기는 배선을 검증한다. 다른 서비스의 명시적 no-op fallback은 유지한다. |
| Outbox `FAILED` | poller는 최대 재시도 뒤 `FAILED`로 저장하고 `findPendingEvents`는 `PENDING`만 읽는다. cleanup도 `PUBLISHED`만 삭제한다. `OutboxEvent`에는 재개 상태 전이가 없다. | 현재 자동 재시도나 수동 runbook은 없으며, 직접 운영 DB를 변경하지 않는다. |
| 재발행 중복 경계 | Kafka 전송 timeout은 실제 발행 여부가 불명일 수 있다. 도메인 payload의 `eventId`와 outbox row의 `event_id`가 중복 방지 축이지만, 재발행 안전성은 해당 이벤트의 모든 소비자 멱등성에 달려 있다. | runbook은 event별 소비자/멱등 증거가 불충분하면 중단하고 담당자에게 넘긴다. DLQ replay는 기존 ADR-0020 경로와 분리한다. |

등급 M: monitoring provisioning, notification-service 설정/배선, runbook을 함께 다루지만 이벤트·DB·HTTP 계약은 바꾸지 않고 되돌림은 이 작업의 설정·코드에 한정한다. 새 외부 의존성이나 GKE 리소스는 만들지 않는다. D-030에서 정한 `signal` label을 재사용한다. 실제 Slack 목적지와 secret 소유자는 운영자가 승인하기 전까지 미정으로 둔다. 외부 목적지·secret 배포·인프라 선택이 새 경계나 되돌리기 어려운 결정을 만들면 해당 적용 전에 ADR 필요성을 다시 판정한다.

## 2. 작업 항목

- [ ] P1. 기존 `signal` 값으로 contact point와 notification policy를 provisioning하고, credential은 저장소 밖의 Secret/environment 입력으로만 받는다. local receiver stub 검증에서 `outbox-publish`와 `dlq`가 같은 운영 receiver로 라우팅되고 default/user 경로로 새지 않는지 확인한다. PR217 한정, 50분 제한 Actions job이 기존 `verify_alerts.py --run` Grafana/Prometheus fixture를 그대로 실행하고 loopback receiver 증거를 올린다. 시작 시 counter-rate rule의 `NoData` 경쟁은 D-093 [PR188](https://github.com/Kimgyuilli/PeekCart/pull/188)의 readiness 수정에 의존한다. **Job 성공 전까지 미완료다.**
- [ ] P2. notification-service의 사용자 알림과 `SlackPort` 운영 호출(Outbox/DLQ 포함)을 서로 다른 설정·전송 경로로 분리한다. local receiver stub이 사용자와 운영 payload를 서로 다른 endpoint에서 관측하며 live endpoint 설정 없이 테스트가 통과해야 한다.
- [ ] P3. Outbox `FAILED` 수동 재발행 runbook을 작성한다. 사전 상태/복구된 broker 확인, event별 모든 소비자의 `eventId` 멱등 근거, 격리 검증, 변경 전후 기록과 중단 조건을 명시한다. SQLite fixture는 논리 가드만 대조하고, 기존 notification-service MySQL 8 CI 테스트가 같은 UPDATE/JSON 문장을 실행해 단일 행 변경과 중복 사전 거부를 확인한다. producer writer freeze와 사후 중복 확인을 요구한다. 앱 상태 전이 코드는 추가하지 않는다. `REPLAY` 행은 이 절차에서 제외하고 `docs/runbooks/dlq-recovery.md`로 보낸다. **구현과 로컬 SQL parity는 준비했지만 MySQL test가 아직 실행되지 않아 미완료로 남긴다.**
- [x] P4. 무료 검증과 실제 운영 재개 조건을 분리해 문서화한다. 무료 검증은 local stub, provisioning 형식/label route 검사, 합성 상태의 dry-run만 사용한다. 실제 Slack 전송은 담당자가 non-production 목적지·secret 주입·단일 canary 수신을 승인한 뒤에만 재개한다. 실제 `FAILED` 행 재발행은 DB 소유자의 승인, broker/topic 복구, event별 멱등성 증명과 정해진 maintenance window를 모두 요구한다.

## 3. 검증 방법

| 항목 | 검증 |
|---|---|
| P1 | `python3 -B scripts/d092-ops-fixture.py`는 정적 contact point/matcher 변이를 거부한다. PR217 전용 Actions job이 `scripts/monitoring/verify_alerts.py --run --output <tmp>`을 실행해 실제 local Grafana provisioning, 두 운영 signal 전달, loopback receiver의 signal 집합, cleanup을 검증한다. Job 전에는 P1 미완료다. 실제 Grafana/GKE 적용이나 외부 채널 성공으로 기록하지 않는다. |
| P2 | 단위/통합 테스트에 같은 synthetic 메시지를 사용자 및 운영 caller로 넣고 두 endpoint가 교차하지 않는지 stub request로 검증한다. 기본 설정 누락과 동일 endpoint 주입은 실패해야 한다. |
| P3 | `python3 -B scripts/d092-ops-fixture.py`는 SQLite에서 논리 가드와 Java integration test/runbook SQL parity를 확인한다. notification-service CI의 MySQL 8 integration test가 runbook의 UPDATE/JSON 문장과 중복 preflight를 실제 MySQL에서 실행해 단일행 변경, duplicate 사전 거부, `PENDING`/`REPLAY` 거부, event ID/payload 보존을 확인해야 한다. CI가 아직 실행되지 않아 P3 미완료다. 이는 동시 writer 제어·production lock/승인 증명이 아니다. |
| P4 | 저장소에 실 secret/실 Slack URL이 없고 검증이 외부 네트워크에 연결되지 않는지 확인한다. 외부 전달 재개 조건과 DB 재발행 조건을 서로 독립된 승인/증거로 판정한다. |

## 미해결 및 재개 경계

- 실제 Slack destinations, 사용자/운영 채널 소유자, production secret 배포 방식은 무료 stub으로 결정하지 않는다. 승인된 non-production 채널과 secret 전달 절차가 준비될 때 외부 전달 검증을 별도 재개한다.
- GKE provisioning 적용·실제 Grafana route 평가에는 승인된 클러스터 세션이 필요하다. 이 계획은 유료 인프라를 만들거나 사용하지 않는다.
- 생산 Outbox 행을 읽거나 바꾸지 않는다. runbook의 실제 실행은 DB 소유자 승인과 명시된 maintenance window가 있을 때만 별도 운영 작업으로 재개한다.
- `FAILED` 행이 broker timeout 등으로 이미 발행됐을 가능성을 배제할 수 없고 소비자 멱등성도 증명되지 않으면 같은 event를 재발행하지 않는다. 담당자 확인 및 수동 중단으로 처분한다.
