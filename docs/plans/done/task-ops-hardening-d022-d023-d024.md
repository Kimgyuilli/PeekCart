# 계획 — 운영 표면 하드닝 (D-024 · D-022 · D-023)

> D-002 측정 세션([#120])이 **밟아서** 발견한 3건. 셋 다 ADR 불필요(기존 결정을 바꾸지 않고
> 결정대로 동작하게 만드는 수정)이고 서로 독립적이라 한 PR 로 묶는다.

## 1. 명제 (부정형)

다음 중 **하나라도** 성립하면 미완이다.

- **N1** 장시간 스케줄 잡이 실행되는 동안 outbox 발행이 여전히 멈춘다.
- **N2** 키쌍이 어긋난 채 배포해도 **아무것도 실패하지 않는다**(배포 성공·Ready·로그인 200 인데
  인증된 요청이 전부 401 인 상태가 그대로 통과한다).
- **N3** infra 파드 템플릿을 바꾸는 apply 에서 신·구 파드가 **같은 datadir 을 동시에** 잡을 수 있다.
- **N4** 위 셋의 수정이 **실패를 주입한 상태에서** 검증되지 않았다.

## 2. 배경 — 착수 전 코드 검증

|---|---|---|---|
| **V1** | (D-024) order-service 의 스케줄러가 단일 스레드다 | **확증, 그리고 더 넓다.** `TaskScheduler`/`ThreadPoolTaskScheduler`/`SchedulingConfigurer` 빈이 **전 모듈 0건**이고 `spring.task.scheduling` 설정도 **전 서비스 0건** → Spring 기본 pool-size=1. 잡 수: **payment 12 · order 11 · product 8 · notification 7**(user 0) | **4개 서비스** 문제. order 만 고치면 나머지 3개가 같은 함정에 남는다 |

### 범위 변화

- **늘었다**: V1 로 D-024 대상이 order-service 1개 → **4개 서비스**.
- **바뀌었다**: V2/V3 로 D-022 가 "preflight 신설" → **"기존 검사를 실행 강제 + 원인 지목"**.
- **줄었다**: V4 로 `gke-security-smoke.sh` 자체는 **건드리지 않는다**(그 검사는 이미 옳다).

## 3. 작업 항목

### D-024 — 스케줄러 스레드 (N1)

- [x] **P1.** `spring.task.scheduling.pool.size` 를 **base `application.yml`** 에 선언한다.
  ADR-0007 기준으로 "환경마다 달라지는 값" 이 아니라 **동작 규약**이므로 프로파일이 아니라 base 다.
  대상 4개(order/product/payment/notification). 값은 **잡 수가 아니라 동시 실행 상한**으로 정하고
  근거를 주석에 남긴다.
- [x] **P2.** 풀을 키워도 **ShedLock 이 중복 실행을 막는다**는 것을 확인한다 — 잡이 병렬로 뜨는 것과
  같은 잡이 두 번 도는 것은 다르다. 기존 `lock-name` 계약이 그대로 유효한지 대조한다.

### D-022 — 배포 게이트 (N2)

- [x] **P3.** 경량 게이트 `scripts/auth-roundtrip-gate.sh` 를 만든다. **NetworkPolicy·클러스터 조회에
  의존하지 않는다** — `GW_URL` 하나로 돈다(V4).
  - (a) 로그인 → 200 + `accessToken` 존재
  - (b) 보호 경로 호출 → **200** ← 이게 게이트다
  - (c) 실패 시 **원인 지목**: 두 키 도메인(`user-jwt-public-keys` · `internal-token-keys`)의
    ConfigMap 공개키와 CSI 마운트 개인키의 **modulus 를 대조**해 어느 쪽이 어긋났는지 출력한다.
    이번 세션에서 이 진단에 40분이 들었다 — 게이트가 그 답을 바로 줘야 한다.
- [x] **P4.** 실행을 **강제**한다. 산문이 아니라 절차에 넣는다 — `k8s/overlays/gke/README.md` 의
  배포 순서에 **필수 단계**로 넣고, 측정 overlay README(`loadtest/README.md` §D-002b'/c)의
  배포 직후에도 넣는다. "돌려야 한다" 가 아니라 **"이 단계를 통과해야 다음으로 간다"** 로 쓴다.

### D-023 — RollingUpdate (N3)

- [x] **P5.** `mysql.yml`·`redis.yml`·`kafka.yml` 에 `strategy: type: Recreate` 를 선언하고,
  **왜 Recreate 인가**(RWO PVC + 단일 인스턴스 → maxSurge 가 같은 datadir 을 두 프로세스에 노출)를
  주석으로 남긴다.
- [x] **P6.** 렌더 산출에서 검증한다 — 3종 전부 `Recreate` 인지, 그리고 **다른 workload 가
  실수로 Recreate 가 되지 않았는지**(가용성 손실).

- [x] **P7.** `docs/TASKS.md` D-022/D-023/D-024 행 갱신 · `PHASE4.md` 이력 · audit.

## 4. 검증 방법

"설정을 넣었다"·"선언했다" 는 검증이 아니다. 각 항목은 **실패를 주입한 뒤 상태로** 확인한다.

| 항목 | 검증 |
|---|---|
| **P1** | **장시간 잡을 주입한다.** 테스트에서 `@Scheduled` 잡 하나를 N초 블록시키고, 그동안 **다른 잡이 실행되는지**를 실행 기록으로 확인한다. 풀=1 이면 실패하고 풀>1 이면 통과하는 테스트여야 한다 — 즉 **수정 전에 red 임을 먼저 보인다** |
| **P2** | 풀을 키운 상태에서 **같은 잡을 두 인스턴스가 동시에** 노려도 ShedLock 이 한 번만 통과시키는지. 통과 횟수를 카운트로 확인 |
| **P3** | **키쌍을 일부러 어긋나게 만든 뒤** 게이트를 돌려 **exit 1 + 어느 도메인이 어긋났는지 지목**하는지 확인한다. 정상 상태에서 exit 0 인 것만으로는 vacuous green 이다 |
| **P4** | 문서만으로는 검증 불가임을 인정한다 — **절차 문서에 단계가 존재하는지**만 확인하고, 강제력의 한계를 §6 에 적는다 |
| **P5/P6** | 렌더 산출을 파싱해 3종이 `Recreate` 이고 **나머지 workload 는 그대로**인지 대조한다. 추가로 `strategy` 미선언 workload 중 RWO PVC 를 쓰는 것이 더 없는지 스윕한다 |
