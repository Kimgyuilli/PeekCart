# D-060 작업 기록

## 2026-10-14 — 계획 및 구현 검토

- 상태: 별도 Codex 리뷰 미호출. 프로젝트 AGENTS 및 Codex용 plan/work 스킬에 따라 두 번째 리뷰어를 호출하지 않았다.
- 코드 확인: Payment의 로컬 마진/승인 원장만으로 Product release CAS를 막지 못함. Product의 기존 예약/환불 원장, Payment의 조회 전용 reconciliation 및 과금-취소 자동 환불을 재사용한다.
- 결정: 사용자가 비동기 접수(202) 후 조회를 선택했다. ADR-0034, L등급. 직접 서비스 호출은 추가하지 않았다.
- 검토 표면: 신규/기존 topic와 group, DLQ intake/quarantine, replay deny, 원장 상태/마이그레이션, HTTP 호출자와 E2E, 늦은 허가 및 refund/completed 역전, 배포/롤백 drain.
- 검증 진행: 최초 Payment 실행에서 새 통합 테스트는 통과했고 기존 상태 전이 표에 새 두 상태가 빠져 실패했다. 표를 갱신했다. 첫 전체 실행에서 구독 수의 기존 기대값 21이 실패하여 새 계약 23으로 갱신했다. 이 실패를 통과로 기록하지 않는다.
- 범위 밖: 실 Toss 호출(D-064), 전체 환불 E2E 확대(D-061), 운영 배포. 승인 결과 불명 중 강제 재고 회수는 금지한다.

## 불필요한 복잡성 재검토

- 사용자 요청에 따라 신규 파일을 포함한 운영 코드와 E2E 변경을 직접 재검토했다. 별도 Codex 리뷰 미호출.
- 유지: WAITING_STOCK/READY/CLAIMED는 각각 회신 대기/허가 커밋/외부 호출 가능성을 구분한다. 합치면 crash 이후 승인 실행과 조회 전용 복구의 경계가 사라진다.
- 유지: dispatch는 최초 승인, 기존 reconciliation은 결과 조회만 담당한다. 별도 잡은 필요하지만 공통 scheduler 프레임워크나 별도 실행 큐는 추가하지 않는다.
- 유지: approval_fenced는 기존 CONFIRMED 예약의 환불 정책을 보존한다. 제거하려면 과거 예약의 재고 복구 정책까지 변경해야 하므로 이번 범위를 넘는다.
- 유지: 일반 취소/확정 실패/성공 환불의 해제 조건은 다르다. 재고 수량 복구 본체만 restoreReleasedStock으로 공유한다. refund/completed 행 잠금은 실제 역전 경합을 위한 것이다.
- 범위 확인: 새 업무 토픽 하나와 소비 구독 두 개, 기존 outbox/원장/조회 API를 재사용한다. 신규 메시징 프레임워크, 재시도 승인, HELD TTL, 운영 API, 범용 추상화는 추가하지 않았다.
- 판단: 현재 삭제할 만한 독립적 기능이나 과도한 추상화는 찾지 못했다. 파일 수 증가는 계약 등록·회귀 검증·문서 동기화 비중이 크다. 운영상의 비용(비동기 지연, 미확정 재고 보유, 전환 시 drain)은 실제로 남으며 단순한 변경이라고 평가하지 않는다.
- 검증 진행 중: 전체 회귀의 Order 모듈은 Kafka 컨테이너 초기화 실패로 재검증이 필요하며, E2E는 아직 완료되지 않았다. 이 검토는 테스트 통과나 외부 리뷰 승인을 의미하지 않는다.

## CI 검증으로 이전

사용자가 CPU 99% 상태를 알리고 CI 검증을 요청했다. 로컬 전체 테스트는 중단했고 E2E는 앱 health 기동 시간 초과로 종료됐다. 완료용 ship preflight는 미완 계획 항목으로 blocked였으며 이를 통과로 기록하지 않는다. 사용자 지시에 따라 검증용 Draft PR을 생성하고 최종 완료 판정은 CI 결과 이후로 남긴다. 문서 consistency precheck는 통과했다.
