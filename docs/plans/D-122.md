# D-122 — 운영 overlay Kafka 볼륨 크기

## 1. 명제
아래 중 하나라도 성립하면 미완이다.
- `gke` 또는 `minikube` overlay 를 렌더하면 `kafka-pvc` 가 base 1Gi 다.
- 그 크기가 이 계획서의 산정 표 상한(아래 §산정)을 담지 못한다.
- 다른 overlay 의 렌더가 main 과 달라진다.
- 배포 래퍼(`scripts/deploy-overlay.sh`)가 먼저 만드는 kafka PVC 에 overlay 크기가 빠져 있어도 테스트가 통과한다.

사용자 결정(2026-11-19): PVC 를 키운다. 시간 기준 7일 보존은 유지하고 크기 기준 브로커 보존(`log.retention.bytes`)은 넣지 않는다(ADR-0020 의 DLQ replay 안전창 7일 전제). 크기는 이 계획서가 산정한다.

### 등급 근거 (M)
- 모듈: `k8s/overlays/gke`·`k8s/overlays/minikube` 와 그 테스트. 한 영역이다.
- 계약 표면: PVC 크기를 읽는 코드나 설정 키가 없다. 배포 래퍼는 렌더 결과를 그대로 적용한다.
- 되돌림: 파일 되돌리기로 끝나지 않는다. PVC 는 줄일 수 없어 1Gi 로 되돌리려면 클러스터에서 PVC 를 지우고 다시 만들어야 한다(Kafka 데이터 유실). 셋 중 하나에 걸리므로 M 이다.
- ADR: 새 외부 의존성, 경계 변경, 새 인프라가 없다. 되돌릴 때 고칠 파일도 이 PR 의 patch 뿐이다. ADR 은 쓰지 않는다. ADR-0020 §D4-2·§Consequences 가 후속으로 남긴 "내부 토픽 bound 와 PVC 증설" 중 PVC 증설을 이 작업이 다룬다. ADR 본문의 1Gi 서술은 작성 시점 사실이라 Update Log 대상이 아니다.

TASKS 행의 "세그먼트 1GiB, 크기 기준 보존 없음"은 브로커 기본값 기준이다. 선언 토픽 30개는 토픽 config 로 이미 크기가 묶여 있다. 묶이지 않는 것은 `__consumer_offsets`, KRaft metadata 로그, 그리고 선언 config 를 받기 전의 자동 생성 토픽이다. 범위는 바뀌지 않는다(크기만 정한다).

### 산정
로컬 실측(2026-11-19, `apache/kafka:3.8.1`, base env 그대로):
- KRaft metadata 로그: 유휴 브로커에서 120초 동안 17,208 바이트, 초당 143 바이트. 7일이면 약 83MiB.
- offset 커밋 1건: `kafka-dump-log` 로 본 배치 크기 153 바이트(그룹 `order-svc-payment-completed-group`, 토픽 `payment.completed`, 1,164건 모두 같은 크기). 이름이 더 긴 그룹은 몇십 바이트 크다.
- 인덱스 파일: 활성 세그먼트의 `.index`·`.timeindex` 는 10MiB 로 잡히지만 실제 할당은 4KiB 였다(sparse).

가정:
- A1. 최대 유입은 프로젝트가 GKE 에서 낸 초당 170 주문(docs/07-roadmap-portfolio.md)이다. `gke` overlay 는 부하 시험에도 쓰인다.
- A2. 정상 경로 주문 하나는 레코드 5개(`order.created`, `stock.reservation.result`, `payment.requested`, `stock.approval.result`, `payment.completed`)를 쓰고, 구독 그룹 수를 더하면 offset 커밋 11건을 만든다.
- A3. 레코드 하나는 헤더와 배치 오버헤드를 합쳐 1KiB 이하다(실측 아님).
- A4. log cleaner 가 정상 동작한다. compact 는 닫힌 세그먼트만 줄인다.

| `.dlq` 토픽 | 15 파티션 x (4MiB + 2MiB) | 90MiB |

`__consumer_offsets` 가 가장 크다. A1 의 최대 유입에서 `order.created` 를 구독하는 그룹의 파티션은 초당 170건 x 153 바이트로 약 1시간 만에 100MiB 활성 세그먼트를 채운다. 부하 세션 몇 번이면 쓰이는 파티션마다 100MiB 가 남을 수 있다. 상한을 지금 쓰는 24 파티션이 아니라 50 파티션으로 잡은 이유는 그룹이 늘어도 상한이 변하지 않게 하기 위해서다.

| overlay | 크기 | 사용 가능(ext4) | 여유 | 근거 |
|---|---|---|---|---|
| `gke` | 10Gi | 약 9.8GiB(10Gi 볼륨의 실측 `df` 10,283,868KiB) | 약 3.8GiB(ext4 예약 블록 5% 를 빼도 3GiB 이상) | 합계 상한 6.0GiB. 5Gi(약 4.9GiB)는 상한보다 작다. 측정 overlay 와 같은 크기이고 pd-balanced 10GiB 비용은 월 1달러 안팎이다 |
| `minikube` | 2Gi | hostpath 라 강제하지 않는다 | | 부하 시험을 돌리지 않는다(docs/01-project-overview.md: 부하·HPA 는 GKE). 선언 토픽 630MiB 와 metadata 200MiB 를 빼면 offset 커밋에 약 1.2GiB 가 남는다. 커밋 170 바이트 기준 약 750만 건, 주문 약 68만 건이다. 로컬 수동 검증과 E2E 규모를 크게 넘는다. 실제 한도는 minikube 노드 디스크(기본 20GB)다 |

세그먼트 크기 판단: 바꾸지 않는다.
- 업무·`.dlq` 토픽은 토픽 config 로 이미 4MiB·2MiB 다. 브로커 `log.segment.bytes` 1GiB 는 config 를 받기 전의 자동 생성 토픽에만 적용된다(ADR-0020 Update Log 의 D-106 ⑩ 경로). KafkaTopicReconciler 가 다시 맞추고, 그 사이 유입은 `gke` 여유 3.8GiB 안에 든다.
- `offsets.topic.segment.bytes` 를 예컨대 10MiB 로 줄이면 offsets 상한이 500MiB 로 준다. 그러나 이 값은 `__consumer_offsets` 를 만들 때만 적용되어 이미 있는 클러스터는 `kafka-configs --alter` 로 내부 토픽을 고치는 별도 절차가 필요하다. 브로커 설정이라는 새 계약 표면도 생긴다. 사용자 결정(PVC 증설)으로 상한을 담을 수 있으므로 채택하지 않는다. 재검토 조건은 §미해결.

### 배포 순서
- `gke`, 기존 클러스터: `scripts/deploy-overlay.sh k8s/overlays/gke` 그대로다. kafka 선행 적용이 PVC 요청을 10Gi 로 바꾸면 PD CSI 가 디스크를 키우고 kubelet 이 파일시스템을 온라인으로 늘린다. 확인: `kubectl -n peekcart get pvc kafka-pvc -o jsonpath='{.status.capacity.storage}'` 가 10Gi, `kubectl -n peekcart exec deploy/kafka -- df -k /var/lib/kafka/data` 의 크기가 약 10,283,868KiB.
- `gke`, 새 클러스터: 처음부터 10Gi 로 만든다.
- `minikube`, 기존 클러스터: kafka 선행 적용이 거부되어 래퍼가 exit 1 로 멈춘다(앱은 적용하지 않는다). `kubectl -n peekcart delete deploy/kafka pvc/kafka-pvc` 뒤 래퍼를 다시 돌린다. 토픽은 래퍼가 다시 만들고 offset 과 메시지는 사라진다. 로컬 데이터라 감수한다. D-114 전에는 Kafka 가 컨테이너 저장소에 써서 Pod 재시작마다 같은 유실이 있었다.
- `minikube`, 새 클러스터: 처음부터 2Gi 로 만든다.

### 롤백
PVC 는 줄일 수 없다. 이 PR 을 되돌린 매니페스트(1Gi)를 적용하면 API 서버가 거부하고 래퍼가 kafka 선행 적용에서 멈춘다. 그래서 `gke` 롤백은 매니페스트를 되돌리지 않고 10Gi 를 유지하는 것이다. 1Gi 로 꼭 돌아가야 하면 Kafka Deployment 와 PVC 를 지우고 다시 만들어야 하고, 토픽·offset·DLQ 원본 레코드가 사라진다(ADR-0020 replay 좌표를 잃는다). 그 경우 DLQ 원장에 replay 대기 행이 없는지 먼저 확인한다. `minikube` 는 배포 순서와 같은 재생성 절차다.

## 3. 검증 방법
- V1(P1·P2) 렌더 대조: 모든 overlay 를 main 과 이 브랜치에서 렌더해 diff 한다. `gke`·`minikube` 는 kafka-pvc 의 `storage` 한 줄만 달라야 하고 나머지 overlay 는 diff 가 없어야 한다.
- V2(P3) 실패 주입: `gke` patch 를 1Gi 로 바꾸거나 `minikube` kustomization 에서 patch 를 빼면 `test_every_app_overlay_brings_up_its_own_kafka_first` 가 실패해야 한다. 되돌리면 통과한다.
- V3 공통: `python3 scripts/tests/test_deploy_overlay.py`, `.github/workflows/ci.yml` 의 `Run CI policy lints` 블록 전부, `scripts/*-lint.sh` 전부.
- GKE 실환경 확장과 minikube 거부 동작은 클러스터에 적용하지 않는다(이번 범위). GKE 는 위 2026-10-25 확장 기록, minikube 는 바이너리의 SC 정의로 갈음하고 다음 배포에서 배포 순서의 확인 명령으로 본다(§미해결).

## 미해결
- GKE 다음 배포에서 확장 결과를 확인한다(배포 순서의 두 명령). 처분: 다음 과금 세션 첫 배포.
- A1~A3 은 실측이 아니다. D-114 의 `d078-s3-run.sh` 가 run 마다 Kafka 볼륨 여유를 남긴다. 처분: 다음 측정 세션 기록으로 run 당 증가량을 보고, 산정 표의 보존 검사 사이 유입·offsets 항목과 크게 다르면 다시 산정한다.
- `offsets.topic.segment.bytes` 축소는 채택하지 않았다. 재검토 조건: 10Gi 가 비용이나 노드 제약으로 부담이 되거나, 실측한 offsets 점유가 상한 5,000MiB 에 가까워질 때.
- `gke-d002a` 계열과 `gke-d078-read-bulkhead-4` 의 kafka-pvc 는 1Gi 로 둔다. D-114 처분과 같다(장시간 세션을 계획하면 B14 점검에서 다룬다).
- ADR-0020 §D4-2 의 7일 좌표 가용은 여전히 보장이 아니다. 업무 토픽은 `retention.bytes` 8MiB 가 먼저 지울 수 있고, 이 작업은 볼륨이 차서 브로커가 멈추는 경로만 줄인다.
