# task-d041-fault-injection-boundary

e2e 결함 주입을 결정적으로 제어할 경계 설계 (D-041, ADR-0028 §후속 ① 의 후속)

## 1. 명제

다음 중 하나라도 성립하면 미완이다.

- 음성 대조군 각각이 검증한다고 주장하는 불변식, 주입 수단, 실패 지점 특정 여부, 소요가 한 표로 남아 있지 않다
- 대조군이 **의도한 지점이 아닌 곳의 실패**를 통과로 받는다 (현재 ②, 그리고 `expect_fail` 전반)
- 결함 주입 경계(무엇을 어디서 제어하는가, 무엇은 제어하지 않는가)가 ADR 로 결정되지 않았다
- 그 경계에서 결함을 주입하면 의도한 검사가 실패하고, 정상 경로는 통과하며, **엉뚱한 지점의 실패는
  대조군이 거부한다**는 증거가 없다
- 기존 실제 스택 대조군 6종 중 하나라도 제거됐다 (D-042 판정 전까지 유지)

## 2. 배경

### 2-1. 코드 확인 (착수 전, 2026-09-28)

대조군 소요는 D-033 실측 run [36075940872](https://github.com/Kimgyuilli/PeekCart/actions/runs/36075940872)
`e2e (negative-control)` 잡 로그의 타임스탬프로 분해했다. `durations.tsv` 는 대조군 전체(461초)만 기록한다.
TASKS 행의 605초는 ADR-0028 시점(D-032 이전) 값이다.

| # | 대조군 | 주입 수단 | 소요 | 시간이 쓰이는 곳 | 실패 지점 특정 |
|---|---|---|---|---|---|
| ① | poller 정지 → A 실패 | ShedLock 행을 1시간 뒤로 선점 (`saga-e2e-smoke.sh:345`) | 186초 | A 의 예약 대기 `DEADLINE` 180초 | 안 함. `expect_fail` 이 아무 실패나 받는다 (`:300`) |
| ② | product-service 정지 → A 실패 | `dc stop` | **1초** | 없음 | **안 함, 그리고 공허하다.** A 첫 줄 `create_product` 가 product-service admin API 를 불러 거기서 죽는다 (`saga_e2e.py:274`). 주장한 불변식 "예약이 성립하지 않는다" 에 닿지 않는다 |
| ④ | listener 부재 → readiness 실패 | ②의 정지 상태 재사용 | 181초 | group 검사 `wait_for` 180초 (`saga_e2e.py` `check_readiness`) | **함.** `consumer group` 사유가 아니면 실패 (`:792`) |
| ③ | 재고 충분 → B 실패 | 재고 100 으로 주문 | 49초 | 취소 부재 45초 대기 | 함. 취소가 오면 실패 |
| ⑥ | egress 양·음 | canary 컨테이너, curl rc | 2초 | — | 함. rc 7/28 만 음성으로 인정 |
| ⑤ | project 병렬 기동 | 두 번째 compose project | 21초 | 인프라 기동·정리 | 해당 없음 (충돌 유무) |

- 고정 대기 3개(①180 + ④180 + ③45 = 405초)가 461초의 88% 다. 모두 "일어나지 않음" 을 상한 대기로 증명한다
- 기존 제어 경계: pg-stub 의 paymentKey 접두사별 불변 script(외부 응답), ShedLock 행 선점(poller),
  `app.scheduling.enabled`·`app.kafka.listener.enabled` 토글(ADR-0029, 테스트 전용 기본 off)
- 서비스 코드에 `Clock` 주입이 없다(`InternalTokenIssuer`·`InternalTokenVerifier` 만). 시간은 제어 불가
- ⑤·⑥ 은 compose 토폴로지 자체가 대상이라 스택 밖 경계로 옮길 수 없다. 이번 경계 설계의 대상은 ①②③④ 다

### 2-2. 범위 결정 (사용자, 2026-09-28)

- 기존 대조군은 **검출력 결함만 고친다.** 6종 모두 유지하고, 새 경계는 옆에 추가해 증거를 만든다
- 고정 대기 단축은 ADR 결정을 따른다. 대조군 제거와 JVM 계약 테스트로의 이동은 D-042 몫이다

### 2-3. ADR 선행 판단

ADR 이 필요하다(TASKS 행이 요구하고, 테스트 제어 경계는 서비스·스크립트 양쪽에 걸친다).
다만 ADR 의 입력이 P1 목록이라 계획보다 먼저 쓸 수 없다. P2 에서 쓴다.

## 3. 작업 항목

- [ ] P1. 대조군 목록 확정. §2-1 표를 `docs/06-testing-strategy.md` 의 e2e 절(§13-1-a 인접)로 옮기고
      각 행에 "주장하는 불변식" 을 한 문장으로 고정한다. 이 표가 D-042 의 입력이 된다
- [ ] P2. ADR-0031 작성. 결정할 것:
      (a) 실패 지점 특정을 어디서 하는가 — runner 가 단계 식별자를 내고 대조군이 그것을 대조하는 방식이 기본안
      (b) "일어나지 않음" 의 대기 상한을 무엇으로 정하는가 — 고정 180초 대신 주입 성립의 양성 관측 +
          시스템 자신의 주기(poller 주기, consumer 세션)에서 유도한 창. 유도 근거가 없으면 고정값 유지
      (c) 서비스 쪽 테스트 제어 표면(poller 일시정지 엔드포인트, `Clock` 빈 등)을 두는가 — 기본안은
          **두지 않는다.** 프로덕션 이미지에 테스트 우회 경로를 싣지 않는다. 필요가 입증되면 그 조건을 적는다
      대안 비교와 기각 사유를 포함한다
- [ ] P3. runner 에 실패 단계 식별 도입 (`saga_e2e.py`). 시나리오가 어느 단계에서 실패했는지를
      종료 출력에 구조화해 남긴다. 기존 시나리오 판정(성공·실패)은 바꾸지 않는다
- [ ] P4. `expect_fail` 을 실패 지점 대조형으로 교체 (`saga-e2e-smoke.sh`). ① 은 "예약 대기 타임아웃" 단계만 통과로 받는다
- [ ] P5. ② 를 불변식에 닿게 재구성. 상품 생성·단가 캐시를 product-service 가 살아 있을 때 마치고,
      정지 후 주문을 넣어 **예약 단계**에서 실패함을 대조한다. ④ 가 ② 의 정지 상태를 재사용하는 구조는 유지한다
- [ ] P6. P2 (b) 가 창 유도를 채택한 대조군에 한해 대기 상한 교체. 채택이 없으면 이 항목은 기록만 하고 닫는다
- [ ] P7. `docs/TASKS.md` D-041 행 갱신, D-042 행에 P1 표 위치 참조 추가

## 검증 방법

실패 지점 특정이 핵심이므로 **정상 주입, 엉뚱한 주입, 무주입** 세 쪽을 모두 본다.

| id | 주입 | 기대 | 확인 |
|---|---|---|---|
| V1 | 정상 실행(`--scenarios a,b,c,d`) | 시나리오 4종 통과, 단계 식별 도입 전후 판정 동일 | 증적 manifest `result=success` |
| V2 | `--negative-control` | 6종 전량 `ok` | 스크립트 종료 코드 0, 출력 |
| V3 | ① 에서 ShedLock 선점 대신 pg-stub 을 정지(엉뚱한 지점 실패) | ① 이 **FAIL** 을 낸다 | 대조군 출력에 실패 단계 불일치 사유 |
| V4 | ② 재구성 후, 정지 대상을 product-service 가 아닌 서비스로 바꿔 A 가 다른 단계에서 실패하게 한다 | ② 가 **FAIL** | 동일 |
| V5 | ② 재구성 후 product-service 를 멈추지 않는다(무주입) | ② 가 **FAIL** (결함이 없는데 통과하면 안 된다) | 동일 |
| V6 | P6 을 적용했다면, 창 유도 근거인 주기 설정을 창보다 길게 바꾼다 | 해당 대조군이 FAIL 또는 명시적 "관측 불가" 로 실패 | 출력 |
| V7 | PR CI | `e2e (scenarios)`·`e2e (negative-control)` 성공, 대조군 소요를 D-033 461초와 대조 | run 로그 |

V3~V6 은 로컬에서 스크립트를 임시 수정해 돌리고 원복한다. 원복은 `git diff` 로 확인한다.

## 완료 조건

- P1~P7 체크, ADR-0031 Accepted
- V1~V5 (P6 적용 시 V6) 결과를 계획서 §검증 기록에 남긴다
- 대조군 6종 유지(제거 0)
- V7 대조군 소요 전후 수치 기록. 단축은 완료 조건이 아니다. 늘어났다면 그 사유를 적는다(② 재구성은 대기를 하나 추가할 수 있다)

## 미해결

- 대조군의 JVM 계약 테스트 이동, 실제 스택 대조군 축소 → D-042
- 시간 제어(`Clock` 주입)가 필요한 결함(주문 만료·리스 만료 잡)은 현재 대조군에 없다. P2 (c) 에서 필요성만 판정하고
  도입은 하지 않는다
- 계획 리뷰: 의도적 생략(file: 사용자 지시 2026-09-22, Codex 리뷰를 호출하지 않는다)
