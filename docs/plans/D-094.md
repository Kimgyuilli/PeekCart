# D-094: Redis 조회 상한 실패 진단 정정

## 명제

V3의 3500ms 상한 실패만으로 timeout 변경을 원인으로 단정하거나, 실제 client timeout·경로 증가분·실측 경과를 함께 확인할 수 없으면 미완이다.

기준 코드 `af60cd6d9dceac541b6f457062093df70753f3ce`. product base는 Redis timeout 500ms를 선언한다. V3는 downstream 무응답 toxic 아래 전체 getProduct 경과를 재며 3500ms 미만과 product/productStock get·put 증가분을 각각 검사한다. 기존에는 시간 단언이 먼저 실패하면 아래 경로 카운터 결과가 나오지 않는다. 실제 spring-data-redis 3.5.10 jar의 javap로 LettuceConnectionFactory.getClientConfiguration().getCommandTimeout() API를 확인했다.

등급 S: 단일 모듈 테스트 진단과 관련 runbook만 바꾼다. bound·production timeout·장애 주입 방식·ADR 결정은 바꾸지 않는다.

## 작업 항목

- [x] P1. 측정 종료 직후 client timeout과 4개 fallback 증가분을 기록하고 시간·경로 단언에 같은 관측값을 붙인다. 단정 대신 가능한 원인과 계측 한계를 설명한다.
- [x] P2. Redis runbook에 상한 실패의 해석과 확인 순서를 기록한다.
- [x] P3. 정상 V3와 500ms+1800ms 인위 지연/timeout 1s 변이를 실제 실행한다. 정상은 기존 bound 통과, 두 변이는 같은 bound 실패와 서로 다른 timeout 관측을 보여야 한다.

## 검증

focused V3 원본 실행 뒤 임시 변이로 측정 구간에 1800ms 지연만 주입하고 실패 XML의 elapsed·commandTimeout=500ms·4개 delta를 확인한다. 별도 변이는 test property timeout=1s만 추가하고 commandTimeout=1000ms 및 같은 bound 실패를 확인한다. 변이를 복구한 원본 focused 실행과 diff-check/관련 lightweight lint를 확인한다. 전체 CI는 PR로 확인한다. 각 관측은 isolated timing probe이며 부하나 원인 분해 실험으로 표현하지 않는다.

## 미해결

실클러스터 부하 재현, Redis/DB/JVM 시간 기여의 분해, production timeout 정책 변경은 범위 밖이다. C가 heavy slot을 사용하는 동안 Gradle/Docker 실행을 보류한다. D-102의 같은 클래스 주석 변경은 별도 PR로 유지하며 전체 branch를 가져오지 않는다. TASKS/PHASE/ADR index는 root가 관리한다.

## 검증 결과

2026-10-21 focused V3: baseline 2075ms 통과 → 500ms 유지+1800ms 지연 3885ms 예상 bound 실패 → timeout1s 4070ms 예상 bound 실패 → restored 2056ms 통과. 각 1test/errors0, 모든 관측의 product/productStock get·put delta는 1.0이었다. 두 negative 모두 시간 단언의 AssertionError이며 본래 3500ms를 유지했다. 원본 복원 source hash도 일치했다. [명령·변이·선택 XML 근거](evidence/D-094/README.md)에 보존했다.

전체 `./gradlew test`는 로컬에서 실행하지 않았고 PR 전체 CI로 확인한다. 별도 Codex 리뷰 미호출.
