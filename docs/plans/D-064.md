# D-064 Toss 테스트 환경 실호출 검증: 승인·조회·취소와 중복 응답

> 2026-10-25 사용자 결정으로 보류를 좁혀 연다. 승인·조회·취소를 실제 Toss 테스트 환경으로 부르고, 중복 승인·중복 취소에 Toss
> 가 실제로 무엇을 돌려주는지 보고, stub·mock 가정과의 차이를 기록한다. 웹훅 외부 수신과 운영 수준 checkout 통합은 범위 밖이다(§7).

기준: 2026-10-25, main `a0617b7`. 보류 사유와 이전 진행(#193, #196)은 TASKS D-064 행.

## 1. 명제

다음 중 하나라도 성립하면 미완이다.

- PeekCart 의 승인(`ApprovalExecutor.execute` 에서 `TossPaymentClient.confirm`)과 환불(`RefundExecutor.execute` 에서
  `TossPaymentClient.cancel`)이 Toss 테스트 환경에서 한 번도 실제로 성공하지 않았다. 원장(`payment_approvals`, `payment_refunds`)
  의 종결 상태와 원장에 남은 응답 원문으로 판정한다.
- 조회, 같은 멱등키의 승인 재요청, 다른 멱등키의 승인 재요청, 같은 멱등키의 취소 재요청, 다른 멱등키의 취소 재요청에 대해 Toss 가
  실제로 돌려준 상태 코드와 본문이 기록돼 있지 않다.
- 클라이언트가 가정한 응답(§2 의 응답 분류 가정과 승인 확정 조건)과 실제 응답의 차이가 표로 남아 있지 않다.
- 실제 응답이 테스트로 고정되지 않아, 이후 클라이언트를 고쳐 실제 응답의 분류가 깨져도 CI 가 잡지 못한다.
- 테스트 키가 추적 파일이나 커밋 메시지, PR 본문에 들어간다.

배경: E2E 는 PG stub(`scripts/e2e/pg-stub/stub.py`)으로, JVM 테스트는 `MockRestServiceServer` 로 Toss 를 흉내낸다. Toss 는 이메일
가입만으로 개발 연동 체험 상점의 API 개별 연동 키(`test_ck_` 와 `test_sk_`)를 준다. 사업자 등록은 전자결제 신청 단계에서 필요하다.
이 키로 쓸 수 있는 결제창은 구버전 `payment()` 이고, 주문서형·결제창형 위젯 키는 전자결제 신청 뒤에만 나온다. 인증 뒤 서버가 부르는
승인·취소·조회 API 는 결제창 종류와 무관하게 같다. 결제창 페이지는 실호출을 일으키기 위한 검증 도구이고 제품 화면이 아니다.

정정(대화 중 제안 대비): 앞서 "중복 승인 확인이 D-059 와 이어진다"고 했으나, D-059 는 환불 재시도의 409
`IDEMPOTENT_REQUEST_PROCESSING` 이다. 그래서 중복 취소 응답도 범위에 넣는다. 조회는 승인 직후(`DONE`)와 취소 직후(`CANCELED`)에 한
번씩 부른다. 승인 쪽 조회 분기(`ApprovalExecutor.verifyByQuery`)와 취소 쪽 합계 판정이 서로 다른 상태의 본문을 읽기 때문이다.

정정(2026-10-26 실행 중): 위 배경의 키 설명은 Toss 문서 기준이었고 실제와 달랐다. 처음 넣은 API 개별 연동 클라이언트 키(`test_ck_`)로
결제창(`payment()`)을 열자 결제창 열기 요청(`px-payment-parameters`)이 401 이었다. 사용자가 개발자센터에서 확인한 결제위젯 연동 키
(`test_gck_`, `test_gsk_`)는 시크릿 키로 없는 결제를 조회했을 때 404 `NOT_FOUND_PAYMENT` 로 인증을 통과했다. 그래서 검증 도구의 결제창을
결제위젯 SDK(`widgets()`, 공식 샘플 `tosspayments-sample` 의 주문서형 순서)로 바꿨다. 서버가 부르는 승인·취소·조회 API 와 PeekCart 경로는
같다.

| stub 의 응답 | `stub.py` | 승인 성공은 `paymentKey`, `orderId`, `totalAmount`, `status`, `method`(`간편결제`), `approvedAt`(`+09:00`) 만 준다. 취소 중복은 400 `ALREADY_CANCELED_PAYMENT`. 승인 중복 응답은 흉내내지 않는다 |

Toss 문서에서 확인한 것: 같은 멱등키 재요청은 첫 응답을 그대로 돌려주고, 첫 요청이 처리 중이면 409 `IDEMPOTENT_REQUEST_PROCESSING`
이며, 키는 15일 유효하다. successUrl 에는 `paymentKey`, `orderId`, `amount` 가 온다. `test_*` 키는 실제 출금이 없다. 문서용 공개 테스트
키로 만든 결제는 코어 API 로 조회되지 않는다는 보고가 있어 체험 상점 키를 쓴다. PeekCart 는 승인에 같은 멱등키를 쓰므로, 같은 키로
승인을 다시 보내면 `ALREADY_PROCESSED_PAYMENT` 가 아니라 첫 성공 응답이 다시 올 것으로 예상한다. 실행으로 확인한다.

## 4. 실행 절차 (P2)

준비(사용자):

1. 토스페이먼츠에 이메일로 가입하고, 개발자센터 API 키 메뉴에서 결제위젯 연동 키 두 개(클라이언트 키 `test_gck_`, 시크릿 키
   `test_gsk_`)를 확인한다. 한 세트로 쓴다(섞으면 `INVALID_API_KEY`). 정정 전에는 API 개별 연동 키라고 적었다(§1 정정).
2. `.cache/toss-sandbox.env` 를 편집기로 만든다. 줄은 `TOSS_CLIENT_KEY=...` 와 `TOSS_SECRET_KEY=...` 두 개다. 키를 대화나 명령줄에
   붙여 넣지 않는다.

스택:

3. 루트 compose 파일을 검증 전용 프로젝트(`docker compose -p peekcart-toss-sandbox`)로 띄워 MySQL·Redis·Kafka 를 새 볼륨에서
   시작한다. 기존 로컬 볼륨은 서비스별 DB 계정이 생기기 전에 초기화돼 있어 쓰지 않는다(2026-10-26 실측, §2 로컬 스택 행).
4. product(8082), order(8081), payment(8083)를 local 프로필로 직접 실행한다. 세 서비스 모두 `APP_INTERNAL_TOKEN_MODE=DUAL_ACCEPT`,
   payment 는 env 파일의 `TOSS_SECRET_KEY` 와 `APP_REFUND_DISPATCH_INTERVAL_MS=2000`(e2e 와 같은 이름과 값)을 받는다.

결제 1건:

5. `sandbox.py serve` 로 결제창 페이지와 successUrl·failUrl 을 localhost 에 띄운다.
6. `sandbox.py prepare`: 상품 생성(admin API), order-service 단가 캐시 대기, 장바구니와 주문, 예약 대기, `prepare` 로 PG 주문 ID 와
   금액을 받아 결제창 주소를 출력한다.
7. 사용자가 브라우저에서 결제창을 한 번 통과한다. 결제수단은 신용·체크카드만 쓴다. 간편결제는 테스트 키여도 실제 앱과 계정으로 이어져
   충전 같은 부수 동작이 생긴다(2026-10-26 카카오페이로 시도해 사용자 지갑에 실제 충전이 일어났다. 승인 API 는 부르지 않아 결제는
   성립하지 않았다). 카드사 인증 창은 팝업이라 브라우저 자동화 탭에서는 열리지 않고 `USER_CANCEL` 로 끝났다. successUrl 이 받은 `paymentKey`, `orderId`, `amount` 를
   run 디렉터리에 적는다.
8. `sandbox.py confirm`: successUrl 값이 prepare 의 PG 주문 ID 와 금액과 같은지 보고 PeekCart `confirm` 을 부른다. 승인 원장과 결제가
   종결될 때까지 기다린다. successUrl 도착 뒤 바로 실행한다(인증 뒤 승인 시한이 있다).
9. `sandbox.py probe-confirm`: Toss 를 직접 부른다. 조회 1회(`DONE`), 같은 멱등키(`approve-{orderId}`) 승인 재요청, 다른 멱등키 승인
   재요청.
10. `sandbox.py refund`: 그 주문에 `order.compensation.requested`(사유 `PAID_BUT_CANCELLED`)를 넣고 환불 원장이 종결되고
    `payment.refunded` 가 발행될 때까지 기다린다.
11. `sandbox.py probe-cancel`: 같은 멱등키(`refund-{orderId}`) 취소 재요청, 다른 멱등키 취소 재요청, 조회 1회(`CANCELED`).
12. 서비스를 내리고 검증 전용 compose 프로젝트를 볼륨째 지운다. 키 파일은 사용자가 지운다(선택).

## 5. 중단 규칙

- 키 오류(`INVALID_API_KEY`, `UNAUTHORIZED_KEY`)가 나면 멈추고 사용자에게 키 세트를 확인받는다. 다른 키로 바꿔 끼우지 않는다.
- 로컬 스택이 서지 않으면 원인을 기록한다. 원인이 실행 방법(포트, env)이면 절차를 고치고 계속하고, 제품 코드나 설정 파일을 고쳐야 하면
  멈추고 사용자와 처분을 정한다.
- 승인이나 환불 원장이 종결되지 않거나 기대와 다른 상태로 닫히면 그 상태와 응답 원문을 남기고 멈춘다. 그 자체가 P5 의 입력이다.
- 결제창은 최대 두 번까지 다시 연다. 그래도 인증이 안 되면 멈춘다.

## 6. 검증 방법

| 항목 | 확인 | 실패 주입 |
|---|---|---|
| 승인 실호출 | `payment_approvals` 종결 상태가 성공이고 원장의 응답 원문 `paymentKey`, `orderId`, `totalAmount` 가 prepare 값과 같다. 결제 상태가 승인이다 | P3 테스트에서 실제 승인 본문의 `totalAmount` 나 `orderId` 를 바꾸면 식별자 대조가 거짓이 되고 승인 확정이 미확정으로 바뀐다 |
| 환불 실호출 | `payment_refunds` 가 `SUCCEEDED`, `payment.refunded` outbox 가 발행됐다. 원장 원문의 `cancels` 합계가 결제 금액과 같다 | P3 테스트에서 실제 취소 본문의 `cancelAmount` 를 줄이면 전액 취소 판정이 거짓이 된다 |
| 재요청 분류 | 실제 본문의 상태 코드와 `code` 로 `TossOutcome` 분류가 기대값(같은 키는 첫 응답 재사용, 다른 키는 "이미 처리됨")과 같다 | 실제 본문의 `code` 를 다른 값으로 바꾸면 분류 테스트가 실패한다. stub 본문으로 바꿔 끼우면 실제 응답에만 있는 필드를 보는 단언이 실패한다 |
| 조회 해석 | `find` 가 실제 `DONE` 본문에서 상태와 취소 합계 0 을, `CANCELED` 본문에서 전액 취소를 낸다 | `cancels` 를 비우면 전액 취소 판정이 거짓이 된다 |
| 키 비노출 | 추적 파일, 커밋 메시지, PR 본문에 `test_ck_` 나 `test_sk_` 로 시작하는 값이 `test_sk_placeholder` 말고 없다 | 가짜 키 문자열을 임시 추적 파일에 넣으면 같은 검사가 잡는다 |
| 회귀 | `./gradlew :payment-service:test`, 관련 lint(`scripts/*-lint.sh`) | 해당 없음 |

## 7. 범위 밖과 미해결

- 웹훅 외부 수신: 공개 주소가 필요하다. ADR-0041 상 일반 결제 웹훅은 서명 없는 힌트이고 서버 조회만 신뢰한다.
- 운영 수준 checkout: 주문서형·결제창형 위젯은 전자결제 신청 뒤에만 키가 나온다.
- 409 `IDEMPOTENT_REQUEST_PROCESSING` 의 실제 재현: 첫 요청이 처리 중이어야 해서 결정적으로 만들 수 없다. D-059 분류는 문서 기준 그대로 둔다.
- stub 을 실제 응답에 맞추는 일: P5 처분을 따른다.
- 부분 취소와 다른 결제 수단(가상계좌 등): PeekCart 계약 밖이다(주문당 전액 1건).
- D-084(영구 404 증빙)와 D-065: 보류를 유지한다.

## 8. 완료 조건

`prepare`)까지만 진행한다.
