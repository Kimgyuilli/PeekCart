# D-110 — 부하 중 order outbox 발행 저하의 경계 분리 (ADR-0045 재검토 조건 1·2)

## 1. 명제

다음 중 하나라도 해당하면 미완이다.

- 부하 중 order outbox 발행이 굶는 원인을 order Hikari 풀 대기와 커밋 비용 중 어느 쪽으로도 판정하지 못했다.
- 판정 근거를 원본 없이 숫자로만 남겼다.
- ADR-0045 재검토 조건 1의 B(비동기 pipelining)와 C(저장 묶기)를 별도 ADR로 다룰지 결론이 없다.

배경(2026-10-26 GKE, `loadtest/reports/2026-10-26/s3/c0/`):
- c1 run에서 부하 60초 동안 order outbox는 약 925건만 발행했다(t1 시점 대기 9,275건, `c1-drain.tsv`).
  부하가 끝난 뒤에는 초당 약 71건으로 빠졌다.
- 같은 구간 order Hikari 풀(10) 지표(`run-window-metrics.tsv`)는 다음과 같다.
  - 유효 run: 대기 평균 46~84개, 획득 대기 평균 115~228ms
  - 무효 run: 대기 평균 112~150개, 획득 대기 평균 331~519ms
  - 커넥션 점유: 26.4~28.7ms
- 디스크 쓰기 지연은 0.58~0.70ms였다. order CPU는 2코어 limit 중 1.69~1.76코어를 썼다.
- 점유 26ms가 SQL·커밋 시간인지 CPU 대기 시간인지는 기존 데이터로 나눌 수 없다.

## 3. 검증 방법

### 사전 판정 규칙 (결과를 보기 전에 고정)

- 발행비 = 부하 구간 poller 발행률 ÷ 같은 반복의 배수 구간 발행률. 반복 3회의 중앙값을 쓴다.
- **J1 풀 경계**:
  - 풀 10의 발행비가 0.5 이하이고 풀 64(pending 평균 1 미만)의 발행비가 0.8 이상이면 "부하 중 발행 저하는 풀 대기가
    지배한다"로 확정한다.
  - 풀 10의 발행비가 0.5보다 크면 로컬이 굶주림을 재현하지 못한 것이다. 이때는 GKE의 2코어 limit(CPU)이 원인
    후보로 남고, 판정은 보류한다.
- **J2 커밋 비용**:
  - 풀 10에서 부하 점유 ÷ 단독 점유가 1.2 이하면 "DB 경합이 점유를 늘리지 않는다(점유 = SQL·커밋 고정 비용)"로 본다.
  - 1.2보다 크면 커밋 비용 경계도 함께 작동한다고 기록한다.
- **J3 B·C ADR**:
  - J1이 확정되면 다음과 같이 정리한다.
    - B는 이벤트당 커넥션 획득 수를 줄이지 않으므로 이 병목의 수정안이 아니다. 별도 ADR을 쓰지 않는다.
    - 수정안 후보 셋(풀 상향, poller 풀 분리, C 저장 묶기)은 후속 행으로 등록한다.
    - 그중 풀 분리(DataSource 경계)나 C(발행·커밋 실패 의미 변경)를 고르면 ADR이 필요하다는 판단도 그 행에 적는다.
  - J1이 보류되면 결론을 "GKE 재측정 필요(D-114 선행)"로 남긴다.
- 로컬은 CPU limit이 없다. 그래서 GKE 점유 26ms가 CPU 대기 때문인지는 이 실험으로 판정하지 않고 한계로 적는다.

### 추가 규칙 (1차 실행 뒤, 재실행 전에 고정)

1차 실행(2026-11-14, 풀 10·20·64, 3 run 모두 통과)의 결과는 아래와 같았다.
- 발행비: 0.03, 0.04, 0.13
- 부하 점유: 13.3ms, 25.3ms, 61.2ms
- 풀 64의 pending 평균: 0.9

풀 대기는 사라졌지만 점유가 늘어 poller가 계속 굶었다. 이 "J1 미충족"(풀 10은 굶고 풀 64도 회복하지 않음)은 위 규칙에
없던 경우다. 이 규칙들은 결과를 본 뒤에 더했다는 점을 밝혀 둔다. 그래서 1차 수치로 판정하지 않고, 아래 계측을
더해 다시 돌린 결과로 판정한다.

- 계측 추가: 구간마다 MySQL `performance_schema.events_statements_summary_global_by_event_type`의 문장 시간 누계를
  차분한다. 이 값을 커넥션 획득 수로 나눠 "획득당 서버 시간"을 얻고, COMMIT 평균 시간도 같이 구한다.
  점유에서 서버 시간을 뺀 나머지는 앱 쪽(JVM CPU, 드라이버, 네트워크)이다.
- **J4 점유 증가의 자리**: 풀 64를 기준으로 증가분 비율을 계산한다.
  비율 = (부하 서버 시간 − 단독 서버 시간) ÷ (부하 점유 − 단독 점유)
  - 0.7 이상: 점유 증가가 MySQL 서버 안(커밋, 잠금, 서버 CPU)에 있다. 경계는 DB 처리량이다.
  - 0.3 이하: 점유 증가가 앱 쪽에 있다. 로컬 JVM이 MySQL과 CPU를 나눠 쓴 결과일 수 있어 로컬로는 판정하지 않는다.
  - 그 사이: 혼합으로 기록한다.
- **J3 보강**:
  - J1이 미충족이고 J4가 DB 쪽이면 다음과 같이 본다.
    - 원인: poller가 이벤트마다 트랜잭션을 하나씩 쓰면서 DB 처리량을 부하와 나눠 쓰는 구조다.
    - 풀 상향과 풀 분리는 획득 대기만 없앨 뿐 서버 쪽 대기를 줄이지 않으므로 수정안이 아니다.
    - B는 저장 횟수를 줄이지 않으므로 수정안이 아니다.
    - 이벤트당 트랜잭션 수를 줄이는 C 계열이 후보다. C는 발행·커밋 실패 의미를 바꾸므로 ADR이 선행이다
      (ADR-0045 재검토 조건 1).
  - J4가 앱 쪽이거나 혼합이면 GKE 재측정이 필요하다(D-114 선행).

### false-green 차단 (실패를 주입해 확인)

- 풀 크기 단언: 환경변수 이름을 틀리게 주고 돌리면 테스트가 실패해야 한다. 기본값 10이 그대로 잡혀 "풀 64" 결과로
  둔갑하는 것을 막는다.
- 계측 단언:
  - Hikari usage/acquire 타이머가 없거나 구간 차분 count가 0이면 실패한다.
  - DB PUBLISHED 증가분과 poller success 타이머 증가분이 다르면 실패한다. 다른 경로의 발행을 poller 발행으로 세는
    것을 막는다.
  - 음성 대조로 poller를 끈 부하 구간을 1회 둔다. 이 구간의 PUBLISHED 증가분이 0이어야 한다.
- 정합성 단언: 배수가 끝나면 PUBLISHED 수가 생성 주문 수와 같고, PENDING과 FAILED는 0이어야 한다.
- 일반 CI 영향: env가 없으면 probe는 skip된다. `scripts/integration-test-container-lint.sh`가 통과해야 한다
  (`@Import(SharedContainers.class)` 사용, `@Testcontainers` 미사용).

## 미해결

- GKE에서 점유를 분해하려면 CPU 대기와 SQL 시간을 따로 재야 한다. 이는 J1이 보류되거나 수정안을 검증할 때
  GKE 세션에서 다룬다(D-114 선행).
- D-111~D-114는 이 작업 범위 밖이다.

## 결과 (2026-11-14, 증적 `docs/evidence/D-110/`)

| 풀 | 부하 획득 대기 ms | 부하 점유 ms | 부하 pending 평균 | 부하 발행/s | 배수 발행/s | 발행비 |
|---|---|---|---|---|---|---|
| 10 | 72.9 | 13.3 | 53.6 | 7.0 | 205.0 | 0.03 |
| 20 | 57.0 | 25.3 | 44.2 | 6.4 | 171.5 | 0.04 |
| 64 | 0.9 | 61.2 | 0.9 | 23.8 | 183.6 | 0.13 |

- J1은 미충족이다. 풀 10에서 poller는 굶지만, 풀 64에서 대기가 사라져도 회복하지 않는다(0.13). 대기가 풀 큐에서
  점유로 옮겨갈 뿐이다.
- J2: 점유비 2.07로 부하가 점유를 늘린다.
- J4는 미판정이다. 2차 실행에서 `performance_schema`로 서버 시간을 재려 했지만, 공유 Testcontainers MySQL에는 그 테이블이
  없어 세 run 모두 실패했다. 이 MySQL은 기본 `my.cnf`(buffer pool 16M, redo 5M, binlog 없음)로 떠서 GKE와 DB 특성이 다르다.
  공유 컨테이너 설정은 모든 통합 테스트에 영향을 주므로 바꾸지 않았다. 사용자 결정(2026-11-14)에 따라 지금 데이터로 결론을 낸다.
- **결론(J3)**:
  - 부하 중 발행 저하의 원인은 구조다. poller는 이벤트마다 트랜잭션을 쓰는 순차 클라이언트라서, 포화된 공유 자원을
    부하 스레드와 같은 몫으로 나눠 쓴다. 획득 1회 비용(대기 + 점유)이 곧 이벤트 1건의 비용이 된다.
  - 풀 상향과 poller 전용 풀은 단독 수정안이 아니다. 대기 자리만 옮긴다.
  - B(비동기 pipelining)는 저장 횟수를 줄이지 않으므로 이 병목의 수정안이 아니다. B는 별도 ADR을 쓰지 않는다.
  - C(저장 묶기)는 이벤트당 트랜잭션 수를 줄이므로 유일하게 구조를 건드리는 후보다. 발행·커밋 실패 의미를 바꾸므로
    ADR이 선행해야 한다(ADR-0045 재검토 조건 1). 후속 행으로 등록한다.
  - 점유 증가가 DB 쪽인지 앱 쪽인지(J4)는 GKE MySQL 서버 지표로 확인한다. 이것은 C 설계의 입력이며 D-114가 선행한다.
- 측정 밖 관찰: 주문번호(날짜 + 32비트)가 같은 날 n건에서 약 1 − exp(−n²/2³³) 확률로 충돌한다. 1만 건이면 약 1.2%다.
  충돌한 요청은 500으로 실패한다. 후속 행으로 등록한다.
