# D-109 — 상품 조회 캐시의 로딩 묶기 · 재고 만료 전 갱신 · 장애 시 마지막 값 응답

기준: 2026-11-13, main `859d73e9`. 결정은 ADR-0046 D2~D6 이다. 이 계획은 ADR 이 계획서로 미룬 클래스 구조, 파라미터,
지표 이름을 정한다. 같은 PR 에 `/sync` 아카이브 정리(D-115·D-117 계획서 이동, D-117 완료 행 이동)를 함께 싣는다.

등급 M: 모듈은 product-service 하나다. 계약 표면이 바뀐다(지표 3개 추가, Redis 키 접두사 `cache:` → `cache:v2:`).
되돌림은 이 PR 의 revert 로 끝난다(v2 키는 TTL 로 사라진다).

## 1. 명제

다음 중 하나라도 성립하면 미완이다.

- 한 Pod 에서 같은 키로 동시에 N 개가 miss 되면 DB 조회가 2회 이상 나간다(D2).
- `productStock` 이 soft 시점(3초)을 지난 뒤 들어온 요청이 둘 이상 DB 를 친다. 또는 갱신이 상한(`PRD-005`)에 거절됐는데,
  값의 나이가 hard 5초 안인데도 503 이 나간다(D3).
- 응답한 재고 값의 나이(DB 에서 읽은 시각부터)가 5초를 넘는다. Redis 가 정상일 때와 장애일 때 모두 해당한다(ADR-0026 D2).
- Redis 가 연결 거부나 무응답일 때, 허용 범위(정보 30분, 목록 10분, 재고 5초) 안의 마지막 값이 Pod 에 있는데도
  DB 를 친다. 또는 범위를 넘은 값을 낸다(D4).
- Redis 가 정상인데 정보·목록 응답이 Pod 메모리에서 나온다(D5).
- 캐시를 감싼 뒤 `cache_gets_total{name=product|products|productStock}` 이 사라지거나 두 벌이 된다(ADR-0009 S7).
- 새 지표 3개(`cache_load_coalesced_total`, `cache_stale_served_total`, `cache_refresh_rejected_total`)가 노출되지 않는다.
- 롤링 배포 중에 옛 Pod 가 새 형식의 값을 읽다가 직렬화 오류(500)를 낸다.
- 런북 `docs/runbooks/redis-cache-fallback.md` 와 `docs/04-design-deep-dive.md` 의 캐시 절이 장애 동작을 옛날처럼 적고 있다.

## 2. 코드 검증 (2026-11-13)

| 전제 | 확인 결과 | 계획에 미친 영향 |

범위 변화: 없다. 다만 위 표의 S7 바인딩과 롤링 배포 호환(키 접두사)은 TASKS 행에 없던 필수 항목이라 P1·P2 에 넣었다.

## 3. 결정한 파라미터와 구조

- **클래스**: `com.peekcart.global.cache.ResilientRedisCache`(`Cache` 구현, `RedisCache` 를 감싼다)와
  `CacheEnvelope(Object value, long loadedAtEpochMs)`. `CacheConfig` 안의 `RedisCacheManager` 하위 클래스가 `decorateCache` 에서
  감싼다.
- **Redis 값 형식**: 세 캐시 모두 `CacheEnvelope` 로 싸서 넣는다. 재고의 soft·hard 판정과 장애 허용 범위를 "DB 에서 읽은 시각"
  으로 재야 하기 때문이다. Redis hit 값의 나이를 모르면 Pod 사본의 나이가 Redis TTL 만큼 늘어 정보는 최악 60분이 된다.
- **키 접두사**: `cache:` → `cache:v2:`. 같은 키에 새 형식을 쓰면, 롤링 배포 중에 옛 Pod 가 모르는 `@class` 를 만나
  `SerializationException` 을 던진다. 핸들러가 이 예외를 되던지므로 500 이 된다. 옛 키는 TTL(최대 30분)로 사라진다.
  배포 중에는 옛 Pod 의 evict 가 v2 키를 지우지 못한다. 그래서 그 사이 수정은 v2 사본에 TTL 까지 남을 수 있다. 같은 일이
  반대 방향(새 Pod 의 evict 와 옛 키)으로도 생긴다. 롤링 배포 몇 분 동안만 열리는 창이고, L-006 이 받아들인 범위 안이다.
- **재고**: soft 3초, hard 5초(Redis TTL 과 Pod 허용 범위 모두). 3초에서 5초까지 2초 동안은 갱신이 거절돼도 다음 요청이
  다시 갱신을 시도할 수 있다.
- **장애 허용 범위**: 정보 30분, 목록 10분, 재고 5초(ADR-0046 D4). Caffeine 의 `expireAfterWrite` 도 같은 값으로 둔다.
- **Pod 사본 크기 상한**: 정보 10,000, 재고 10,000, 목록 1,000(목록 값은 페이지 단위라 크다).
- **기다림 상한**: 3초. 이 시간 안에 리더의 로딩이 끝나지 않으면 `PRD-005`(503)다. 로딩이 멈춘 동안 같은 키의 요청이
  Tomcat 스레드를 다 쓰지 않게 하려는 것이다. ADR-0037 의 "대기열 없음"은 상한(permit)의 성질이다. 이 기다림은 permit 도
  커넥션도 잡지 않는다.
- **위치**: 위 값은 동작 규약이라 `CacheConfig` 상수로 둔다(ADR-0007). 프로퍼티로 열지 않는다. 테스트는 `Clock` 을 바꿔 시험한다.
- **지표**(모두 `cache` 태그):
  - `cache.load.coalesced`: 다른 요청의 로딩을 기다려 받은 요청 수(D2)
  - `cache.stale.served`: Redis 오류로 Pod 사본을 낸 응답 수(D4)
  - `cache.refresh.rejected`: 재고 갱신이 상한에 거절돼 기존 값을 낸 수(D3)

### `get(key, loader)` 흐름

1. Redis 를 읽는다. 가용성 오류면 핸들러가 `cache.fallback{get}` 을 센다. 그 밖의 오류는 되던진다.
2. hit 인데 나이가 hard 이상이면(시계 차나 TTL 경계) miss 로 본다. 그 밖의 hit 이면 Pod 사본에 `(값, loadedAt)` 을 둔다. 재고이고 나이가 soft 이상이면 이 키의 갱신을 맡으려 한다. 맡으면 로더를 돌리고,
   `PRD-005` 로 거절되면 기존 값을 낸다(`refresh.rejected`). 못 맡으면 기존 값을 바로 낸다. 정보·목록은 값을 그대로 낸다(D5).
3. Redis 오류면 Pod 사본을 본다. 허용 범위 안이면 그 값을 낸다(`stale.served`).
4. 그 밖(miss, 범위 초과, 사본 없음)은 로딩을 묶는다. 키별 진행 중 로딩이 있으면 그 결과를 기다리고(`load.coalesced`,
   상한 3초), 없으면 로더를 돌린다. 끝나면 Redis 에 쓰고(실패는 `cache.fallback{put}`), Pod 사본에도 둔다. 로더 예외는 기다리던
   요청에도 같은 예외로 전달된다.

## 4. 작업 항목

- [x] P1. `CacheEnvelope`, `ResilientRedisCache` 를 만든다. 내용은 §3 흐름, `get(key)`·`get(key, Class)`·`put`(봉투로 싼다),
  `evict`·`clear`(Pod 사본을 먼저 지운다)다. 접두사를 `cache:v2:` 로 바꾸고, `CacheConfig` 를 하위 클래스로 바꿔 감싼다.
  `product-service/build.gradle` 에 Caffeine 을 넣는다.
- [x] P2. 감싼 캐시용 `CacheMeterBinderProvider` 빈을 둬서 S7 `cache_gets_total` 을 유지한다.
- [x] P3. `ProductCacheService` 의 세 `@Cacheable` 에 `sync = true` 를 단다. javadoc 의 재고 stale 서술에 soft 3초를 더한다.
- [x] P4. 지표 3개를 등록한다. 등록 방식은 `ResilientCacheErrorHandler` 처럼 `ObjectProvider<MeterRegistry>` 로 지연한다.
  공통 태그가 사라지는 문제를 피하려는 것이다.
- [x] P5. 단위 테스트 `ResilientRedisCacheTest` 를 쓴다. 가짜 `Cache`·`Clock` 으로 아래를 본다.
  - 동시 miss N 개에 로더가 1회 돈다.
  - 재고 soft 전에는 갱신하지 않고, soft 뒤에는 한 요청만 갱신한다.
  - 갱신이 거절되면 기존 값이 나간다.
  - Redis 오류일 때 범위 안이면 사본을, 범위를 넘으면 로더를 쓴다.
  - Redis 정상 hit 에는 사본을 쓰지 않는다.
  - evict 가 사본을 지운다.
  - 기다림 상한을 넘으면 `PRD-005` 다.
  - 가용성 오류가 아닌 Redis 오류는 되던진다.
- [x] P6. 통합 테스트를 고친다.
  - `ProductCacheFallbackIntegrationTest`: `outageBounds...` 를 둘로 나눈다. 같은 키 동시 요청은 묶여 200 이고 DB 는 1회다.
    다른 키 동시 miss 는 503 이다. V5 를 "장애 중 같은 키 N회 조회에 DB 1회"로 뒤집는다. 키 패턴은 `cache:v2:` 로 바꾼다.
  - Redis 정상 상태의 같은 키 동시 miss 도 DB 1회인지 확인하는 테스트를 더한다.
  - 재고 갱신 거절 테스트를 더한다. 다른 키가 permit 을 잡은 동안 soft 를 지난 재고를 조회하면 200 이고 기존 값이 나와야 한다.
    `ProductStockCacheStalenessIntegrationTest` 의 TTL 계약(5초 뒤 신값)은 그대로 통과해야 한다.
- [x] P7. `ProductObservabilityMetricsIntegrationTest` 로 `cache_gets_total` 이 이름마다 한 시계열인지 확인한다. 이 테스트는
  이미 있으니 통과만 확인한다. 새 지표 3개가 노출되는지는 P6 테스트에서 단언한다.
- [x] P8. 문서를 고친다.
  - `docs/runbooks/redis-cache-fallback.md`: §0·§1·§5 의 장애 동작(Pod 사본 응답과 DB 조회 상한), §2 의 새 지표, §4.2 의
    키 패턴(`cache:v2:`), §6 의 배포 순서(롤링 중 v2 전환과 옛 키 처분)를 고친다.
  - `docs/04-design-deep-dive.md` 캐시 절: ADR-0046 을 참조로 걸고 동작을 고친다.
  - `ProductCacheService`·`CacheConfig`·`ResilientCacheErrorHandler` 의 javadoc 가운데 "put 실패면 모든 후속 요청이 DB 를 친다,
    완화는 후속(M7)" 서술을 고친다.

## 5. 검증 방법

각 항목은 먼저 고치기 전 코드로 실패를 확인한다. 테스트를 먼저 쓰고 옛 동작에서 빨간불을 본 뒤에 구현한다.

- **D2**: 로더를 래치로 잡아 둔 채 같은 키로 동시에 5건을 보낸다. 옛 코드에서는 `findById` 가 5회(또는 상한 거절로 503)
  나와야 하고, 새 코드에서는 1회에 5건 모두 200 이어야 한다. 다른 키 동시 miss 의 503 은 그대로인지 같은 테스트에서 본다.
  묶기만 확인하고 상한 경로가 사라진 것을 놓치는 false-green 을 막기 위해서다.
- **D3**: `Clock` 을 3초 넘게 돌린 뒤 동시에 N 건을 보내 로더가 1회인지 본다. 갱신을 래치로 잡으면 나머지 요청은 기다리지 않고
  기존 값을 받아야 한다. 거절을 주입하면 기존 값이 나와야 한다. 5초를 넘기면 거절이 그대로 `PRD-005` 인지 본다. hard 경계에서
  옛 값을 계속 내는 오류를 잡기 위해서다.
- **D4**: Toxiproxy 로 Redis 를 끊는다. 범위 안이면 `findById` 0회에 `cache_stale_served_total` 이 늘어야 한다. `Clock` 으로
  범위를 넘기면 DB 1회가 나와야 한다. 재고는 5초를 넘긴 사본을 내지 않는지 본다.
- **D5**: Redis 가 정상일 때 DB 값을 바꾸고 evict 한다. 다음 조회가 Pod 사본의 옛 값이 아니라 새 값인지 본다.
- **S7**: `/actuator/prometheus` 에서 `cache_gets_total{name="product"...}` 를 확인한다. P2 를 빼고 돌려 이 테스트가 실패하는지도 본다.
- **롤링 호환**: 옛 형식(봉투 없는 값)을 `cache:` 키에 직접 넣는다. 새 코드가 그 키를 읽지 않는지(DB 1회) 본다.
- **회귀**: `./gradlew :product-service:test` 전체와 `scripts/integration-test-container-lint.sh` 를 돌린다.

## 6. 범위 밖과 미해결

- **GKE 측정**(TASKS ⑤ 뒤쪽): 캐시 ON 고부하의 503 비율과 Redis 중단 시 DB 조회 수다. 클러스터 과금과 D-114(측정 볼륨)
  선행이 걸려 있어 다음 측정 세션으로 넘긴다. 이 PR 뒤 D-109 는 ◐ 부분 완료(남은 것은 GKE 측정)로 둔다.
- **Redis 무응답 중의 요청당 대기**: 장애 중에도 요청마다 Redis 명령 타임아웃을 한 번 기다린 뒤 Pod 사본을 낸다. 회로 차단기는
  ADR-0046 범위가 아니다. 무응답 장애에서 지연이 문제로 측정되면 따로 다룬다.
- **Pod 간 동시 재적재**: Pod 수만큼 같은 키를 다시 읽는다. ADR-0046 재검토 조건 2 의 대상이다.
- **새 지표의 Grafana alert**: 이번에는 노출까지만 한다. 알림 기준은 GKE 측정에서 값을 본 뒤 정한다.
