# task-phase4-closure

Phase 4 순서표 구현 ①~⑥ 이 전부 머지됐는데 `docs/TASKS.md` 헤더는 `## Phase 4 — MSA 분리
(예정)` 인 채였다. 마지막 계획서(`task-d029-mysql-cpu-base-promotion`)도 아카이브되어
`docs/plans/` 루트가 비었다. 단계의 실제 상태와 문서가 어긋나 있었다.

코드 변경 0. 문서 종결 처리다.

## 명제

순서표 항목이 전부 머지됐으면 단계는 끝난 것이다. 단, 순서표에 **미착수로 남은 행이
있는데 그것을 지우거나 끝난 것처럼 적으면** 미완이다. 열린 항목은 추적 축을 옮겨
살려둔 채로 단계만 닫아야 한다.

## 검증으로 드러난 사실 (종결 전 코드 확인)

| 전제 | 결과 |
|---|---|
| 순서표 ①~⑥ 전부 머지됨 | 확인 — #48~#68 · #69/#71/#72 · #73~ · #93 · #94 · #96 |
| `운영 관측성 / L-004` 행도 끝났다 | **반증** — 미구현이다 (아래) |
| Slack 채널이 이미 분리돼 있다 | **반증** — `SlackPort` 구현이 하나, 웹훅도 하나 |

`SlackPort` 구현체는 `common/src/main/java/com/peekcart/global/slack/SlackNotificationClient.java`
**하나**뿐이고 설정도 `slack.webhook.url` **단일 웹훅**이다. 그래서 `OutboxPollingService`
(발행 실패 = Outbox `FAILED`)와 `DeadLetterRecorder`(처리 실패 = DLQ)의 알림이 같은 채널로
나간다. 둘은 대응이 정반대다 — 전자는 브로커 복구 후 재발행, 후자는 데이터 수정 후 원본
토픽 재투입. 운영자가 알림 문구로만 구분해야 한다. 동반 공백으로 DLQ 적재량 메트릭이 없다
(`docs/learning/11-consumer-idempotency-dlq.md:316,431`).

이걸 이유로 단계를 열어두지 않고 **D-030 으로 승격해 이월**한다. Phase 1~3 이
D-003(Won't Fix)/D-004(운영지식)를 남기고 닫힌 것과 같은 처리다. 단계 종결과 부채 추적은
별개 축이다.
