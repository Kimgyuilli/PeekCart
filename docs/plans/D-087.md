# D-087: Docker Gradle 구간의 실제 CI profile 보존

## 1. 명제와 코드 전제

Docker build의 태스크 헤더를 시작 시각으로 오인한 컴파일8초/기동설정28초 주장이 현재 근거로 남거나, 새 CI 측정이 raw profile과 checkout/build ref에 연결되지 않으면 미완이다. BuildKit cache-hit의 이전 보고서를 이번 Gradle 실행으로 집계하거나 누락/손상 자료를0초로 처리해도 미완이다.

기준 main `bdc370a80e0bfa6adefb6a436a5f608f878d1b69`의 Dockerfile/images job과 archive D039를 읽었다. root는 ci.yml images/profile 단계만 위임했으며 다른 CI/shared TASKS/master/PHASE는 수정하지 않는다.

| 전제 | 직접 확인 |
|---|---|
| 실제 builder | Gradle wrapper8.14.4, JDK17 build stage에서 bootJar -x test --no-daemon. host setup-gradle 캐시는 Docker build에 연결되지 않는다. 현재 --profile/report export는 없다. |
| CI cache | build-push-action@v6은 service별 gha scope/image load/mode=max export를 사용한다. 동일 builder의 별도 local export target으로 report만 꺼낼 수 있고 runtime 최종 파일은 jar만 유지한다. |
| 원래 로그 | run36393965323/job108836245553 raw를 API로 재확보했다. bootJar35.6초, common compileJava/processResources/classes 헤더27.96초, jar28.06초다. 네 개 모두27.96이라는 task 행의 압축 표현과 구분한다. cache export vertex44.1초도 별도 확인했다. |
| 해석 한계 | 위 헤더로 실제 compile 시작을 알 수 없어8/28 분해는 유효한 profile 측정이 아니다. 현재 CI의 actual profile을 얻기 전 새 비중/최적화 결론을 확정하지 않는다. |
| 역사 정정 | done/task-d039-gradle-setup.md 원문은 보존하고 append 정정한다. PHASE5 기존 문장은 root 공유 영역이므로 필요한 정정 근거만 전달한다. |

등급 M: Docker/CI 산출물 계약을 보강한다. 제품 모듈/배포 정책/외부 의존성 변경은 없으며 새 ADR은 불필요하다. build-stage report와 scratch export target은 runtime image에 넣지 않는다. 캐시를 깨는 nonce/무조건 no-cache는 사용하지 않는다.

## 2. 작업 항목

- [x] P1. bootJar 실제 실행에 --profile과 생성 metadata를 추가하고 별도 export target으로 HTML/metadata만 추출한다. runtime stage 내용/이미지 소비와 gha cache 정책은 보존한다.
- [x] P2. images job에서 actual checkout/run/builder/build ref/원 진행 로그·build record·profile hash를 보존한다. main build의 bootJar cached와 fresh 실행을 구분하고 export build를 원래 측정으로 바꾸지 않는다.
- [x] P3. fail-closed analyzer에서 실제 Gradle HTML summary/task 시간과 BuildKit bootJar/cache export vertex 시간을 별도로 기록한다. 누락/stale/서비스 불일치/parse 실패·잘못된 수치를 거부하고 cached report는 미측정으로 표시한다. 시간 축을 합산하거나 미래 목표를 결정하지 않는다.
- [x] P4. 정상/음성 fixture와 잘못된 구현 대조를 Actions에 연결하고 실제 재측정 자료를 보존할 경로를 마련한다. source/실행 SHA·원자료/범위/한계를 own evidence에 보존하고 D039에는 좁은 append 정정을 남긴다. 전체 CI/정확 head 독립 검토는 별도로 받는다.

## 3. 검증

Actions 우선으로 실제 images job에서 HTML/metadata/history logs/record를 수집한다. 로컬은 parser의 최소 개발 fixture와 syntax만 확인하고 Gradle/Docker는 실행하지 않는다. 보고서 누락/부분 값/NaN/음수/중복·stale와 cache-hit 이전 자료를 paired control로 확인한다. 실제 fresh profile을 얻지 못하면 미측정으로 남기고 원자료를 보존한다. runtime stage 내용 보존과 기존 module/image 계약 lint는 CI에서 확인한다. 별도 Codex 리뷰 미호출. 공유 TASKS/master 및 PHASE는 root 소유다.

## 단순화 기준

사용자 지시에 따라 목적별 Python collector/analyzer 하나와 selftest 하나만 추가하고 범용 설정/등록 계층이나 shell wrapper는 만들지 않는다. 기존 Buildx action과 동일 builder를 재사용한다. 원 plain log와 .dockerbuild를 보존하므로 사용하지 않는 rawjson 이중 수집/검증은 제거했다. HTML의 project-total은 raw에 남기고 JSON task 시간에 중복 합산하지 않는다. begin과 두 build ref 기록은 fresh/stale 연결과 원이미지/추출build 구분에 필요한 단계다.

## 구현/검증 상태

checkbox는 계측/validator/fixture/CI 배선 구현 완료를 뜻한다. 첫 Actions d0ec에서10 method/8 mutants는 통과했으나 Buildx ref 인자 오류로 실제 profile 수집은 실패했다. 첫 수정도 progress stream 오류로 분석에 실패했다. 단일 stream 수정 후10 method/10 mutants 및 실제 CI profile은 Actions 대기이며 D087 전체 측정 목표 달성으로 기록하지 않는다. 최종 최소 로컬1 method PASS와 AST/whitespace, 새 보존 gate만 확인했다. runtime stage 계약과 exact CI failure propagation은 전체 suite에서 검사한다. 사용자 단순화 지시에 따라 기존 policy lint의 PyYAML을 재사용하고 rawjson 중복과 추가 wrapper는 없앴다. 실제 보고서를 읽은 뒤 새 수치와 한계를 추가한다.
