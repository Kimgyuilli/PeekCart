# D-075 — outbox 발행 처리율 정책 결정 보류

## 1. 명제와 현재 상태

목표 TPS와 최대 backlog 수용 시간 없이 설정 상향·비동기 발행·현행 수용을 임의로 선택하거나, 과거 측정값을 이번 실행의 실측으로 보고하면 미완이다.

**보류**: 2026-10-17 사용자가 목표 처리율·backlog 수용 기준 결정을 보류했다. 이번 작업은 개별 보류 계획과 코드 전제 기록뿐이다. 구현, 설정 변경, 부하 실험, CI 실행을 수행하지 않았다. 보류는 현행 처리율을 수용했다는 뜻이 아니며 사용자 답변 부재를 승인으로 간주하지 않는다.

## 2. 배경과 코드로 확인한 전제

기준은 `e66fe86`의 코드다. 후보 구현은 공유 messaging과 여러 서비스 설정·발행 계약에 영향을 줄 수 있어 잠정 L이다. 현재 변경은 문서뿐이며, 재개 시 선택안의 모듈·공유 계약·롤백 범위로 등급을 다시 확인한다.

| 전제 | 읽기 전용 확인 | 의미 |
|---|---|---|
| 스케줄 기본 지연 | `peekcart-common-messaging/.../outbox/OutboxPollingScheduler.java`: fixedDelay 기본 5s | 실행 소요 뒤 지연이 붙으므로 batch/delay만으로 처리량을 보장하지 않음 |
| poller 소유권 | 같은 scheduler의 서비스별 ShedLock, 최소 4초/최대 5분 | delay만 줄여도 락·사이클 계약을 함께 확인해야 함 |
| 기본 발행 설정 | Order/Product/Payment의 application.yml: batch 100, retry 5, publish timeout 6s, cycle timeout 4m | 과거 측정 조건과 현재 기본값을 구분 |
| 추가 영향 소비자 | Notification도 같은 공유 poller와 batch 100/timeout 계약 사용 | 구현 재개 시 세 서비스만 확인하고 공유 영향 누락 금지 |
| 현재 발행 경로 | 공용 `OutboxPollingService`: 목록을 순회하며 `send(...).get(timeout)` 후 PUBLISHED/save, 예외 시 retry 증가 | 비동기화는 완료·실패·중복·순서·종결 판단을 바꿀 수 있음 |
| 기존 계측 | 같은 poller의 outbox.backlog pending/failed와 outbox.publish success/failure Timer | 새 성능 측정의 입력 후보일 뿐 이번 측정 증거 아님 |
| replay 경계 | 같은 poller의 DOMAIN/REPLAY 분기, ADR-0020/0022 발행·drain 계약 | 처리율 변경이 replay 원장과 안전한 배수 경계를 훼손하면 안 됨 |

과거 자료 `docs/progress/evidence/d002bc-gke-20260917.md` §②는 기본 14.3~16.3건/초, 설정 완화 77.3건/초 및 남은 병목 미분리를 기록한다. 552초 배수 기록도 과거 GKE 실험이다. 이번 세션에서 재현·원인 분리하지 않았으며 로컬/GKE의 성능 동등성을 주장하지 않는다.

### ADR 판단

ADR-0009 S8 계측, ADR-0012 이벤트/순서 경계, ADR-0020/0022 replay 발행·배수 계약은 기존 제약이다. 설정 상향, 비동기 배치 발행, 현행 명시 수용 중 **정책 선택은 미정**이며 새 ADR 번호나 결정을 만들지 않는다. 재개 후 공유 발행 의미·경계·롤백 계약을 바꾸는 안이면 구현 전에 ADR을 작성하거나 갱신한다. 단순 설정 조정이어도 목표와 실패·배수 계약 근거를 먼저 기록한다. 현재 구조 이동은 제안·수행하지 않았다.

## 3. 재개 후 작업 항목

- [ ] P1. 사용자와 목표 TPS의 측정 단위·대상 경로, 최대 backlog 수용 시간 및 초과 시 대응 기준을 결정한다.
- [ ] P2. 무료 환경에서 수행할 원인 분리 계획·자원 예산·측정 조건을 확정하고 root 슬롯 승인 후 실험한다. polling wait, broker ack, DB 저장 비용과 장애 배수 시간을 구분한다.
- [ ] P3. 증거에 따라 설정 상향/비동기 발행/현행 수용을 결정하고 ADR 필요성을 확정한다. 선택 전 코드·설정 변경 금지.
- [ ] P4. 선택한 변경 또는 수용 근거를 검증하고 필수 CI·독립 검증·root 병합·완료 기록을 수행한다.

## 검증 방법과 완료 조건

P1 결정 전에는 성능 합격선을 만들지 않는다. 재개 시 같은 부하·데이터·자원·기간의 기준/변경 대조, 처리량과 backlog 시간, 오류·중복·순서·실패 복구·배수 결과를 함께 수집한다. broker timeout/늦은 ack/중단 후 재개·재전달 반례에서 실제 원장 상태와 소비자 멱등성을 확인해야 한다. 후보가 부하를 더 처리하더라도 유실·순서 훼손이나 근거 없는 PUBLISHED가 생기면 실패다.

무료 환경으로 목표를 검증할 수 없다면 해당 조건을 미완으로 남긴다. 유료 러너·GKE·실 PG·예산 증액은 허용되지 않는다. 전체 목표/수용 결정, 필요한 구현·검증·필수 CI·독립 검증·병합·기록을 충족하기 전에는 D075를 완료하거나 archive하지 않는다.
