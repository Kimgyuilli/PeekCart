# D-075: outbox 로컬 병목 분해 (부분 분석)

## 1. 명제와 코드 전제

과거 GKE의 약 13ms/event를 새 실측으로 쓰거나, scheduler 대기·락·Kafka 발행·DB 저장 시간을 구분하지 않은 채 원인을 단정하면 미완이다. 목표 TPS/backlog/초과 대응 정책을 임의로 확정하거나 300개 fixture를 목표 부하로 표현해도 미완이다.

2026-10-17에는 사용자 정책 결정 보류로 계획만 작성했다. 2026-10-21 사용자는 무료 로컬 분석과 정책 독립 수정을 재개하도록 승인했다. 현재 부분 범위는 측정 probe와 근거다. 기존 보류 기록은 audit 및 git 이력에 남기며 정책 결정은 여전히 열려 있다.

기준 `a7ffa11 (측정 직전 최신 main; 최초 계획 기준545e5dc에서 fast-forward)`.

| 코드 전제 | 검증한 의미 |
|---|---|
| OutboxPollingService | batch 조회 뒤 event마다 buildRecord/send().get(timeout), 성공 timer, markPublished/save를 순차 실행한다. publish timer는 build/send/ack 대기까지이고 save는 제외한다. |
| transaction | poller 전체에 Transactional이 없다. adapter는 Spring Data save로 위임한다. timed decorator는 실제 repository proxy를 호출해 save 반환까지(그 호출의 transaction 완료 포함) 잰다. 조회·저장 결과를 별도 DB 조회로 확인한다. |
| OutboxPollingScheduler | fixedDelay 기본5s는 실행 종료 뒤 지연이다. ShedLock 최소4s/최대5m가 있어 delay500ms만으로 실행 주기500ms를 보장하지 않는다. |
| 소비자 | order/product/payment/notification 네 서비스가 공유 poller를 사용한다. 본 probe는 order schema와 공유 구현을 검증하며 네 서비스 동등 성능을 주장하지 않는다. |
| 실제 환경 | SharedContainers의 MySQL8.0.46/Kafka3.8.1/Redis7, Kafka acks=all/idempotence=true. 단일 로컬 broker이고 운영 GKE 자원/복제/네트워크와 다르다. |

등급 M: order 테스트 probe와 자체 근거만 변경한다. production 설정/발행 의미는 바꾸지 않는다. 새 ADR 불필요. 향후 비동기 발행 등 의미 변경은 ADR-0012/0020/0022와 별도 설계·검증이 필요하다.

## 2. 이번 부분 작업

- [x] P5. opt-in probe에서 실제 MySQL/Kafka, unchanged poller와 repository proxy, publish Timer를 측정하고 단위를 기록한다. 앱의 배경 jobs/listeners는 off로 유지한다.
- [x] P6. 같은 300개 fixture, 3반복으로 batch100/delay5s/minlock4s, 100/500ms/4s, 500/500ms/4s, 100/500ms/0s 진단 대조를 측정한다. 실제 Spring fixed-delay task와 JDBC ShedLock을 쓰되 전체 앱 scheduler 부하를 재현했다고 쓰지 않는다.
- [x] P7. 같은 실제 producer로 순차 send.get와 제한된 in-flight 발행을 측정해 DB 없는 진단 대조로 제시한다. 각 반복의 broker 레코드·payload/키/개수와 DB 상태를 확인하며 예외/타임아웃을 정상 성능 표본에 섞지 않는다.
- [x] P8. warmup·반복 raw·실제 start/end·lock skip·producer 설정·DB/timer 단위·자원 한계를 보존하고 선택안/권고를 정책 결정과 분리한다. 필요한 검증과 CI를 보고한다.

## 3. 검증 방법

root heavy 독점 슬롯 승인 뒤 offline/no-daemon/no-parallel/max-workers=1로 opt-in focused probe를 실행한다. 정상 측정은 별도 fixture topic으로 warmup한 뒤 시작하고 seed/검증 시간은 측정 밖이다. DB save/find와 poll wall, 기존 publish Timer의 합 및 잔여를 나란히 기록한다. 이 계측은 broker 내부 처리 시간이나 DB 내부 CPU의 순수 인과 분해가 아니다.

같은 fixture에서 baseline/control profile을 반복하며 실제 scheduler start/end와 lock skip을 기록한다. direct producer 대조는 DB와 서비스 발행 의미를 제거한 진단으로 한정한다. broker record 누락/중복/잘못된 payload나 DB PENDING/FAILED 잔존이면 측정은 실패다. 인위 지연 대조로 계측값이 해당 항목에서 증가하는지 확인하며 성능 개선 합격선을 만들지 않는다. timeout/발행 실패는 별도 실패 근거로 처리한다.

전체 CI와 관련 lint를 확인한다. 실제 원본 XML과 선택 결과를 비밀 검토 뒤 보존한다. 측정하지 않은 자원/네트워크/실운영 경합은 미측정으로 남긴다.

## 기존 정책 항목과 미해결

이전 계획의 stable ID P1(목표 TPS/backlog/초과 대응 결정), P3(설정/비동기/수용 정책 선택), P4(선택한 정책의 검증·병합)은 이번 범위에서 열린 상태다. P2의 무료 원인 분리만 P5~P8로 구체화했다. 이번 부분 완료로 D-075 전체를 archive하거나 완료로 옮기지 않는다.

과거 `d002bc-gke-20260917.md`의14.3~16.3/77.3건/s와552초 배수는 이번 로컬 입력·결과가 아니다. 목표·수용 정책, 실제 GKE/복제 broker/CPU 경합, 장애 배수·replay/비동기화 의미의 전체 검증은 남는다. 외부 PG/Slack/운영 변경이나 유료 실행은 하지 않는다. D-078의 실제 jitter/DLQ 부하와 scheduler pool4 stress는 이 로컬 기반 뒤 별도 PR 후속이며 완료로 보지 않는다. TASKS/PHASE/ADR index 및 master는 root 소유로 수정하지 않는다.

## 실제 검증 결과 — 2026-10-21

최초 compile 오류는 실제 jar API로 수정했고, 같은 focused command의 두 번째 실행은1test/failures0/errors0, Gradle2분16초로 통과했다. XML의53개 marker와3반복/4profile/6producer trial/두 control을 파싱해 검증했다. broker payload·키·개수·같은 key 순서와 DB 상태를 실제 대조했다. [원본·실행·선택지](evidence/D-075/README.md)를 보존한다.

300fixture drain 중앙값은 baseline12.255s, delay-only9.408s(매회12lock skip), larger-batch1.825s, minlock0 진단3.094s였다. active에서 실제 save 호출 시간이 가장 컸고 producer-only window32 대조는 DB가 빠진 조건이다. 유한 drain·로컬 측정의 한계를 유지하며 production 정책/설정/공유 코드는 바꾸지 않았다. 전체 CI는 PR 대기이며 전체 D-075 완료가 아니다.
