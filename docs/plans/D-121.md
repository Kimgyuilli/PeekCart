# D-121 — 취소 선도착 marker 의 경합을 잠금 조회와 엔티티 삭제로 닫기

## 1. 명제

다음 중 하나라도 해당하면 미완이다.

- `order.created` 와 `order.cancelled` 를 다른 consumer group 이 같은 주문으로 겹쳐 처리할 때, 취소 marker(`payment_cancellations`)가 남고
  Payment 가 PENDING 으로 생기는 순서가 있다(ADR-0012 D3 취소 게이트 누수).
- 생성 쪽이 취소 marker 를 적용한 뒤에도 marker 행이 남는다(파생 `deleteByOrderId` 의 스냅숏 SELECT).
- 이 수정이 기존 경로와 반대 순서의 잠금을 만들어 교착 가능성을 더한다.

배경: D-112(#266) 경합 분석에서 발견했다(`docs/plans/done/D-112.md` §미해결). D-112 는 예약 결과 marker 만 잠금 조회와 엔티티 삭제로 바꿨다.
이 건은 같은 방식을 취소 marker 에 적용한다. 단, 취소 쪽 Payment 조회는 D-112 와 달리 "없을 때만" 잠근다(아래 교착 분석, 사용자 결정 2026-11-19).

등급 M 근거: 모듈은 `payment-service` 하나이고 공개 API·이벤트 스키마·DB 스키마·설정 키가 바뀌지 않는다. 되돌림도 이 모듈 안에서 끝난다.
그래서 기준상 S 지만, 경합과 잠금 순서 설계라 애매할 때 높은 쪽을 고르는 규칙에 따라 M 으로 둔다.

### 교착 분석과 결정

D-112 처럼 취소 쪽을 늘 `findByOrderIdForUpdate` 로 바꾸면(2번 안), Payment 가 있고 APPROVED 인 경로에 "결제 행 잠금, 그다음 환불 INSERT IGNORE"
순서가 생긴다. `finalizeOutcome` 은 "환불 행 잠금, 그다음 결제 UPDATE" 순서다. 같은 주문의 환불이 보상 요청으로 이미 확정 중일 때
`order.cancelled` 가 늦게 오면 서로를 기다린다. 지금 코드는 결제 행을 잠그지 않고, APPROVED 면 상태도 바뀌지 않아 UPDATE 도 없다.
그래서 INSERT IGNORE 가 확정 커밋을 기다렸다가 0 을 받고 끝난다.

결정(사용자 결정 2026-11-19): 1번 안. 취소 쪽은 기존 비잠금 조회를 먼저 하고, 없을 때만 `findByOrderIdForUpdate` 로 다시 조회한다.

- 비잠금 조회가 Payment 를 보면 커밋된 행이므로 생성 쪽과 경합이 없다. 기존 경로와 잠금 순서를 그대로 둔다.
- 다시 조회했는데 Payment 가 보이면 막 생성된 Payment 다. 생성 쪽의 미커밋 INSERT 가 있으면 잠금 조회가 그 커밋을 기다린다. 취소를 적용한다.
- 그래도 없으면 `uk_payments_order_id` 키 구간 잠금이 생성 쪽 INSERT 를 이 커밋 뒤로 세운다. 그 아래에서 marker 를 저장한다.

2번 안을 기각한 이유: 대칭과 단순함을 얻는 대신 교착이 새로 생긴다. InnoDB 가 한쪽을 롤백하면 소비자 쪽은 재시도로 수렴하지만,
확정 쪽이 지면 PG 환불은 끝났는데 원장 확정이 claim lease 만료 뒤 reconcile 까지 밀린다. 1번 안은 같은 경합을 막으면서 기존 잠금 순서를 바꾸지 않는다.
대가는 미존재 경로의 조회가 두 번이라는 것과 D-112 와 모양이 조금 다르다는 것이다.

생성 쪽은 D-112 와 같다. Payment 를 INSERT 한 뒤 취소 marker 를 잠금 조회한다. 있으면 `cancelBeforePayment` 를 적용하고 그 엔티티를 PK 로 지운다.
그 뒤에 예약 결과 marker 를 잠금 조회하므로 취소 우선 규칙(CANCELLED 면 예약 결과 미적용)은 그대로다.

새 잠금의 교착 점검: 생성 쪽은 processed_events, payments INSERT, 취소 marker 잠금 조회, 예약 marker 잠금 조회, 자기 결제 행 UPDATE 순서다.
취소 쪽 미존재 경로는 payments 키 구간 잠금 뒤 취소 marker INSERT 만 한다. 취소 쪽이 기다릴 수 있는 것은 생성 쪽이 이미 잡은 취소 marker 구간 잠금인데,
그 생성 쪽은 payments INSERT 를 이미 마쳐 취소 쪽 잠금을 기다리지 않는다. 순환이 없다. D-112 의 예약 결과 경로와 같은 구조다.

## 3. 검증 방법

- 통합 테스트 두 순서. 멈추는 쪽은 바깥 `TransactionTemplate` 안에서 handler 를 끝낸 뒤 커밋 전에 latch 로 선다(D-112 테스트와 같은 틀).
  풀어 준 뒤 DB 에서 `payments.status='CANCELLED'`·`payment_cancellations` 0행을 확인한다.
  - 생성 쪽 선INSERT 순서: 생성 쪽이 Payment INSERT 와 marker 잠금 조회를 마치고 커밋 전에 멈춘 상태에서 취소 쪽을 시작한다.
    실패 주입: 수정 전 코드에서 실패해야 한다. 취소 쪽 재조회를 빼면(비잠금 조회만) 미커밋 Payment 를 못 보고 marker 를 남겨 실패해야 한다.
  - 취소 쪽 선잠금 순서: 취소 쪽이 잠금 조회와 marker 저장을 마치고 커밋 전에 멈춘 상태에서 생성 쪽을 시작한다.
    실패 주입: 수정 전 코드에서 실패해야 한다. 생성 쪽 marker 조회를 비잠금으로 바꾸면 스냅숏이 취소 커밋 전이라 marker 를 못 보고 실패해야 한다.
    엔티티 삭제를 파생 `deleteByOrderId` 로 되돌리면 marker 잔존 1 로 실패해야 한다.
  - 각 실패 주입은 코드를 바꿔 실패를 확인하고 되돌린다. 결과는 audit 에 남긴다.
- 단위 테스트: 비잠금 조회가 비고 잠금 조회가 PENDING Payment 를 찾으면 CANCELLED 로 바꾸고 marker 를 저장하지 않는다. APPROVED 경로는 잠금 조회를 부르지 않는다.
- `./gradlew :payment-service:test` 와 `scripts/*-lint.sh`(특히 `integration-test-container-lint.sh`) 통과.

## 미해결

- 예약 결과 경로(D-112)는 Payment 가 있어도 잠금 조회한다. 그 경로는 환불 테이블을 건드리지 않아 이번 교착 분석에 걸리지 않으므로 그대로 둔다.
- 취소 marker 의 고아 행(선행 `order.created` 가 DLQ 에 남은 주문)은 기존과 같이 남는다. `order.created` replay 때 적용된다.
