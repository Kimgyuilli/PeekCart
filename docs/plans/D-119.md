# D-119 — outbox 발행 상태의 사이클 단위 저장

## 1. 명제
아래 중 하나라도 성립하면 미완이다.
- `OutboxPollingService.pollAndPublish` 가 broker ack 를 받은 이벤트마다 `save()` 를 따로 불러, 이벤트 한 건마다 커넥션 획득과
  커밋을 한 번씩 쓴다. 부하로 공유 자원이 포화되면 poller 의 이벤트 1건 비용이 획득 1회 비용(D-110 풀 10: 대기 73ms + 점유 13ms)이 된다.
- 바뀐 발행·커밋 실패 의미(중복 범위가 1건에서 사이클 단위로 커짐, `published_at` 이 ack 시각이 아니라 기록 시각)가 ADR 로 정해지지
  않았고 ADR-0045 Alternative C 의 기각이 그대로 남아 있다.
- 로컬 probe 로 부하 중 발행률이 얼마나 바뀌는지 사전 등록한 기준으로 판정하지 않았다.

사용자 결정(2026-11-19): ADR + 구현 + 로컬 검증까지 한다. GKE 에서 점유 증가의 자리(J4)를 확인하는 일은 다음 과금 세션으로 넘긴다.
J4 결과는 C 를 고를지를 바꾸지 않고, C 만으로 충분한지(용량 확보가 더 필요한지)를 가른다. 근거는 §2 의 D-110 해석이다.

### 설계 (ADR-0049 초안의 결정)
- **D1 저장 단위**: 사이클 안에서 ack 받은 이벤트 id 를 모아 루프를 나올 때 한 문장으로 저장한다.
  `UPDATE outbox_events SET status='PUBLISHED', published_at=:now WHERE id IN (:ids)`. 커넥션은 이 문장 동안만 잡는다. 발행 중에는 쥐지 않는다.
  상태 조건은 두지 않는다. 지금의 merge 도 행 상태를 보지 않고 덮는다.
- **D2 실패 경로는 그대로**: 발행 실패 이벤트의 `retryCount`·`FAILED` 저장은 이벤트마다 한다. 실패는 드물고, 묶으면 소진 알림과 저장의 순서를 다시 정해야 한다.
- **D3 실패 의미**: 묶음 저장이 실패하거나 프로세스가 ack 와 저장 사이에서 죽으면 그 사이클에 ack 받은 이벤트가 모두 PENDING 으로 남아
  다음 사이클에 다시 발행된다. 중복 범위의 상한은 1건에서 `batch-size`(500)로 커진다. at-least-once 와 소비 멱등(ADR-0020 D1)은 그대로다.
- **D4 `published_at`**: ack 시각이 아니라 PUBLISHED 를 기록한 시각이다. 차이는 한 사이클 길이 이하다.
- **D5 새 설정 키 없음**: 묶음 크기는 `batch-size` 를 따른다. 따로 두면 동작 정책 키가 4서비스 base yml 에 하나 더 생기고 ADR-0045 의 키 누락 검사도 늘어야 한다.

### 트레이드오프
- 대안 "N건마다 저장"은 중복 범위를 N 으로 줄이지만 상수 하나와 경계 처리가 늘고, 사이클이 1초 안팎인 지금 조건에서 얻는 것이 적다. ADR 에 기각 사유로 남긴다.
- 대안 "한 트랜잭션 안에서 이벤트별 UPDATE"(saveAll)는 `published_at` 을 ack 시각으로 지키지만 문장 왕복이 이벤트 수만큼 남아 점유가 길어진다.
- 대안 B(비동기 pipelining)는 저장 횟수를 줄이지 않는다(D-110 J3). C 뒤에 남는 병목이 순차 send 이면 그때 다룬다(재검토 조건).

### ADR 판단
필요하다. 발행·커밋 실패 의미가 바뀌고 4서비스에 걸치며, ADR-0045 의 Alternative C 기각을 뒤집는다(ADR-0045 재검토 조건 1).

## 검증 방법
- V1 단위(`OutboxPollingServiceTest`), 실패 주입:
  (a) 3건 모두 성공 → `markPublished([e1,e2,e3])` 1회, `save` 0회.
  (b) e1 성공·e2 실패·e3 성공 → `markPublished([e1,e3])` 1회, `save(e2)` 1회(retry 1).
  (c) deadline·interrupt 로 끊길 때 끊기기 전 성공분만 저장된다.
  (d) `markPublished` 가 예외 → 사이클이 예외로 끝난다(삼키지 않는다).
  (e) 실패 경로 save 예외와 묶음 저장 예외가 겹치면 원래 예외가 던져지고 저장 예외가 suppressed 에 있다.
  (f) ack 0건 사이클은 `markPublished` 를 부르지 않는다.
- V2 통합(`OutboxAtLeastOnceIntegrationTest`, Testcontainers): PENDING 3건을 넣고 첫 사이클의 묶음 저장을 실패시킨다. 3건 모두 PENDING 으로
  남고(DB), 다음 사이클에 3건이 다시 발행되어 토픽에 이벤트마다 같은 eventId payload 가 2회 이상 있는지 확인한다.
  소비 효과 1회는 이 모듈에 `order.created` consumer 가 없어 직접 세지 않는다. 멱등의 전제인 eventId 보존을 단언한다(기존 테스트와 같은 범위).
  주입을 빼면 같은 테스트가 실패하는지 대조해 주입이 실제로 작동했음을 확인한다.
  (정정 2026-11-19: 초안은 `processed_events` 를 센다고 적었으나 기존 테스트도 그것을 세지 않았고 이 모듈에 consumer 가 없다.)
- V3 회귀: `./gradlew test` 전체(4서비스 outbox·replay·DLQ·관측 통합 테스트 포함), `scripts/*-lint.sh`, ci.yml CI policy lint.
- V4 로컬 측정: D-110 과 같은 명령(`PEEKCART_POOL_PROBE=true ... OrderPoolContentionLocalProbeTest`)과 같은 `extract.py` 를 쓴다.
  같은 세션에서 기준 코드(main `8433ad29`, worktree)의 풀 10, 변경 코드의 풀 10·64 를 각각 3반복 돌린다.
  **판정은 결과를 보기 전에 여기서 고정한다.** 지표는 풀 10 의 **따라잡기 비율** = 부하 발행/s ÷ 부하 반복(주문)/s, 3반복 중앙값.
  - K1 충족: 0.9 이상. 로컬에서 부하 중 발행이 주문 수신을 따라간다.
  - K2 부분: 0.9 미만이고 같은 세션 기준 코드의 10배 이상. 구조 병목은 풀렸고 다음 병목이 남았다. 남은 병목(순차 send 인지)을 기록하고
    ADR-0049 재검토 조건에 연결한다.
  - K3 미충족: 기준 코드의 10배 미만. C 가 로컬 병목을 풀지 못했다. ADR-0049 를 Accepted 로 올리지 않고 사용자와 처분을 정한다.
  - 정합성: 반복마다 `order.created` PUBLISHED 수 = 주문 수, PUBLISHED 가 아닌 outbox 0, poller 끈 대조 구간의 DB 발행 0(기존 probe 단언).
  - 기준 코드 풀 10 의 발행비가 D-110(0.03)과 자릿수가 다르면 기계 조건이 바뀐 것이므로 D-110 수치와 비교하지 않고 같은 세션 값만 쓴다.
