# ADR-0031: e2e 음성 대조군의 결함 주입 경계

- **Status**: Accepted
- **Date**: 2026-09-28
- **Deciders**: PeakCart
- **관련 Phase**: Phase 5

## Context

`saga-e2e-smoke.sh --negative-control` 은 결함을 일부러 주입하고 해당 검사가 실패하는지 매 PR 에서
확인한다(`docs/06-testing-strategy.md` §13-1-a). D-033 실측 run
[36075940872](https://github.com/Kimgyuilli/PeekCart/actions/runs/36075940872) 의 대조군 잡 로그를
대조군별로 나누면 461초 중 405초(88%)가 "일어나지 않음" 을 고정 상한으로 기다리는 시간이다.

| 대조군 | 소요 | 대기 |
|---|---|---|
| ① poller 정지 → A 실패 | 186초 | 예약 대기 `DEADLINE` 180초 |
| ② product-service 정지 → A 실패 | 1초 | 없음 |
| ④ listener 부재 → readiness 실패 | 181초 | group 검사 180초 |
| ③ 재고 충분 → B 실패 | 49초 | 취소 부재 45초 |

시간보다 먼저 드러난 것은 **검출력 결함**이다.

- ① 과 ② 는 bash `expect_fail` 로 판정한다. 명령이 **어떤 이유로든** 실패하면 통과다
- ② 가 1초에 끝나는 이유가 그것이다. 시나리오 A 첫 줄 `create_product` 가 멈춘 product-service 의
  admin API 를 불러 거기서 죽는다. 주장한 불변식 "예약이 성립하지 않는다" 에 닿지 않는다
- 반면 ③ 과 ④ 는 runner(`saga_e2e.py`) 안의 대조군 함수라 실패 사유를 특정한다

이 결정의 복원 확인(D2-3)을 처음 돌렸을 때 결함이 하나 더 드러났다. ① 은 락을 풀 때 ShedLock 행을
**DELETE** 했다. ShedLock(6.3.1 `StorageBasedLockProvider`)은 행을 만든 적이 있다고 기억하면
(`LockRecordRegistry`, `WeakHashMap`) INSERT 없이 UPDATE 만 하므로, 행이 사라지면 UPDATE 가 0행이 되어
poller 가 GC 가 그 기억을 치울 때까지 락을 잡지 못한다. 로컬 실측에서 ① 이후 order-service 의
`order.created` 가 전부 `PENDING` 에 머물렀다. 그 상태에서 ③ 은 예약도 취소도 일어나지 않아 **재고와
무관하게 통과**한다. CI 에서도 같은 일이 GC 시점에 따라 일어났을 수 있다.

현재 쓰는 주입 수단은 전부 스택 바깥에 있다. ShedLock 행 선점, 컨테이너 정지, pg-stub 의
paymentKey 별 불변 script, 입력 데이터(재고 수량)다. 서비스 코드에 테스트 전용 제어 표면은 없고,
`Clock` 주입도 없다.

## Decision

**결함 주입은 스택 바깥의 기존 수단으로만 한다. 대조군은 runner 안에서 실패 지점을 특정하고,
"일어나지 않음" 은 고정 상한이 아니라 주입 성립의 양성 관측과 시스템 자신의 주기에서 유도한 창으로
증명하며, 주입을 거둔 뒤 같은 흐름이 되살아나는지로 창이 공허하지 않음을 확인한다.**

### D1. 실패 지점 특정은 runner 가 한다

- 대조군은 모두 `saga_e2e.py negative-control <이름>` 함수로 둔다. bash 는 스택 조작(정지·기동·
  ShedLock 행)만 하고 판정은 `expect_pass` 하나로 받는다. `expect_fail` 은 없앤다
- 대조군이 기다리는 지점은 시나리오와 **같은 함수**를 쓴다. 예약 대기는 `wait_reserved()` 하나를
  시나리오 A 와 대조군 ①② 가 공유한다. 대조군이 시나리오와 다른 단언을 검사하면 시나리오의 검출력을
  말해주지 못한다
- 타임아웃은 어느 대기에서 났는지 `Timeout.stage` 로 싣는다. 대조군은 기대한 stage 가 아니면 실패한다.
  사람이 읽는 메시지 문자열을 대조하지 않는다(문구를 다듬으면 대조군이 깨진다)

### D2. "일어나지 않음" 은 원인 관측 + 유도한 창 + 복원 확인으로 증명한다

셋이 한 묶음이다. 하나라도 빠지면 부재가 결함 때문인지 스택이 죽어서인지 가르지 못한다.

1. **원인 관측**: 주입이 실제로 성립했음을 양성으로 본다. ① 은 이 주문의 `order.created` outbox 행이
   `PENDING` 에 머문다. ② 는 같은 행이 `PUBLISHED` 인데(이벤트는 나갔다) product-service 가 응답하지 않는다
2. **유도한 창**: 결함이 없었다면 결과가 도착했을 시간이다. 정상 경로의 지연은 outbox poller 주기
   (`app.outbox.polling.delay`, 기본 5초)와 한 홉의 소비로 정해지므로 ①② 의 창은 poller 6주기인
   **30초**로 둔다. ④ 는 멈춘 consumer 의 group 이탈이 세션 타임아웃(Kafka 기본 45초, 이 레포는 덮지
   않는다) 안에 반영되므로 **60초**다
3. **복원 확인**: 주입을 거두면 같은 주문의 예약이 도착해야 한다. ① 은 ShedLock 행 삭제 후, ② 는
   product-service 재기동 후 `wait_reserved()` 가 성공해야 한다. 이것이 창이 "짧아서 못 본 것" 이
   아니라 "결함 때문에 안 온 것" 임을 보장한다

창을 짧게 잡는 것의 비용은 flake 가 아니라 **검출 범위**다. 창보다 느린 우회 경로는 잡지 못한다.
이 비용을 받아들이는 근거는 우회 경로가 있다면 정상 경로와 같은 홉 수를 지나므로 같은 창 안에
도착한다는 것이다.

③ 의 창은 바꾸지 않는다. "취소가 오지 않음" 을 가를 구조적 근거가 없다. 취소를 만드는 경로가 예약
실패 외에도 있고(결제 타임아웃 잡 등), 그 경로의 지연을 주기에서 유도할 수 없다. 45초 고정을 유지한다.
다만 원인 관측은 더한다. 재고가 충분해 예약이 **실제로 성공했음**을 먼저 본 뒤에 취소 부재를 기다린다.
그래야 saga 가 아예 안 도는 상태가 통과로 보이지 않는다.

주입을 거두는 조작은 대상 도구의 상태 모델을 따른다. ShedLock 해제는 행 DELETE 가 아니라
`lock_until` 을 과거로 돌리는 UPDATE 다(Context 참조).

### D3. 서비스에 테스트 전용 제어 표면을 두지 않는다

poller 일시정지 엔드포인트, 테스트 프로파일 전용 빈, `Clock` 주입 모두 도입하지 않는다.
현재 대조군 4종은 스택 바깥 수단으로 결정적으로 주입된다. 제어 표면은 프로덕션 이미지에 실리고,
실리는 순간 운영 경로의 우회로가 된다.

재검토 조건: 시간 경과가 원인인 결함(주문 만료·리스 만료 잡)을 대조군으로 검증해야 할 때.
그 결함은 스택 바깥에서 시간을 제어할 수단이 없다. 그때 `Clock` 주입을 별도 ADR 로 판단한다.

## Alternatives Considered

### Alternative A: 고정 대기를 그대로 두고 검출력 결함만 고친다

- **장점**: 변경이 가장 작다. 창 유도의 논증이 필요 없다
- **단점**: 405초가 그대로 남는다. ② 를 불변식에 닿게 고치면 예약 대기 180초가 하나 더 붙는다
- **기각 사유**: 고정 180초는 부재의 근거가 아니라 시나리오 성공 경로용 상한을 빌려 쓴 값이다.
  원인 관측과 복원 확인이 있으면 긴 창이 주는 추가 증거가 없다

### Alternative B: 서비스에 테스트 제어 엔드포인트를 둔다

- **장점**: poller 정지·재개, 시간 진행을 명령으로 결정적으로 제어한다
- **단점**: 프로덕션 이미지에 운영 경로를 멈추는 표면이 실린다. 프로파일로 막아도 설정 한 줄로 열린다
- **기각 사유**: 현재 대조군 4종은 스택 바깥 수단으로 충분하다(D3). ADR-0029 가 테스트용 토글을
  "테스트에서 기본 off" 로만 두고 운영 표면을 만들지 않은 것과 같은 원칙이다

### Alternative C: 대조군을 JVM 통합 테스트로 옮긴다

- **장점**: 스택 조작이 없어 빠르고 결정적이다
- **단점**: 이미지·네트워크·서비스 연결은 서비스 단위로 증명할 수 없다
- **기각 사유**: 이 결정의 범위가 아니다. 어떤 대조군을 옮길 수 있는지는 D-042 가 이 ADR 의 대조군
  목록을 입력으로 판정한다

## Consequences

### 긍정적 영향

- ② 가 주장한 불변식을 실제로 검증한다. 종전에는 product-service 의 admin API 가 죽었다는 것만 봤다
- 모든 대조군이 실패 지점을 특정한다. "아무 실패나 통과" 경로가 사라진다
- ① 의 해제가 poller 를 되살린다. 종전에는 GC 시점에 따라 대조군 나머지 내내 poller 가 죽어 있었고
  ③ 이 그 상태에서 공허하게 통과할 수 있었다
- 대조군 소요가 줄 것으로 예상한다. ① 186초 → 약 40초, ④ 181초 → 60초. ② 는 1초 → 약 45초로 는다
  (공허했던 것을 고친 비용이다). 실측은 계획서 §검증 기록에 남긴다

### 부정적 영향 / 트레이드오프

- 창(30초·60초)이 설정값에 기대는 상수다. poller 주기나 세션 타임아웃을 크게 바꾸면 창을 다시
  유도해야 한다. 상수 옆에 유도 근거를 주석으로 둔다
- 창보다 느린 우회 경로는 잡지 못한다(D2)
- 대조군이 상태 파일로 여러 단계에 걸친다(② 는 준비 → 정지 → 검사 → 기동 → 복원 확인).
  단계 사이 상태는 대조군 출력 디렉터리의 JSON 하나로 넘긴다

### 후속 결정에 미치는 영향

- D-042 는 이 ADR 의 대조군 목록(`docs/06-testing-strategy.md` §13-1-b)을 입력으로 쓴다
- 시간 제어가 필요한 대조군이 생기면 D3 의 재검토 조건이 발동한다
