# ADR-0027: base MySQL CPU 상한 = 2000m — 공통 읽기/쓰기 천장의 해제 (D-029)

- **Status**: Accepted
- **Date**: 2026-09-22
- **Deciders**: Kimgyuilli
- **관련 Phase**: Phase 4

## Context

`k8s/base/infra/mysql/mysql.yml` 의 MySQL 컨테이너는 `requests.cpu: 250m` /
`limits.cpu: 500m` 으로 돌고 있었다. 이 값은 Phase 1 minikube 환경(4코어/8GB)을
기준으로 정한 것이고, 그 뒤 **한 번도 재검토되지 않았다.**

그 사이 성능 측정이 두 번 있었고, **서로 독립적으로 같은 곳을 가리켰다.**

### 측정 ① 주문 경로 (D-002bc, [#119](https://github.com/Kimgyuilli/PeakCart/pull/119))

`evidence/d002bc-gke-20260917.md`

| MySQL 상한 | 주문 생성 | p95 | MySQL 실사용 |
|---|---|---|---|
| 500m | 54.0 건/초 | 2.38s | **498m / 500m — 한도 도달** |
| **2000m** | **158.6 건/초** | **879ms** | 1,259m / 2000m (여유) |

**×2.94.** 500m 조건은 `dropped_iterations 26,401` 로 목표 300 rps 를 달성하지 못했다.

### 측정 ② 읽기 경로 (D-026/D-002a, [#129](https://github.com/Kimgyuilli/PeakCart/pull/129))

`evidence/d026-d002a-read-ceiling-20260920.md` — 30런, 셀당 3회 중앙값, A→B→A′ 되돌림 설계.

| 블록 | MySQL | detail OFF | MySQL 스로틀(s/60s런) |
|---|---|---|---|
| A | 500m | 393.4 rps | 147.6 |
| B | **2000m** | **903.8 rps** | **0.1** |
| A′ | 500m 복귀 | **392.6 rps** (+0.2%) | 105.0 |

**×2.30.** 되돌림이 **+0.2%** 로 복귀했으므로 재시작·드리프트 효과가 아니다.
스로틀이 147.6초 → 0.1초로 **소멸**했다.

### 왜 이것이 의미 있는가

D-002a 증적(`d002a-gke-20260916-0030.md:111`)은 읽기 경로의 공통 천장(detail 378.1 ≈
list 380.0)을 두고 **"CPU 도 Hikari 풀도 아니다 — MySQL 내부가 남았다"** 로 닫았다.
그때 배제한 "CPU" 는 **product-service 의 CPU** 였고, **MySQL 자신의 CPU 상한은 그
"MySQL 내부" 안에 미분리 상태로 들어가 있었다.** D-026 세션이 그것을 분리했다.

즉 두 측정이 말하는 것은 하나다 — **`limits.cpu: 500m` 은 읽기와 쓰기 양쪽의
공통 천장이었다.**

### 왜 ADR 인가

`mysql.yml` 은 **overlay 8개 전부가 공유한다.** 참조 경로가 두 갈래다:

- `gke` · `minikube` → `../../base` 경유 (`k8s/base/kustomization.yml`)
- `gke-d002a` · `gke-d002bc` · `minikube-rotation-drill` → `mysql.yml` **직접 참조**

이 결정을 6개월 뒤 뒤집으려면 이 파일 밖도 같이 봐야 한다 — 측정 overlay 2개의
"base 와 같은 값이다" 주석, `gke-d002bc` patch 의 "base 와 동일하게 둔다" 주석이
전부 base 값에 묶여 있다. 되돌림 비용이 파일 경계를 넘으므로 ADR 이다.

## Decision

**base `mysql.yml` 의 `limits.cpu` 를 500m → 2000m 로 올린다.
`requests.cpu` 는 250m 그대로 둔다.**

값을 2000m 로 정한 이유는 **그것이 측정된 값**이기 때문이다. 500m 과 2000m 사이는
측정하지 않았고, 2000m 조건의 실사용은 1,259m 로 여유가 있었다(즉 이 값은 실사용에
타이트하게 맞춘 값이 아니다). 실사용 + 마진으로 1500m 같은 수를 고를 수도 있었으나,
**측정하지 않은 숫자를 발명하지 않는다** — 재측정으로 더 좁힐 수 있으면 그때 좁힌다.

`requests` 를 건드리지 않는 이유도 같다. A→B→A′ 되돌림 실험이 흔든 손잡이는
**`limits` 하나**였고 ×2.30 은 그 손잡이의 효과다. `requests` 를 동반 상향하면
**측정 범위를 넘어선 변경**이 되고, 되돌릴 때 두 축을 같이 봐야 한다.

## Alternatives Considered

### Alternative A: base 500m 유지 · `requests` 동반 상향 없이 상한만 2000m — **채택**

- **장점**: 측정된 손잡이 하나만 움직인다 · `requests` 불변이므로 **스케줄링 영향 0**
  (k8s 스케줄러는 `limits` 를 보지 않는다) · QoS 가 Burstable 로 유지돼 기존 거동과 같은 계열
- **단점**: 1,000m 남짓의 버스트가 **보장되지 않는다.** 노드 압박 시 `requests` 250m
  초과분이 먼저 깎인다 — "잘 될 땐 3배, 안 될 땐 그대로"
- **채택 사유**: 단점이 실재하지만 **그것을 측정하지 않았다.** 아래 Alternative B 참조

### Alternative B: `limits` 2000m + `requests` 를 실사용(1,259m)에 맞춰 상향 — 기각

- **장점**: 버스트가 보장된다. 증적 §미해결 2 가 지목한 **노드 레벨 CPU 경합**
  (MySQL 과 product-service 가 같은 2노드를 공유) 가설이 사실이면 이쪽이 맞다
- **단점**: `requests` 는 예약이므로 **유휴 시에도 점유**한다. GKE e2-standard-4 ×2
  (할당가능 ~7.9 vCPU) 에서 base requests 합이 2100m → 2850m 로 오른다. 포트폴리오
  규모에서 유휴 예약을 늘리는 것은 비용이다
- **기각 사유**: **노드 레벨 경합을 측정하지 않았다.** 증적 §미해결 2 가 "DB 를 안
  건드리는 캐시 ON 경로(캐시 miss 0)가 DB CPU 한도에 반응했다" 를 **분리하지 못한 채**
  남겨 뒀고, 그 후보 중 하나가 바로 이 노드 경합이다. **추측으로 메우지 않는다.**
  경합이 측정으로 확인되면 이 ADR 을 이어받는 결정으로 `requests` 를 다룬다

### Alternative C: base 는 500m 유지하고 `gke` overlay 에만 2000m patch — 기각

- **장점**: minikube 로컬이 영향을 안 받는다 · 환경별로 값을 가를 수 있다
- **단점**: **base 값이 "포화로 확인된 값"으로 남는다.** 500m 은 주문 경로에서
  498m/500m 로 한도에 닿았고 읽기 경로에서 60초당 147.6초를 스로틀당한 값이다.
  그것을 기본값 자리에 두면 새 overlay 는 기본적으로 고장난 설정을 상속한다
- **기각 사유 (두 겹)**:
  1. **minikube 보호라는 명분이 성립하지 않는다.** `limits` 는 스케줄링에 쓰이지
     않는다. minikube(4코어) 의 base requests 합은 **2100m < 4000m** 로 변경 전후가
     같고, 현재 `limits` 합은 이미 **7250m = 4코어의 1.8배**로 오버서브스크립션 상태다.
     이 변경은 새 성질을 도입하지 않는다
  2. **ADR-0007 의 취지와 어긋난다.** ADR-0007 은 문언상 `application-{profile}.yml`
     을 다루므로 k8s overlay 에 직접 적용되지는 않는다. 그러나 그 판단 기준
     ("환경마다 달라야 하는 값인가, 아니면 동작 규약인가")은 그대로 유효하고,
     CPU 상한은 **연결 정보가 아니라 동작 규약**이다. 환경 차이가 정당화되려면
     "이 환경은 그 값을 감당 못 한다" 는 근거가 필요한데 위 1 이 그것을 부정한다

## Consequences

### 긍정적 영향

- 주문 경로 처리량 **×2.94**(54 → 158.6 건/초), p95 2.38s → 879ms
- 읽기 경로 detail 처리량 **×2.30**(393 → 904 rps), MySQL 스로틀 147.6s → 0.1s
- base 기본값이 **포화로 실측된 값에서 벗어난다** — 새 overlay 가 고장난 설정을 상속하지 않는다
- D-002a 가 "MySQL 내부" 로 뭉갰던 질문이 닫힌다

### 부정적 영향 / 트레이드오프

- **버스트가 보장되지 않는다** — `requests` 250m, 실사용 최대 1,259m. 초과분은
  노드 압박 시 먼저 깎인다 (Alternative B 기각의 대가)
- **minikube 오버서브스크립션이 7250m → 8750m 로 깊어진다** (4코어의 2.2배).
  로컬은 400 VU 부하를 돌리지 않으므로 동시 버스트가 발현할 가능성은 낮지만,
  여러 서비스가 동시에 바쁜 로컬 시나리오에서 체감 경합이 늘 수 있다
- **`Recreate` 전략(D-023, RWO PVC 단일 인스턴스)이라 이 값을 바꾸면 Pod 가 재기동되고
  InnoDB 버퍼풀이 식는다.** 배포 시 첫 요청들이 느리다. D-023 이 기록한 그대로 —
  `mysql.yml:24` 주석이 트리거를 "파드 템플릿을 바꾸는 모든 apply" 로 적고 있고
  **"MySQL 한도 변경 시 실제 재현"** 이 그 사례다. 이 변경이 바로 그 트리거다

### 이 결정은 세 가지를 모르는 채로 내려졌다

**이것을 숨기지 않는다.** 뒤의 측정이 아래를 채우면 이 ADR 은 갱신 대상이다.

1. **읽기 경로 `list` 배속이 확정값이 아니다.** A 367.6 → B 1406.4 → A′ 409.9 에서
   되돌림 오차 **+11.5%** 로 게이트(±10%) **실패**, 블록 B 산포 **44.5%**
   (개별 782.7 / 1406.4 / 1408.4 — 첫 런만 낮다, 버퍼풀 미가열). 효과 크기가
   오차보다 크므로 **방향은 확실하나 배속 숫자는 미확정**이다. 이 ADR 이 의존하는
   숫자는 되돌림 게이트를 통과한 **detail ×2.30** 과 주문 경로 **×2.94** 다
2. **2000m 에서도 천장이 남아 있고 그 정체를 모른다.** detail OFF 가 **904 rps** 에서
   멈추는데 그 셀의 MySQL 스로틀은 **0.1초**다 — 즉 **MySQL CPU 가 아니다.** 이 결정은
   "천장을 없앴다" 가 아니라 **"천장 하나를 걷어냈다"** 다
3. **캐시 ON 경로가 DB CPU 에 반응한 이유를 모른다.** list ON 이 894.9 → 2249.2 인데
   이 셀의 캐시 miss 는 **0** 이다. DB 를 안 건드리는 경로가 DB CPU 한도에 반응했다.
   후보는 노드 레벨 CPU 경합 또는 cgroup `cpu.stat` 판독 범위이고, 그 세션은
   **분리하지 못했다.** 이것이 Alternative B 를 기각한 근거이기도 하다

### 후속 결정에 미치는 영향

- 위 3 이 노드 경합으로 확인되면 **`requests` 처분을 다루는 후속 ADR** 이 필요하다
  (이 ADR 의 Alternative B 재개)
- 위 2 의 새 천장(904 rps)을 분리하는 것이 D-002 계열의 다음 축이다
- 측정 overlay `gke-d002a-mysql-2000m` 은 base 와 값이 같아져 **no-op 이 된다.**
  `list` 재측정(위 1)이 남아 있어 삭제하지 않고 **A/B 대조 쌍으로 보존**한다 —
  이제 대조군은 `-500m`(base 를 끌어내리는 patch)이고 실험군이 base 다
