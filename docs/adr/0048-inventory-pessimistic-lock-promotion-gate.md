# ADR-0048: 재고 비관적 락 승격 게이트의 허용 범위 (contend DLQ/주문 중앙값 0.15%)

- **Status**: Accepted
- **Date**: 2026-11-14
- **Deciders**: 프로젝트 오너 (2026-11-14, D-111 질문 3건)
- **관련 Phase**: Phase 6

## Context

ADR-0025 는 재고 동시성 제어를 `Inventory.@Version` 과 jitter 재시도로 정했다. 비관적 락(Alternative C)은 기각하지 않고
유보했다. 승격 조건은 "부하 세션에서 동일-상품 경합 시 낙관락 충돌률 또는 DLQ 유입이 허용 범위를 넘으면"이다.
허용 범위에는 숫자가 없었다. 숫자가 없으면 어떤 측정 결과로도 승격 여부를 판정할 수 없다.

같은 부하(초당 170건) 비교는 2026-10-25 UTC 세션(D-108 §5)에서 처음 성립했다. 아래 수치는 원자료에서 다시 셈했다.
DLQ 는 product Pod 3개의 `kafka_listener_recovered_total{topic="order.created"}` 차분이고, 주문은 `order.created`
PUBLISHED 건수다. 충돌은 `kafka_listener_delivery_failed_total{cause="optimistic_lock"}` 차분이다.

| run | 주문 | 충돌 (주문 대비) | DLQ | DLQ/주문 |
|---|---|---|---|---|
| contend c1 (유효) | 10,200 | 73 (0.72%) | 5 | 0.049% |
| contend c2 (유효) | 10,194 | 89 (0.87%) | 7 | 0.069% |
| spread s1 (대조) | 10,200 | 0 | 0 | 0 |
| contend 재시도 1 (무효, 드롭 331) | 9,924 | 62 (0.62%) | 7 | 0.071% |
| contend c3 (무효, 드롭 431) | 9,770 | 59 (0.60%) | 8 | 0.082% |

무효 run 은 k6 드롭이 판정 규칙을 넘은 run 이다. DLQ/주문은 유효 run 과 같은 범위에 있다. 재시도 2 는 MySQL 디스크가
가득 찬 구간에 걸려 주문 4,933건에서 멈췄으므로 표에서 뺐다. 이전 세션 값은 다음과 같다.
- 2026-10-24: 0.040~0.068%. 다만 r3 만 목표 부하에 가까웠다.
- Phase 4 `d002bc`: 0.072%. jitter 도입 전이다.

판정에 필요한 사실은 넷이다.

1. **SLO 가 없다.** `03-requirements.md` §7 에는 주문 실패율 목표가 없다. 그래서 절대 수치를 외부에서 끌어올 수 없다.
2. **DLQ 1건은 주문 1건의 실패다.** 예약 결과가 없는 주문은 Order 스케줄러가 예약 미확정으로 취소한다. 집계 시점에
   취소된 주문(c1 3건·c2 7건)은 모두 DLQ 주문이었다. 여기에 Slack 알림과 replay 판단(ADR-0020~0022)이 따라온다.
3. **충돌은 대부분 흡수된다.** 충돌 73·89회 중 DLQ 는 5·7건이다. 흡수된 충돌의 비용은 그 주문이 1·5·30초(±50%)
   backoff 만큼 늦어지는 것이다. 사가 왕복 p50 128~142초는 outbox 폴링이 정한다(D-108 §5, ADR-0045).
4. **run 당 DLQ 가 5~8건이라 잡음이 크다.** 기준선이 그대로여도 건수는 Poisson 분포로 흔들린다(λ ≈ 6). 허용 범위를
   기준선 바로 위에 두면 아무것도 바뀌지 않았는데도 넘는다.

측정 조건도 판정의 일부다. 예약 consumer(`StockReservationConsumer`)는 listener concurrency 1 이고, `order.created`
파티션은 3이며, contend overlay 의 product replicas 는 3이다. 그래서 같은 상품을 동시에 쓰는 writer 는 최대 3개다.
위 수치는 이 상한 아래에서 잰 값이다.

## Decision

**contend 시나리오 유효 run 2개 이상의 DLQ/주문 중앙값이 0.15% 를 넘으면 ADR-0025 의 C 승격 절차를 시작한다.
낙관락 충돌률은 기록하지만 게이트에 넣지 않는다.**

- **(D1) 지표와 산식**: DLQ/주문 = `kafka_listener_recovered_total{topic="order.created"}` 차분 ÷ `order.created`
  PUBLISHED 건수다. 차분은 product 전 Pod 의 원값 전후로 낸다. 측정 하네스(`d078-s3-run.sh`)의 `prom-delta.tsv`·`counts.txt`
  가 이미 두 값을 남긴다.
- **(D2) 측정 조건**: contend 시나리오는 상품 10개, 초당 170건, 60초, `gke-d078-contention` overlay(product replicas 3)다.
  유효 판정은 그 세션 계획서의 드롭 규칙을 따른다.
- **(D3) 표본 규칙**: 유효 run 2개 이상의 중앙값으로 판정한다. run 1개가 넘은 것은 재측정 사유일 뿐 승격 사유가 아니다.
- **(D4) 허용 범위 0.15%**: 기준선 0.059% 의 약 2.5배다. 기준선이 그대로일 때 잡음만으로 넘을 확률은 run 1개 기준
  0.05% 수준이다. 2개 중앙값 기준으로는 사실상 0이다. 그러니 넘었다면 회귀가 실제로 있었다는 뜻이다. 주문 1만 건당 15건이다.
- **(D5) 충돌률은 기록만 한다**: 흡수된 충돌의 비용은 지연이다. 그 지연은 사가 왕복을 정하는 outbox 폴링보다 한 자리
  작다. 흡수되지 못한 충돌은 이미 DLQ 로 잡힌다. 충돌률은 측정 기록에 남겨 추세만 본다.
- **(D6) 넘었을 때**: ADR-0025 대로 한다. C 의 DB 비용(product 커넥션·행 락 점유, MySQL CPU)을 같은 시나리오로 잰다.
  그 결과로 D1 을 부분 무효화하는 ADR 을 쓴다. 측정 없이 바로 바꾸지 않는다.
- **(D7) 판정이 무효가 되는 변경**: 아래가 바뀌면 기존 판정은 무효다. 다음 contend 측정까지 게이트는 미판정이다.
  - 동시 writer 수: `order.created` 파티션, product replicas, 예약 listener concurrency
  - 예약 트랜잭션의 구성: 선검사·차감·원장·outbox 저장 외의 쓰기가 늘어나는 경우
  - product error handler 의 재시도 예산과 backoff
  - contend 상품 수

**현재 판정**: 유효 run 중앙값 0.059%(c1 0.049%·c2 0.069%)로 미달이다. 무효 run 을 넣어도 최대 0.082%다.
**C 로 승격하지 않는다.** ADR-0025 D1~D6 은 그대로다.

## Alternatives Considered

### Alternative A: 허용 범위 0.1% (주문 1,000건당 1건)
- **장점**: 읽기 쉬운 숫자다. 기준선 대비 여유가 작아 회귀를 일찍 잡는다.
- **단점**: 실측 최대 0.082% 와 가깝다. 기준선이 그대로여도 run 1개가 넘을 확률이 약 4.3%, 2개 중앙값이 넘을 확률이
  약 1.2% 다. 측정 세션 하나에 GKE 비용이 들어서, 오경보 한 번이 곧 과금 세션 한 번이다.
- **기각 사유**: 잡음만으로 넘는 게이트는 승격 근거가 되지 못한다.

### Alternative B: 충돌률도 게이트에 넣는다 (예: 주문 대비 3%)
- **장점**: ADR-0025 의 문구("충돌률 또는 DLQ 유입")를 그대로 따른다. DLQ 가 늘기 전의 경합 증가를 먼저 본다.
- **단점**: 충돌률 상한에는 DLQ 보다 더 근거가 없다. 흡수된 충돌의 비용(지연)이 사가 왕복에서 보이지 않는다(Context 3).
  두 지표 중 하나만 넘어도 승격을 검토하게 하면 근거 약한 쪽이 판정을 정한다.
- **기각 사유**: 사용자에게 보이는 결과(주문 실패)에 묶인 DLQ 하나로 판정한다. 충돌률은 D5 대로 추세만 본다.

### Alternative C: 지금 비관적 락으로 승격한다
- **장점**: 충돌과 재시도가 사라진다. 다품목 순서를 맞추면 "락 ⊃ 트랜잭션"이 구조로 성립한다.
- **단점**: 행 락과 커넥션을 트랜잭션 끝까지 잡는다. 부하 중 병목은 이미 DB 쪽이다. order Hikari 풀이 한계선이고
  (D-108 ①), 점유 증가가 MySQL 쪽인지도 아직 미판정이다(D-110, D-119). C 의 DB 비용은 측정한 적이 없다.
- **기각 사유**: 측정이 게이트 아래다. DB 를 더 누르는 변경을 할 근거가 없다.

## Consequences

### 긍정적 영향
- ADR-0025 의 승격 게이트가 측정 결과로 판정할 수 있는 규칙이 된다. 다음 contend 세션은 이 산식을 인용하면 된다.
- 기존 하네스 출력(`counts.txt`·`prom-delta.tsv`)만으로 계산된다. 새 지표나 코드가 필요 없다.
- 표본 규칙이 run 1개의 잡음으로 과금 세션과 설계 변경이 시작되는 것을 막는다.

### 부정적 영향 / 트레이드오프
- 0.15% 에는 외부 근거가 없다. 기준선과 잡음에서 나온 숫자라 "회귀했는가"는 답하지만 "사용자에게 충분한가"는 답하지 않는다.
  SLO 가 생기면 그 값이 우선한다.
- 기준선 표본이 유효 run 2개뿐이다. 다음 측정에서 기준선 자체가 움직이면 2.5배라는 여유도 다시 봐야 한다.
- 충돌률이 게이트에서 빠지므로 DLQ 로 번지기 전의 경합 증가는 기록을 읽어야만 보인다.
- 게이트 계산은 자동화하지 않는다. 측정 계획서가 이 ADR 을 인용하지 않으면 판정이 빠질 수 있다.

### 후속 결정에 미치는 영향
- D7 의 변경(파티션 증설, replicas, 예약 트랜잭션 구성, 재시도 정책)을 계획할 때 contend 재측정을 같이 계획한다.
- SLO 를 정하게 되면 D4 를 그 값으로 바꾸는 ADR 을 쓴다.
