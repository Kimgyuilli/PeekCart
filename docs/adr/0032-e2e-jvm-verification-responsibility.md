# ADR-0032: 실제 스택 e2e 와 JVM 테스트의 검증 책임 경계

- **Status**: Accepted
- **Date**: 2026-09-28
- **Deciders**: PeakCart
- **관련 Phase**: Phase 5

## Context

실제 스택 e2e(`scripts/e2e/saga_e2e.py`)는 readiness 5항, 사가 시나리오 4종의 단언, 음성 대조군 6종을
맡는다(`docs/06-testing-strategy.md` §13-1-a·b). 한편 서비스마다 Testcontainers 기반 JVM 통합 테스트가
같은 사가의 상당 부분을 다시 검증한다. D-042 는 둘의 책임이 겹치는 곳을 찾아, 서비스 단위에서
결정적으로 증명할 수 있는 것을 JVM 으로 옮기는 방안을 검토했다. 전 항목의 분류와 근거는 계획서
`docs/plans/done/task-d042-verification-responsibility.md` §4 에 있다.

검토 과정에서 드러난 사실은 네 가지다.

1. **e2e 단언 하나가 두 가지 주장을 싣는다.** "이 이벤트가 실제 토픽·group·HTTP 를 거쳐 다른 서비스에
   닿는다"(배선)와 "도착한 입력으로 올바른 상태를 만든다"(로직)다. 예를 들어 "주문이 CANCELLED 가 된다"
   는 `payment.failed` 가 order-service 의 group 에 도착한다는 것과, 도착한 이벤트로 주문을 취소한다는
   것을 함께 주장한다. 단언을 한 덩어리로 분류하면 "JVM 과 중복" 과 "스택에서만 증명 가능" 이 동시에 참이
   된다
2. **JVM 은 배선을 보지 못한다.** 테스트에서 `@KafkaListener` 는 기본 off 다(ADR-0029). 소비자 테스트는
   핸들러에 envelope 를 직접 넣는다. 이벤트 payload 타입은 `common` 모듈을 생산자와 소비자가 같이 쓰므로
   같은 커밋 안의 필드 불일치는 컴파일이 막는다. 남는 틈은 토픽 이름, group id, 서비스별 직렬화 설정,
   이미지에 실린 설정과 스케줄러다. 앱 서비스끼리는 HTTP 로 서로 부르지 않는다. HTTP 경계는 gateway
   라우팅과 Toss(e2e 에서는 pg-stub)뿐이다
3. **로직은 대부분 JVM 에 이미 있다.** e2e 단언이 겨누는 로직 결함 23건을 프로덕션 코드에 주입했다.
   20건은 지목한 JVM 테스트가 실패로 잡았다. 3건은 모듈 테스트 전체가 통과했다. PAY-005 응답 코드,
   `payment.failed` 알림, 예약 실패로 취소된 주문의 알림이다
4. **시간은 단언이 아니라 스택 기동에 있다.** run
   [36338959413](https://github.com/Kimgyuilli/PeekCart/actions/runs/36338959413) 에서 scenarios 잡의
   구간은 infra-up 36초, 토픽 사전 생성 49초, 앱 4개 순차 기동 72초, 시나리오 4종 82초다. 배선을 싣지
   않는 단언(원장·재고 조회 등)은 모두 같은 체인의 다른 대기 뒤에 붙은 조회 1회라, 빼도 시간이 줄지 않는다

## Decision

**실제 스택은 배선을 맡고 JVM 은 로직을 맡는다. e2e 단언은 배선을 싣는 한 남기고, 로직이 e2e 에만
있으면 e2e 를 줄이지 않고 JVM 을 늘린다. 이번 재평가로 제거하는 e2e 단언과 대조군은 없다.**

### D1. 판정 단위는 단언이 아니라 (배선, 로직) 쌍이다

- 배선은 스택 전용이다. 토픽·group·HTTP 경로, 이미지에 실린 설정·migration·스케줄러, compose 토폴로지가
  여기에 든다
- 로직은 JVM 에서 증명할 수 있으면 JVM 이 맡는다
- e2e 단언을 빼려면 두 조건이 모두 필요하다. 로직이 JVM 에 있어야 하고, **그 배선을 다른 e2e 단언이
  이미 지나야 한다**

### D2. "JVM 이 이미 덮는다" 는 결함 주입으로만 성립한다

테스트 이름이 비슷하다는 것은 같은 결함을 잡는다는 증거가 아니다. 판정할 때마다 그 단언이 겨누는 결함을
프로덕션 코드에 넣고, 지목한 JVM 테스트가 실패하는지 본다. 실패하지 않으면 JVM 공백이다. 주입하지 않은
항목은 중복으로 주장하지 않는다(A0 단가 캐시 전제, D3 식별자 non-null 이 이 경우다).

### D3. e2e 에만 있는 로직은 JVM 에 추가한다

e2e 단언은 배선 때문에 그대로 둔다. JVM 에 테스트를 더하면 같은 결함을 PR 의 `test` 잡에서 먼저 잡는다.
`test` 잡은 스택이 필요 없고 서비스별로 병렬로 돈다.

### D4. 음성 대조군은 자기가 검증하는 단언을 따라간다

대조군은 단언이 결함을 잡는지를 검증한다(ADR-0031 D1). 그래서 대조군을 따로 옮기거나 지우는 판단은
없다. 대조군 ①② 는 예약 대기, ④ 는 readiness group 검사, ③ 은 시나리오 B 가 남는 한 남는다.
⑤⑥ 은 compose 토폴로지가 대상이다.

## Alternatives Considered

### Alternative A: 로직이 JVM 에 있는 단언을 e2e 에서 뺀다

- **장점**: e2e 가 "배선만 본다" 는 모양이 선명해진다
- **단점**: 배선을 싣는 단언은 뺄 수 없어 대상이 배선 없는 조회 7건으로 줄어든다. 그 조회들은 시간을
  쓰지 않는다
- **기각 사유**: 얻는 것이 없다. 조회를 빼면 스택 위에서 같은 불변식을 한 번 더 대조하는 효과만 잃는다

### Alternative B: 소비자 계약 테스트(Pact 등)로 배선을 서비스 단위로 옮긴다

- **장점**: 생산자·소비자 호환성을 스택 없이 검증한다
- **단점**: payload 타입이 이미 `common` 공유라 같은 커밋의 필드 호환성은 컴파일이 보장한다. 계약 테스트가
  더하는 것은 배포 버전 스큐뿐인데, 이 레포는 같은 커밋의 이미지를 함께 배포한다
- **기각 사유**: 새 도구·브로커 없이 풀리지 않는 문제가 현재 없다. 버전 스큐는 아래 공백으로 남긴다

## Consequences

### 긍정적 영향

- 어떤 결함을 어느 층이 잡는지 결함 주입 기록으로 남는다(계획서 §4-2)
- JVM 공백 3건이 드러났다. 채우면 그 결함을 스택 없이 먼저 잡는다

### 부정적 영향 / 트레이드오프

- PR 검증 시간은 이 결정으로 줄지 않는다. 전후가 같다
- 로직 결함 20건은 JVM 과 e2e 에서 두 번 검증된다. e2e 쪽 비용은 배선 검증에 이미 포함돼 있다

### 후속 결정에 미치는 영향

- e2e 시간을 줄이려면 스택 기동(토픽 사전 생성, 앱 순차 기동)을 봐야 한다. 이 ADR 의 범위가 아니다
- 배포 버전 스큐(서로 다른 커밋의 생산자·소비자가 공존하는 상태)는 e2e 와 JVM 모두 보지 않는 공백이다.
  무중단 배포에서 서비스별 이미지를 따로 올리게 되면 재검토한다
